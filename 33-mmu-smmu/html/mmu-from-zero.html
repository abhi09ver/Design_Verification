A learning path for freshers · from zero to SMMU

MMU From Zero

No background needed. We start with "what is an address" and climb one small step at a time until you can explain how a System MMU protects memory, and how a verification engineer tests it.

Each level has the same four parts: a story you already know, the real thing it stands for, a toy you can play with, and one sentence to remember.

Level 1

Memory is a long street of numbered houses

The story

Picture a very long street. Every house has a number: 0, 1, 2, 3… Each house holds exactly one small thing. To fetch something, you just say the house number.

The real thing

RAM is a huge list of bytes. Each byte has a number called its address. The CPU says "read address 2" or "write 13 into address 4". A real machine has billions of addresses.

An address is just a house number for one byte of memory.

Level 2

The problem: many programs, one street

The story

Now imagine a game, a browser and a music app all living on the same street. The game writes its score to house 500. The browser also picks house 500 for a password. Now they overwrite each other. Worse, a bad app could walk over and read the password.

Problem 1: collisions

Two programs choose the same address by accident and break each other.

Problem 2: snooping

A program reads or changes memory that belongs to someone else.

Problem 3: messy space

Free memory ends up in scattered little holes, so a program needing a big block can't find one.

If everyone uses real addresses directly, nobody is safe.

Level 3

The fix: pretend addresses and a translator at the gate

The story

A hotel. Every guest's key card says "Room 1". Guests never see the real room numbers. When you tap your card, the front desk looks you up and sends you to the real room, say 714. Two guests can both hold "Room 1" and still land in different real rooms. And the desk refuses if you try a room that isn't yours.

The real thing

Programs use virtual addresses (VA). Hardware called the MMU (Memory Management Unit) sits between the CPU and memory and turns each VA into a physical address (PA). The operating system (OS) tells the MMU the rules.

MMU = a translator plus a security guard: it changes pretend addresses into real ones and blocks anything not allowed.

Level 4

Pages: translate in boxes, not one house at a time

The story

Writing down where every single house goes would take a gigantic notebook. So we group houses into blocks of 100. Address 523 means "block 5, house 23 inside it". We only remember where each block moved. The position inside the block never changes.

Toy 1 · split an address

The real thing

Memory is cut into pages, usually 4096 bytes (4KB). Because 4096 = 212, the lowest 12 bits of an address are the offset (position inside the page) and the rest is the page number. Only the page number gets translated.

Address = page number + offset. Translate the page number, keep the offset.

Level 5

The page table: the front desk's notebook

The story

The front desk keeps a notebook. Each line says: "pretend block 3 → real block 1, guests may read and write". Some lines have a sticker: "read only". Some lines are blank: "no such room".

Toy 2 · be the MMU (pages of 100)
Virtual page→ Physical pageAllowed

Try 345 read, 345 write, 120 write, 250 read, 999 read.

The real thing

The OS builds a page table in memory. Each line is a page table entry (PTE) holding the physical page plus permission bits (read, write, execute, user or kernel). The MMU reads it on its own; this reading is called a page table walk.

Page table = the rule book. One line per page: where it really lives and who may touch it.

Level 6

Levels: a notebook with an index

The story

With billions of pages, a flat notebook would be enormous and mostly blank. So we use a book with an index: the first page says "rooms 0–999 are in chapter A", chapter A says "rooms 300–399 are on page 12", page 12 has the actual line. If a whole chapter is empty, we don't even print it.

The real thing

Arm uses up to 4 levels (0–3) for a 48-bit address with 4KB pages. Each level is a 4KB table of 512 entries. An entry either points to the next table or says "this whole block maps here" (a 2MB or 1GB block, a shortcut that skips the remaining levels).

Multi-level tables save space; the price is several memory reads per translation.

Level 7

The TLB: sticky notes for answers you just looked up

The story

The desk clerk is tired of flipping through the index book. So she sticks a few notes on the desk: "page 3 → 1". Next time someone asks for page 3 she reads the sticky note instantly. The desk only has room for 4 notes, so the oldest-used note gets thrown away when a new one is needed.

Toy 3 · TLB with 4 sticky notes

Click page numbers to make the program touch that page. A hit is instant. A miss costs a 4-step walk and adds a note.

Touch a page to start.
The real thing

The TLB (Translation Lookaside Buffer) is a small, very fast cache of recent translations inside the MMU. Programs touch the same pages over and over, so most lookups hit. Real CPUs have small L1 TLBs and bigger L2 TLBs.

TLB = a cache of translations. Hit = fast; miss = walk the tables.

Level 8

Faults: when the desk says "no"

The story

Sometimes the notebook has no line for your room, or your card says "read only" and you try to write. The clerk does not guess. She stops you and calls the manager (the OS). The manager might fix the notebook (load the page) and let you try again, or throw you out.

Translation fault

No valid line. Common and often normal: the OS loads the page, then retries.

Permission fault

Line exists, but you lack the right: writing a read-only page, running code from a data page.

Access flag fault

Page is mapped but marked "not yet used", so the OS can track which pages are busy.

Address size fault

The address is bigger than the system supports.

A fault is the MMU refusing and asking the OS to decide. It is how protection is enforced.

Level 9

Name tags and cleaning up old notes

The story

The game and the browser both have a "page 3", going to different real pages. If the sticky notes don't say whose note it is, the browser could use the game's note. So each note gets a name tag. And when the manager changes the notebook ("page 3 moved"), she must tear off the old sticky notes, or the clerk will keep sending people to the old room.

ASID = the program's name tag

Each TLB entry carries an Address Space ID, so programs never use each other's entries. A VMID is the same idea for whole virtual machines.

TLB invalidation = tearing off notes

After changing a page table, software sends a TLBI ("forget page 3 for ASID 7"), then waits until it is finished. Forgetting this step is one of the most common real bugs.

Tag every cached answer with its owner, and throw away stale answers whenever the rules change.

Level 10

Two translators: virtual machines

The story

A hotel inside a hotel. A small hotel rents a whole floor of a big hotel. The small hotel's desk says "Room 1 → my room 20". But "my room 20" is itself pretend; the big hotel's desk turns it into real room 714. Two desks, one after another.

The real thing

Stage 1 (VA → IPA) is controlled by the guest OS. Stage 2 (IPA → PA) is controlled by the hypervisor, which keeps VMs apart. Even the guest's page tables live at IPA addresses, so every stage-1 step needs a stage-2 lookup too. A full cold lookup can take 24 memory reads.

Virtual machines add a second translation stage owned by the hypervisor.

Level 11

Devices need a guard too: the SMMU

The story

So far only guests at the front desk (CPU programs) got checked. But delivery trucks (the GPU, the network card, the SSD) drive straight onto the street to drop off and pick up boxes. Without a gate, one buggy or hacked truck could drive into any house. So we put a second guard on the truck road. Each truck shows a badge.

The real thing

Devices read and write memory directly (DMA, Direct Memory Access). The SMMU (System MMU, Arm's IOMMU) is an MMU for those devices. It uses the same page-table format as the CPU. Every device transaction carries a StreamID (which device, the badge) and optionally a SubstreamID (which job or process inside that device, also called PASID on PCIe).

SMMU = the MMU for devices. StreamID tells it who is asking.

Level 12

How the SMMU finds each device's rules

The story

The truck guard has a filing cabinet. Badge 7 → drawer 7 → a device card: "this truck belongs to VM 2, use these rules". If the truck runs several jobs, the card points to a stack of job cards, one per job number, each saying which notebook (page table) to use.

The real thing

STE = Stream Table Entry (64 bytes, one per device). It says whether to block, pass through, or translate, and points to stage-2 tables and the CD table. CD = Context Descriptor (64 bytes, one per process context). It holds the stage-1 page table pointer and ASID.

StreamID → STE → (SubstreamID) → CD → page tables → real address.

Level 13

Talking to the SMMU: mailboxes

The story

The manager and the guard don't phone each other for every small thing. The manager drops orders into an in-tray ("forget the note for page 3", "re-read device card 7"). The guard drops problem reports into an out-tray ("truck 12 tried a locked house"). Each tray is a ring: when you reach the end, you start again at the top.

Command queue (software → SMMU): orders like invalidate TLB, invalidate STE/CD, and CMD_SYNC, which means "tell me when everything before this is done".

Event queue (SMMU → software): fault reports such as "bad STE" or "translation fault for StreamID 12 at address X".

PRI queue (SMMU → software): PCIe devices asking "please bring this page into memory for me".

Each ring has a PROD pointer (where the writer puts the next item) and a CONS pointer (where the reader takes the next item). PROD = CONS means empty.

Software sends commands through a ring buffer; the SMMU reports problems through another.

Level 14

What a verification engineer does here

The story

Before the hotel opens, someone has to try to break it. They send fake guests with wrong keys, change rooms in the middle of check-in, fill the mailbox until it overflows, and check every single time that the clerk sent people to the right room. That person is the verification engineer. Their job is to find the bug before a customer does.

1. Predict

Write a reference model: a simple program that knows what the correct answer should be ("VA 345 for ASID 7 must go to PA 145").

2. Poke

Build stimulus: random and planned traffic from fake devices, random page tables, random commands.

3. Compare

A scoreboard checks the chip's real output against the prediction, every time.

4. Count

Coverage records which situations you have actually tried (every fault type, every page size, full queue…) so you know when you are done.

Starter test ideas (try to think of why each one could fail)
