I

Architecture

What the ISA promises

PL·01

The RV32I contract

The ISA is a contract between software and every implementation. Verification checks the implementation against this contract and nothing else, so you need to know exactly what it does and does not promise.

Extensions are separate contracts: M mul/div, A atomics, C 16-bit, F/D float, Zicsr, Zifencei. "RV32IMC" means base plus those. A verification plan starts by naming the exact ISA string.

Deep dive

  • Load/store architecture: only loads and stores touch memory, and every ALU op is register–register or register–immediate. That is what makes a single-cycle or 5-stage datapath simple.
  • x0 is not a register you can write. Writes are discarded and reads return 0. addi x0,x0,0 is the canonical NOP. A hardware bug that stores into x0 is invisible until something forwards from it.
  • No condition codes: branches compare two registers directly. There are no flags to rename in an OOO core, which removes a whole bug class.
  • No integer overflow trap: add wraps silently. Software detects overflow with slt/sltu.
  • Divide by zero does not trap (M extension): x/0 = −1, x%0 = x, and −2³¹/−1 = −2³¹. Tomasulo lab bug B06 returned +1.
  • Implementation-defined ≠ undefined: misaligned data access may be handled in hardware or trap. The DV plan must pick the policy the design implements, and the reference model must match it.

Spec rules & constraints

  • Instructions are 32-bit and 4-byte aligned (without C). A jump or taken branch to a non-aligned target raises instruction-address-misaligned.
  • Register read happens before write in one instruction: jalr x1,0(x1) uses the old x1.
  • HINT space: writes to x0 with other encodings are legal NOP-like hints. They must not trap.

Bugs that live here

  • B06 signed divide by zero returned +1 instead of −1.
  • B14 Booth multiplier overflowed on −2³¹ (the one value with no positive twin).
  • Classic: the regfile write port lets x0 be written, and forwarding then sends that value onward.

Interview

Q: Where do you start verifying a RISC-V core?

Pin the contract: ISA string, privilege modes, the misaligned and illegal-instruction policy, and the reset state. Then pick a golden model configured to that exact contract. Every later check derives from it.

PL·02

Formats and immediates

Six formats keep rs1, rs2 and rd in the same bit positions so decode can read registers before it knows the format. Immediates pay the price: their bits are scrambled to keep the sign bit at inst[31].

Deep dive

  • B and J offsets are in units of 2 bytes: bit 0 is implicit 0. That gives ±4 KiB for branches and ±1 MiB for JAL. With C absent, bit 1 must also be 0 at the target, or the jump traps.
  • Why scramble? Each immediate bit sits in as few positions as possible across formats, so the mux tree in decode stays small. Sign extension always comes from inst[31], so it can start before the format is known.
  • funct7 matters only for 3 cases: ADD/SUB and SRL/SRA (bit 30), and SRLI/SRAI (imm[10], also inst[30]). Every other funct7 in OP is reserved, so it should decode as illegal, not as an alias.
  • A decoder keyed on partial fields aliases. YARP keyed I-type control on {opcode[4], funct3}. JALR (1100111, f3=000) collided with LB (0000011, f3=000). That is bug Y3.
  • Stimulus encodes the same layout. A generator that packs B-type bits wrong produces legal-looking but different branches. Cross-check your encoder against an assembler or ISS once.

Spec rules & constraints

  • Illegal: opcode not in the table, a reserved funct3/funct7 combination, or the all-zero instruction 0x00000000 (defined illegal so zeroed memory traps).
  • SLLI/SRLI/SRAI on RV32: imm[5] = 1 is reserved.
  • JALR requires funct3 = 000. Other values are reserved.

Bugs that live here

  • Y3 JALR aliased LB in a {opcode[4],funct3} key, so every JALR issued a phantom data read.
  • B01 Tomasulo decode let immediate bits leak into the opcode key: valid instructions decoded as OTHER, then deadlock.
  • B02 I-type immediates were zero-extended: addi x1,x0,-1 gave 0x00000FFF.

Interview

Q: How do you verify a decoder?

Exhaustively. 2³² is too many, but opcode×funct3×funct7 plus immediate boundary values is small. Compare every control field against a table derived from the spec, and make sure reserved encodings decode to illegal. Formal equivalence against a spec-written decoder closes it.

PL·03

Semantics corners: signed, unsigned, shifts, jumps

Most ALU bugs are not wrong operators. They are wrong interpretations of the same 32 bits. SystemVerilog makes this worse: logic is unsigned unless you say otherwise.

slt / slti / blt / bgesigneda=−1 (0xFFFFFFFF), b=1 → 1   (unsigned says 0)

sltiuimm is sign-extended, then compared unsignedsltiu rd,rs,−1 → 1 unless rs=0xFFFFFFFF
sltiu rd,rs,1idiom= seqz (rd = rs==0)
sll / srl / srashamt = rs2[4:0]rs2=33 shifts by 1; sra keeps the sign
lui / auipcimm<<12, auipc adds pcauipc uses its own pc, not pc+4

Deep dive

  • Three compare semantics, four bug shapes: signed-as-unsigned, unsigned-as-signed, magnitude (abs), and wrong operand order. Each one agrees with the correct answer on half the input space or more.
  • In SystemVerilog: a < b on logic [31:0] is unsigned. Signed needs $signed(a) < $signed(b), and one unsigned operand makes the whole expression unsigned. Bug Y2 is exactly this.
  • Shifts: only the low 5 bits of the amount count. SRA must replicate bit 31 ($signed(a) >>> sh). >>> on an unsigned operand is a logical shift.
  • JALR clears bit 0 only. Bit 1 left at 1 makes a misaligned target, which must trap when C is absent. A design without traps (YARP) must document what it does instead, and the model must follow.
  • rd = rs1 on JALR: the target uses the old rs1, and the link value goes to rd. An implementation that writes rd first jumps to pc+4+imm.

Spec rules & constraints

  • Writes to x0 by any of these instructions are discarded, including the jal/jalr link.
  • No instruction sets flags. Overflow is silent wrap.
  • SUB is funct7 = 0100000. Any other non-zero funct7 on OP is reserved.

Bugs that live here

  • Y1 SLT compared |a| < |b|. Caught 9/9 only after compare-corner coverage plus a targeted test.
  • Y2 BLT/BGE used unsigned compares, and BLTU/BGEU used magnitudes. The original testbench never caught it (0/10).
  • P5 SUB decoded as ADD. Missed entirely by a stimulus that was 70% JAL/LUI.

Interview

Q: Name a test that exposes a signed/unsigned bug.

Operands with different signs, and both negative, on every compare form: slt, slti, sltu, sltiu, and all six branches. Make it a coverage cross (instruction × operand-sign class), not a hand test, so you can prove it was hit.

PL·04

Loads, stores, sizes and alignment

A load is address, size, sign rule and byte placement. Each of the four is a separate place to be wrong, and the memory interface contract decides which side of the boundary each one lives on.

Deep dive

  • Sign rule depends on the instruction, not the data: LB/LH extend bit 7/15, while LBU/LHU zero-extend. A bug only shows when the loaded byte has its top bit set. Random memory full of zeros never shows it (mutant P6).
  • Misaligned (lw at 0x101, lh at 0x103): allowed to work, trap, or be emulated by the execution environment. Pick one. The YARP lab uses byte-wise access in RTL, TB memory and the C model. The original testbench $fatal-ed on it, which gave 40% false failures.
  • Store data: SB/SH write only the low byte/half of rs2. Memory must not touch the other lanes (read-modify-write or byte strobes).
  • Load-after-store is the real check: a store that never lands is invisible until a later load reads the same bytes. Constrain addresses into a small window so that happens often.
  • A load to x0 still performs the access (it matters for I/O side effects), but the result is discarded.

Spec rules & constraints

  • Little-endian byte order is mandated for the base ISA.
  • Alignment policy is implementation-defined. The reference model must be configured to the same policy as the RTL.
  • The load address is rs1 + sign-extended imm, computed modulo 2³².

Bugs that live here

  • B10 Tomasulo lbu/lhu read whole words and sign-extended.
  • D2 YARP TB driver gated store writes on a stale clocking-block sample, so stores never reached memory. Loads read 0 and the C model disagreed.
  • M1 TB memory model $fatal on misaligned addresses, although the spec says handle them.

Interview

Q: Your loads pass. Why might stores still be broken?

Loads only prove stores if they read back what was stored. Random addresses make that rare. Check the store stream directly (address/size/data vs the model at the interface) and bias load addresses onto recently stored bytes.

PL·05

Traps, CSRs and precise exceptions

The base ISA leaves exceptions to the privileged spec, and that is where senior interviews go. A trap has to look as if every older instruction finished and no younger one started.

mcauseException (intr=0)mcauseInterrupt (intr=1)
0instr addr misaligned3machine software
2illegal instruction7machine timer
3breakpoint (ebreak)11machine external
4 / 6load / store misaligned
5 / 7load / store access fault
11ecall from M

Deep dive

  • Synchronous vs asynchronous: an exception belongs to one instruction and is deterministic, so an ISS can predict it. An interrupt arrives between instructions at a time the design chooses. The ISS cannot predict it and must be told: "DUT took interrupt X before instruction N".
  • mepc points at the faulting instruction for exceptions (ecall included: software adds 4) and at the next unexecuted instruction for interrupts.
  • Priority when several apply: the spec orders exceptions (e.g. instruction-address faults before illegal instruction) and interrupts (MEI > MSI > MTI). These are corners worth a cross.
  • CSR side effects: reading mcycle/minstret is non-deterministic against a model. Mask, or let the model take the DUT value. CSR writes with WARL fields need the model to apply the same legalization.
  • Common OOO trap bugs: a younger store already sitting in the store queue gets drained after the trap; a younger load updated the RAT; mepc taken from the fetch PC instead of the faulting PC.

Spec rules & constraints

  • Traps are precise in the base privileged spec.
  • MIE clears on trap entry and is restored from MPIE on mret.
  • Writes to read-only CSRs are illegal-instruction exceptions. WARL fields legalize silently.

Bugs that live here

  • YARP has no trap support. An illegal opcode silently acts as a NOP, so the model must mirror that policy or every illegal instruction mismatches.
  • Interrupt taken in the same cycle as a branch mispredict: mepc points into the wrong path.
  • Store committed to memory after an older load faulted (imprecise).

Interview

Q: How do you check interrupts against an ISS?

The DUT decides when. The TB observes the retirement point where the trap was taken and injects the same interrupt into the ISS at that instruction boundary, then compares everything else as usual. Separately, check the decision is legal: enabled, pending, priority, latency bound, with SVA plus coverage.

PL·06

Single-cycle datapath (YARP)

Every instruction does fetch, decode, read, execute, memory and write-back in one clock. The datapath is a set of muxes, and the control unit's only job is to set them.

Classop1op2ALUwbpcmem
Rrs1rs2functALU+4–

Branchpcimmadd–taken ? alu : +4–
JAL / JALRpc / rs1immaddpc+4alu & ~1–
LUI / AUIPC– / pcimm– / addIMM / ALU+4–

Deep dive

  • The branch unit compares rs1/rs2 while the ALU computes pc+imm. Two units run in parallel. In YARP the compare is a separate module, and that is where Y2 lived.
  • The clock period is the longest path: imem → decode → regfile read → ALU → dmem → wb mux → regfile setup. That is why single-cycle CPUs are slow. The pipeline (PL-11) cuts this path into stages.
  • Combinational memory read: single-cycle assumes rd_data arrives in the same cycle as the address. Real memories are synchronous. That forces either a pipeline or a valid/ready stall FSM (PL-08).
  • White-box points for DV: the regfile write port (wr_en, rd, data) gives one retire event per cycle. It is the natural compare point for a commit scoreboard.

Spec rules & constraints

  • Exactly one instruction retires per accepted fetch. No retire without a fetch handshake.
  • Register writes and the PC update happen on the same edge: the retire edge.
  • Loads write the register only once the data is valid.

Bugs that live here

  • Y4 The first cycle after reset froze the PC but still wrote the regfile, so the first instruction executed twice.
  • P4 Retiring a load before data_mem_ready advanced the PC early. It shows up as a PC mismatch.

Interview

Q: What is the critical path of a single-cycle RISC-V?

A load: PC → imem → decode/regfile read → address add → dmem read → extend → wb mux → regfile setup. Pipelining cuts it at the four boundaries between those blocks.

PL·07

Control decode and encoding collisions

The control unit maps opcode/funct to a bundle of mux selects. Bugs come from default values, overrides that clear too little, and keys built from too few bits.

Deep dive

  • Start from all-zero (no side effects) and turn on only what each instruction needs. A side-effect signal (data_req, rf_wr_en, pc_sel) that defaults on is a phantom write waiting to happen.
  • An override must restate every side-effect field. A partial override inherits whatever the earlier case left. That is how Y3 happened.
  • A default: that executes ADD hides illegal encodings. The core silently runs garbage, and only a model with the same quirk agrees.
  • Phantom requests are invisible to register checks. The register result was correct, so only an interface check (scoreboard comparing every data access, or SVA "data_req only for load/store") catches them.
  • Decode is ideal for formal: write the spec table as SVA (opcode==JALR |-> !data_req) and prove it for all encodings.

Spec rules & constraints

  • data_req is asserted iff the opcode is LOAD or STORE.
  • rf_wr_en is never asserted for STORE or BRANCH.
  • Reserved funct3/funct7 values decode to illegal.

Bugs that live here

  • Y3 JALR phantom load. Caught 9/9 by the data-access compare in the fixed TB.
  • B01 Opcode key polluted by immediate bits, so instructions decoded as OTHER and the core deadlocked.
  • B03 ALU silently dropped OP-IMM: the instruction never completed.

Interview

Q: The register results all match the ISS. What can still be wrong in decode?

Side effects that do not reach registers: phantom memory reads, writes to x0 that forward, illegal encodings that execute instead of trapping, and CSR or fence side effects. Check the interfaces as well as the architectural state.

PL·08

Valid/ready memory handshake

Real memories answer late. The core raises req, holds the payload stable, and the transfer happens only on the edge where req and ready are both high. YARP's spec turns this into ten rules, and each rule is one assertion.

RuleSpec text, compressedSVA
R1 R2i_req held, i_addr stable until i_readyi_req&&!i_rdy |=> i_req && $stable(addr)
R3d_req starts in the instr-accept cycled_req && !$past(d_wait) |-> i_hs
R4–R7d_req and payload stable until d_readyd_wait |=> d_req && $stable({a,be,wr,wd})
R8 R9back-to-back legal; ready may toggle alonecover, never assert
R10no fetch while data pendingd_wait |=> !i_req

Deep dive

  • Pending FSM: on an instruction handshake for a load/store, if d_ready is not already high, latch the instruction (the memory stops driving it next cycle), drop i_req, and hold the data payload from the latch. Retire on the data handshake.
  • Ready without a request is legal (R9). A responder that holds ready high gets 1-cycle transfers. A responder that waits to see req first costs a cycle every time.
  • The instruction bits disappear after the handshake. Forgetting to latch them (mutant P1) makes the data payload change mid-transfer. SVA R4/R5 catch it immediately; without SVA it shows up as a hang.
  • A rule with no data effect needs an assertion: fetching during a pending load (mutant P2) corrupts nothing visible in this TB. The scoreboard passed 6/6, and only SVA R10 caught it.
  • Cover the legal corners too: stall→handshake, back-to-back handshakes, ready held with no request. Otherwise the assertions may be vacuously true.

Spec rules & constraints

  • The payload is only meaningful while req is high.
  • No combinational path from ready to req (protocol deadlock rule of thumb).
  • The reserved size code 2'b10 is never driven.

Bugs that live here

  • RTL The uploaded YARP had no ready ports at all. Random ready tripped R2 on the first stall.
  • P1 No instruction latch: caught by SVA R4. The original TB hung on 10/10 seeds.
  • P2 Fetch while pending: caught only by SVA R10.
  • P3 PC ignores ready: SVA R2 at the first stall.

Interview

Q: Why put protocol assertions in the interface, not the scoreboard?

Every test and every environment that instantiates the interface gets them, they fire at the exact cycle (not at the next compare point), and they check rules that have no data effect. The scoreboard checks results; assertions check behaviour.

PL·09

Reset, first cycle and X-propagation

Reset bugs live in the cycles nobody tests: the edge reset releases, the first fetch, and state that was never reset. Make the testbench hostile in those cycles.

Deep dive

  • Gate every architectural side effect with the same condition that gates the PC. YARP froze the PC with reset_seen_q but let the regfile and data request run (Y4).
  • Polite testbench models hide bugs. Memory that returns 0 when not requested makes the extra cycle harmless. Hostile models return real data whenever the spec allows, including with no request and with random ready.
  • Unreset state: the YARP regfile has no reset (legal: x1–x31 are UNSPECIFIED at reset). The model must start from the same values, or the TB must initialise registers by program before comparing.
  • X-propagation: an X on ready or rd_data right after reset (driver bug D1) can be optimistic in RTL sim (if/case treat X as false) and pessimistic in gate sim. Drive every responder output in the reset sequence.
  • Reset in the middle: assert reset during a pending load. Every FSM must return to idle, and no write may happen on the reset edge.

Spec rules & constraints

  • PC = reset vector at the first fetch. The vector is implementation-defined (YARP: parameter RESET_PC, 0x1000 by default).
  • Only pc and mstatus-type CSRs have mandated reset values. GPRs are unspecified.
  • No architectural write may occur before the first instruction is accepted.

Bugs that live here

  • Y4 First instruction executed twice. Found with an always-answering imem.
  • D1 TB drove only reset_n, leaving ready/rd_data at X after reset.

Interview

Q: How do you verify reset?

Reset at time 0 and mid-traffic (pending load, stall, branch in flight); check that every state element returns to its spec value; check that no side effect happens on the reset edge or in the first cycle; check that the first fetch is the reset vector. Run both X-pessimistic and hostile-memory variants.

Pipelines, out-of-order, memory

PL·10

The performance equation

Time = instructions × CPI × clock period. Every microarchitecture idea attacks one factor and usually hurts another. Performance verification checks that the cycle count matches the model, not just the answers.

pq5 programNstallsflushes4+N+s+2fmeasuredCPI
p01_alu230027271.17
p02_forwarding140018181.29
Formula checked against every pq5 run: cycles = 4 + N + load-use stalls + 2 × flushes (pipeline fill = 4, mispredict penalty = 2 because branches resolve in EX). Removing branch prediction failed no functional test but raised CPI to 1.66 on a loop. Only a cycle check catches that.

Deep dive

  • Single-cycle: CPI = 1, T = the whole datapath. 5-stage: CPI ≈ 1 + stall rate, T ≈ ⅕. OOO superscalar: CPI < 1, with T bounded by wakeup/select and bypass loops.
  • Amdahl: speedup = 1 / ((1−f) + f/s). Halving the latency of an op used 10% of the time buys at most 5%.
  • Performance bugs are silent. A predictor that never predicts, a BTB that evicts the wrong way (B15) or a stall that is one cycle too long all pass every functional test.
  • How to verify performance: a cycle-approximate model or analytic formula per microbenchmark, assertions on bounded latencies (e.g. "a load-use stall lasts exactly 1 cycle"), and trend checks of CPI per test in regression.

Spec rules & constraints

  • The ISA says nothing about timing: performance is a design spec, so write it down (latencies, penalties, throughput).
  • Measure CPI with the same retire event the scoreboard uses.

Bugs that live here

  • B15 BTB replacement evicted the most recent entry and never used a free way. Found by unit test, invisible functionally.
  • pq5 mutant "no branch prediction": 0/10 directed and 0/100 random fail, yet p04_loop_sum CPI rose to 1.66 (p09_multiply 1.48).

Interview

Q: All tests pass. How would you find a performance bug?

Compare cycle counts to an expected model per directed microbenchmark (loop, pointer chase, branchy code), assert latency bounds with SVA, and track CPI per test across regressions so a jump flags a change.

PL·11

The 5-stage pipeline

Cut the single-cycle path into IF, ID, EX, MEM and WB with registers between them. Five instructions are in flight, and correctness now depends on the timing between them.

instr \ cycle123456789
i1 add x5,…IFIDEXMEMWB
i2 sub …,x5IFIDEX ◀ fwdMEMWB
i3 lw x6,0(x5)IFIDEXMEMWB
i4 add …,x6IFIDstallEX ◀ fwdMEMWB
i5 beq takenIFIFIDEX ✱MEM

Deep dive

  • Every stage register carries a valid bit. valid=0 is a bubble. A flush clears valid; a stall holds the register and injects valid=0 downstream. Forgetting to clear valid in one register is the classic flush bug: pq5 failed 98/100 random tests when either IF/ID or ID was left unflushed.
  • Fill latency: with no hazards N instructions take Δ + N − 1 = N + 4 cycles (Δ = 5 stages).
  • Structural hazards are removed by design: separate instruction and data memory, a 2-read/1-write regfile, and the PC adder separate from the ALU.
  • WAR and WAW cannot happen in an in-order pipeline where the write always happens in the last stage. RAW is the only data hazard (PL-12).
  • Stall vs flush in the same cycle: flush must win (the stalled instruction is on the wrong path). pq5 also proves that it cannot happen, with assertion a_noflushstall.

Spec rules & constraints

  • Commit order = program order, one retire per cycle at most.
  • A flushed instruction must have no architectural effect: no rf write, no store, no CSR change.

Bugs that live here

  • pq5 mutant: flush forgets IF/ID → 6/10 directed, 98/100 random fail.
  • pq5 mutant: x0 writable → 54/100 random fail (it shows up when a later instruction forwards x0).
  • B09 Tomasulo frontend ignored back-pressure and replayed stale bundles: the commit stream was no longer the program.

Interview

Q: What does the scoreboard compare for a pipelined core?

The same thing as for a single-cycle one: the retire stream (pc, instr, rd, wdata, mem ops) in order against the ISS. Pipelining changes when instructions retire, not what they do, so the checker sits at retire and ignores timing.

PL·12

Data hazards: forwarding and the load-use stall

A result exists before it is written back. Forwarding passes it backwards to the instruction that needs it; the one thing it cannot do is go backwards in time, which costs a load-use bubble.

pq5: remove one mechanismdirected failrandom fail
no forward from MEM (dist 1)9/10100/100

Deep dive

  • Forward condition per operand: valid && wr_en && rd != 0 && rd == rs. Every term is a bug if missing: invalid (flushed) producer, a store or branch (no write), x0, wrong register.
  • Priority: if two older instructions write the same register, the nearer one is newer. Reversing the priority fails only 5/100 random programs, so it needs a directed "write x5 three times then read" test or a coverage cross on (distance × same-rd).
  • Load-use: the loaded value exists at the end of MEM; the next instruction needs it at the start of EX. One bubble, detected in ID: EX.is_load && EX.rd != 0 && EX.rd ∈ {ID.rs1, ID.rs2}.
  • Redundant guards can be proven: pq5's "don't forward a load's address from MEM" guard is unreachable because the interlock already stalls. The assertion a_loaduse proves it.
  • Store data is an operand too: rs2 of a store needs forwarding exactly like an ALU operand, and so does the branch compare in EX.

Spec rules & constraints

  • Read-after-write must observe the latest older write in program order.
  • The x0 source always reads 0, regardless of any in-flight write to x0.

Bugs that live here

  • Forwarding priority reversed: passes 95% of random tests.
  • Forwarding from a flushed (valid=0) instruction: a wrong-path value leaks into the right path.
  • Store data (rs2) not forwarded: the store writes a stale value; only a later load sees it.

Interview

Q: How do you make sure forwarding is fully covered?

Cross producer type (ALU, load, jal link) × distance (1, 2, 3, 4+) × consumer operand (rs1, rs2, store data, branch) × same-rd collisions. Random programs with a small register pool (e.g. only x1–x6) hit it fast. Close the holes with directed sequences.

PL·13

Control hazards and branch prediction

Fetch has to guess the next PC before the branch is decoded. Correctness requires only that a wrong guess be squashed completely; performance is how rarely you guess wrong.

Deep dive

  • Penalty = depth of resolution. Resolving in EX costs 2 (pq5); resolving in ID costs 1 but needs a comparator plus forwarding into ID. Deep OOO cores pay 10–20 cycles, which is why predictors are large.
  • Recovery must undo speculative state: in-order cores clear valid bits; OOO cores also restore the rename map (checkpoint or ROB walk), free physical registers, kill younger LSQ entries and repair the global history.
  • Predictor bugs are mostly performance bugs, unless the predictor can produce a target that is never checked (e.g. a non-branch predicted taken, with no check in EX).
  • DV for prediction: functional (every mispredict flushes completely), then performance (accuracy on known patterns: loops, alternating, correlated), then unit tests of replacement, aliasing and counter saturation.

Spec rules & constraints

  • Prediction is invisible to the ISA: wrong-path instructions must never retire or change memory.
  • A taken branch/jump to a misaligned target traps on the branch itself (no C).

Bugs that live here

  • B15 BTB PLRU evicted the newest entry and ignored a free way.
  • Mispredict in the same cycle as an older load-use stall: the stall holds the wrong-path instruction.
  • RAS not repaired after a mispredicted call: every later return mispredicts (performance only).

Interview

Q: How do you verify that a mispredict leaves no trace?

Directed: branch to code that would store or write registers on the wrong path, then check memory and the regfile. Random: lockstep ISS at retire, plus an SVA that nothing retires with a flushed ID, plus coverage of mispredict × wrong-path instruction type (store, load, CSR, branch).

PL·14

Out-of-order core: rename, issue, commit

Issue instructions when their operands are ready, not in program order, then retire in program order so software never notices. The ROB is the bridge between the two orders.

Deep dive

  • Renaming removes WAR and WAW: each destination gets a fresh tag (ROB entry or physical register). Only true RAW dependences remain.
  • Wakeup/select is the critical loop: the CDB tag compares against every RS source, and back-to-back dependent issue needs wakeup and select in one cycle. Tag width and CDB count bound IPC.
  • Tag 0 is a real tag. Using 0 as "no tag" while also allocating ROB entry 0 means one entry can never be woken. Tomasulo lab bug B04: a deadlock that only shows when entry 0 is used for a long-latency op.
  • Free-list consistency: two structures tracking the same resource (a dispatch free-list vs busy bits) will drift. Lab bug B12 failed 79 of 120 random seeds before the fix.
  • Commit is where correctness is defined: the scoreboard compares the commit stream, exceptions and interrupts are taken at the head, and stores leave the core only after commit.
  • Mispredict recovery: squash everything younger than the branch in ROB, RS and LSQ; restore the RAT (checkpoint at the branch, or walk the ROB); free the tags.

Spec rules & constraints

  • Retire order = program order; retired state is always a precise architectural state.
  • No younger instruction may make a visible change before an older one retires (stores, CSRs, I/O loads).

Bugs that live here

  • B04 ROB tag 0 could never be woken: deadlock.
  • B05 A second DIV overwrote the first in the divider: deadlock and lost result.
  • B11 MMU consumed one load-buffer entry twice. Caught by SVA A7 on the program that "passed".
  • B12 Dispatch free-list disagreed with busy bits: 79/120 random seeds failed.

Interview

Q: What do you check in an OOO core beyond the commit stream?

Liveness (every allocated ROB entry eventually retires: watchdog plus SVA), resource conservation (free + used = total for ROB, RS, physical registers, LSQ, every cycle), uniqueness (no tag in two places), and no wakeup for a tag that is not in flight. Those are what found B04, B05, B11 and B12.

PL·15

Load/store queue and memory disambiguation

Registers are renamed but memory is not. A load that runs ahead of an older store to the same address reads stale data, unless the LSQ catches it.

Deep dive

  • Senior stores: a committed store still in the queue is architecturally done but not yet in memory. Loads must still see it, flushes must not kill it, and a reset or flush that drops it loses data (lab B13, distilled into b19_senior_store).
  • Byte-level overlap: compare address and size. sb 0x101 then lw 0x100 overlaps one byte. Comparing word addresses only forwards the whole word: wrong.
  • Ordering inside the LSQ: the youngest older store wins. Multiple loads to one address must each complete (lab B08: the third load was marked done and never broadcast).
  • Memory consistency: single-core needs program-order semantics for one hart. Multi-core RVWMO allows more reordering, but FENCE must restore order, and atomics (A ext) need LR/SC reservation rules.
  • DV stimulus: small address pools (8–16 lines), mixed sizes and offsets, stores with late addresses (dependent on a slow divide), and many loads in flight. That is how B07 and B13 were found by random before directed tests existed.

Spec rules & constraints

  • A load returns the value of the youngest older store to each byte, else memory.
  • Stores are not visible outside the core until commit.
  • FENCE orders memory operations as specified (predecessor/successor sets).

Bugs that live here

  • B07 Loads ignored older stores (no disambiguation): wrong data on aliasing.
  • B08 The third load to one address never broadcast: deadlock.
  • B13 Store-queue ordering: deadlocks, orphaned and bypassed stores.

Interview

Q: How would you stress an LSQ?

Constrain addresses to a few lines so aliasing is common, mix byte/half/word at all offsets, make store addresses depend on long-latency ops so loads run ahead, and fill the queues (back-pressure). Check with the ISS at commit, plus SVA that the store queue drains in order and nothing is lost on a flush.

PL·16

Memory hierarchy: caches, coherence, translation

Caches and TLBs must be invisible to the ISA except for timing. Verifying them is mostly about proving that invisibility under replacement, races and multiple masters.

Deep dive

  • Write-back + write-allocate is the usual L1D. A dirty line must be written back before eviction, and an eviction racing a read of the same line is a classic corner.
  • Replacement: LRU, PLRU or random never change results, only timing. A broken replacement policy is a performance bug, unless it evicts a line with a pending fill.
  • Coherence verification = invariants plus a golden memory: single-writer/multiple-reader per line, data value = last write in a global order, no lost writebacks. Use formal on the protocol tables and random with heavy line sharing.
  • Virtual memory (Sv32): 2-level page walk, PTE V/R/W/X/U/A/D bits, page faults (cause 12/13/15). TLB bugs: stale entries after sfence.vma, a missed A/D update, wrong permission on superpages.
  • Self-modifying code: instruction fetch may be stale after a store until fence.i (Zifencei). The ISS and the DUT must agree on when the new code becomes visible.

Spec rules & constraints

  • Without fences, a single hart still sees its own stores in program order.
  • Caches are architecturally invisible: a timing difference only.
  • fence.i synchronises the instruction and data streams of one hart.

Bugs that live here

  • Eviction of a dirty line racing a new miss to the same set: the writeback uses the new tag.
  • A snoop hit on a line in transit (fill pending): a stale S state.
  • sfence.vma doesn't flush the global entries the spec requires: stale translation.

Interview

Q: How do you verify a cache you can't see from the ISA?

Reference memory model at the cache boundary (every load returns the latest write), invariants as SVA (one owner, dirty implies valid, no hit on two ways), stimulus that forces conflict misses (addresses mapping to one set) and back-to-back evict/refill, and coverage of every state-transition × request type.

Deep dive

  • Start from risk, not from tests: list features × failure modes (wrong value, hang, wrong order, lost update, performance) and assign a checker and a stimulus to each cell. That table is the verification plan.
  • Checker before stimulus: a perfect stimulus with a weak checker finds nothing. The YARP course TB passed with a broken store path because nothing compared stores directly.
  • Open-source anchors worth naming: riscv-dv (SV/UVM random instruction generator), riscv-arch-test (compliance), Spike / Sail (golden models; Sail is the formal spec), riscv-formal with RVFI (formal ISA checks via a standard retire port).

  • Every waiver of a coverage hole has a written reason and an owner.

  • Performance blind spot: pq5 "no prediction" passed every functional test.

Interview

Q: You join a CPU team mid-project. What do you look at first?

The verification plan's feature × check × coverage map and where it is thin; the bug database trend per unit (where bugs still arrive); whether the golden-model compare covers everything that retires (CSRs, traps, memory); and whether anything checks liveness and performance.

PL·18

Golden model and the commit scoreboard

Step a reference ISS once per retired instruction and compare everything that instruction changed. Small, fast and exact: this is the backbone of every CPU testbench.

Deep dive

  • Lockstep vs end-of-test: comparing only final registers misses overwritten errors and gives no location. Comparing per retire pinpoints the first divergence. That is the instruction you debug.
  • Compare deltas, not the world: comparing all 32 registers every retire (the course TB) is simple and slow. Comparing the one written register plus a periodic full check is how large cores do it.
  • Model the same policy as the RTL: reset PC, alignment, illegal-instruction behaviour, unreset registers. In the lab a C++ model was written to the YARP policy and cross-checked against a Python ISS on 213/213 programs before it was trusted.
  • Non-determinism: interrupts, mcycle/time, memory-mapped I/O and LR/SC success can't be predicted. The ISS follows the DUT for those (inject the interrupt, copy the read value), and separate checks judge whether the DUT's choice was legal.
  • Memory compare is a separate stream: a correct register result with a phantom access (Y3) or a missing store (D2) passes the register compare.

Spec rules & constraints

  • One retire event ⇒ exactly one step(). Never step speculatively.
  • Compare PC first. A PC mismatch makes every later compare noise.
  • Fail on the first mismatch with expected vs actual and the instruction.

Bugs that live here

  • S2 Course scoreboard read RTL regs from a thread woken by @cb: a race with the regfile NBA. Fixed by sampling at negedge.
  • S3 No count check: a hung core or a dropped handshake passed.
  • A1 End of test 32 cycles after the generator, not the driver: the last load was still pending, so a false mismatch (or the last instruction went unchecked).

Interview

Q: Your ISS and RTL disagree. How do you decide who is wrong?

Go to the spec text for that instruction and corner, then a second model (Sail or Spike vs your ISS), then the RTL. Model bugs are real: cross-check the model independently before trusting it, as the lab did on 213 programs.

PL·19

Class-based testbench anatomy

Generator → driver → DUT → monitor → scoreboard, joined by mailboxes and one virtual interface. Every component has one job, so a test can change stimulus without touching any of them.

Deep dive

  • Blueprint pattern: the generator constructs one transaction in new() and calls randomize() + copy() in run(). A test swaps the blueprint for a subclass with extra constraints. This is the pre-UVM version of a factory override.
  • copy() before put(): putting the blueprint itself means every mailbox entry is the same object, and the driver sees the last randomization N times. The copy must copy every field (bug T3).
  • Reactive driver: for a CPU, the TB is the memory. The driver waits for a request, waits the transaction's delay, then drives ready and data. Stimulus = instruction + delays.
  • Monitor samples every cycle; the handshake is decoded in the scoreboard. The monitor must never block (unbounded mailbox) or it skips cycles.
  • End of test is a protocol: the generator done → the driver done (count) → drain cycles → scoreboard completeness check (retired == num_tr, nothing pending) → a watchdog for hangs.

Spec rules & constraints

  • Components talk only through mailboxes and the interface, never by hierarchical references into each other.
  • Construction in new(), activity in run(): that ordering is what makes overrides possible.

Bugs that live here

  • C2 agent.sv included before monitor.sv: type used before declaration.
  • C3 scoreboard run() was a function calling mailbox.get(), a blocking task.
  • A1 drain counted from the generator, not the driver.
  • W1 no watchdog: a hung core ran forever (10/10 seeds on mutant P1).

Interview

Q: How does this map to UVM?

Transaction = sequence_item; generator + blueprint = sequence + factory override; mailbox = TLM port/fifo; driver/monitor/agent the same; scoreboard = subscriber; end-of-test drain = objections + drain time; watchdog = global timeout.

PL·20

Constrained-random instruction generation

A solver picks uniformly among all solutions, not among the opcodes you had in mind. Instruction streams need the opcode chosen first, legal control flow, and a deliberate register and address strategy.

Deep dive

  • Uniform over solutions is the LRM rule. solve opcode before funct3, … makes the opcode uniform first; dist adds weights. Verilator ignored both here, so the portable fix was a weighted randcase in pre_randomize plus rand_mode(0).
  • Legal control flow: B/J immediates keep bit 1 clear, JALR jumps to an aligned absolute target (rs1 = x0). Otherwise the PC wanders into unaligned or unmapped space.
  • Alignment constraints on imm are useless when the base register is random: rs1 + imm is what must be aligned. Either constrain the base (x0 window), or make the model and memory handle misalignment.
  • Register pool: draw from a small pool (x1–x6) so dependences and forwarding happen; reserve registers for addresses and loop counters in streams.
  • Constraint override by name: a subclass constraint with the same name replaces the base one (used for the b2b and stall delay profiles); different names AND together.
  • Instruction streams (riscv-dv): build sequences with intent (loops, call/return, load/store patterns), not just independent instructions.

Spec rules & constraints

  • Never generate an encoding the plan has not decided how to check (illegal, reserved, misaligned): either constrain it out or model it.
  • Measure the mix every run. A histogram is a one-line check.

Bugs that live here

  • T1 opcode skew: R/branch/memory almost untested while every run passed.
  • T2 2-aligned branch targets: undefined territory for a core without C.
  • T3 copy() skipped the instruction fields.

Interview

Q: Your random test passes 1000 seeds. Are you done?

Only if coverage says the seeds did something. Print the opcode histogram and the corner bins. Here 1000 passing seeds were 70% JAL/LUI, with almost no memory traffic and zero SUBs.

PL·21

Clocking blocks, sampling and races

Three of the worst testbench bugs in the lab came from when a value is read, not what is read. Know the scheduler well enough to say which value you get.

Deep dive

  • Inputs are sampled in the Preponed region (#1step): the value the design had just before the edge. That is race-free and correct for monitors, and a trap if you expect to see what you just drove.
  • Outputs are applied in Re-NBA (with output skew): after the design's NBAs for that edge. Two drives in the same step: the last one wins, and "last" depends on thread order.
  • Class threads woken by @cb run in the Reactive/Active part of the step. Hierarchical peeks at design flops can see old or new values depending on the simulator. Sample at negedge, or tap the write port (wr_en, rd, data) so the value is the event.
  • A responder sees req one edge late. A clocked driver that waits to see req before raising ready costs a cycle per transfer; holding ready high in advance is legal and gives back-to-back transfers.
  • Direction discipline: one clocking block per role (drv_cb with outputs, mon_cb all inputs) plus modports. An all-inout block (the original interface) lets a monitor drive the bus with no complaint.

Spec rules & constraints

  • Drive each signal from exactly one place per clock edge.
  • Monitors use clocking-block inputs only; never sample with a bare @(posedge clk) in a class.

Bugs that live here

  • D2 stale sampled ready: stores never reached the TB memory model.
  • D3 fork/join_none deassert raced the next assert.
  • S2 regfile read from @cb thread: scheduler-dependent.
  • D1 ready/rd_data left X after reset.

Interview

Q: What does #1step mean in a clocking block?

Sample in the Preponed region of the clock's time step, i.e. the last value before any update caused by that edge. It removes the race between the design changing a signal on the edge and the testbench reading it.

PL·22

Assertions: protocol rules and microarchitecture invariants

An assertion checks behaviour at the cycle it happens, for every test that binds it. It is the only checker for bugs that never produce a wrong value.

Deep dive

  • Where to put them: protocol SVA in the interface (every env gets them), microarchitecture invariants bound to the RTL with bind (designers can own them), and ISA-level properties in formal (riscv-formal style).

  • disable iff (!reset_n) on everything, or every reset becomes a failure.
  • Assertions find bugs earlier in time: P1 (no instruction latch) was a 10/10 hang in the original TB. With SVA it failed on the exact cycle with "R4 data_mem_req dropped before ready".
  • Formal on small blocks: decoder, ALU, arbiters, FIFOs and protocol FSMs can be proven completely. Prove the unit, simulate the core.

Spec rules & constraints

  • Every spec protocol rule has one named assertion and one cover.
  • Assertions must never fire on correct RTL: run them on the known-good design first (0/9 false fires in the lab).

Bugs that live here

  • Original course interface had no assertions: P2 was invisible to every test.
  • Vacuous pass: an assertion on a signal renamed in RTL compiles against a stale wire and never triggers. Covers expose it.

Interview

Q: Give an example of a bug only an assertion can catch.

In the lab: the core kept fetching while a load was pending, which the spec forbids. The memory model happened not to answer, so no result was ever wrong, and the scoreboard passed 6/6. The protocol assertion d_wait |=> !i_req failed at once.

Interview

Q: 100% code coverage. Is the design verified?

PL·26

Debug playbook: from a red regression to a root cause

Debug is a search. Shrink the space fast: first divergence, then the instruction, then the cycle, then the signal. Classify early: DUT, testbench, model or spec.

Deep dive

  • Read the log you have before rerunning: the A1 "lbu mismatch" was diagnosed from timestamps alone. The load was accepted at 29.59 µs, and end of test ran at 29.64 µs with a 16-cycle data delay.
  • Impossible values point to the testbench: an LBU result of 0x7b5babbc cannot come from a zero-extended byte, so the compare happened at the wrong time, not the ALU.
  • One-line experiments: remove one suspected condition and rerun the same seeds (the D2 store fix took mem from 3/3 failing to 4/5 passing, exposing A1 as the remaining cause).
  • Hangs: find the oldest unfinished item (ROB head, pending request) and what it waits for (tag, ready, credit). Watchdogs should print that state when they fire.
  • Make it smaller: shrink N, shrink the seed's program, then hand-write the minimal directed test. The regression keeps the small test forever.

Spec rules & constraints

  • A fix is not done until the failing seed passes, the new directed test passes, and the full regression is still clean.
  • Never change the checker to make a failure go away without a spec reference.

Bugs that live here

  • Rerunning until green: the original TB failed 40% of clean seeds. A flaky TB hides real bugs in noise.

Interview

Q: A random test fails once in 500 seeds. What do you do?

Reproduce with the exact seed, find the first divergence, classify it (DUT, TB, model, spec), shrink it to a directed test, fix it, then ask why it was 1/500: add coverage for that corner and bias stimulus toward it so the class is hit every night.

jalr target? (rs1 + imm) & ~1, using the old rs1 even if rd = rs1. (PL-03)
08
Signed divide by zero? Quotient −1, remainder = dividend, no trap. (PL-01)
09
Where do you compare against the ISS? At retire: pc, rd/wdata, memory ops, traps, CSR writes. (PL-18)
10
How do you handle interrupts in lockstep? The DUT decides; inject the same interrupt into the ISS at that retire boundary; check legality separately. (PL-05)
11
Why is randomize() skewed? Uniform over all solutions; opcodes with more free fields win. solve-before or pick the opcode first. (PL-20)
12
What does #1step sample? The value just before the clock edge (Preponed). (PL-21)
13
A bug only SVA can find? One with no data effect, e.g. a protocol violation the responder tolerates. (PL-22)
14
Code coverage 100%: done? No: executed ≠ checked ≠ right combinations. (PL-23)
15
How do you qualify a testbench? Mutation: inject realistic bugs, require 100% caught and 0 false fails. (PL-24)
16
Store-to-load forwarding corner? Partial overlap (sb then lw): wait or merge bytes. (PL-15)
17
What's RVFI? RISC-V Formal Interface: a standard retire trace port used by riscv-formal and handy for scoreboards. (PL-17)
18
How do you find deadlocks? Watchdog + per-resource liveness and conservation assertions + full-queue stimulus. (PL-14)

Deep dive

  • "How would you verify X?" template: (1) spec and risks, (2) reference model, (3) checkers: scoreboard + SVA + liveness, (4) stimulus: directed corners + constrained random, (5) coverage model, (6) closure: holes, mutation, regression trend.
  • Say numbers: "4 of 9 to 9 of 9 bugs caught", "79 of 120 seeds", "CPI 1.17 vs 1.66". Measured results are what separate a senior answer.
  • Name trade-offs: lockstep compare (precise, slower) vs end-of-test (fast, blind), formal (complete, depth-bound) vs simulation (deep, incomplete).
  • Close with the lesson: every bug story ends with which checker or coverage point you added so the bug class cannot return.

Spec rules & constraints

  • Answer the question asked first, in one sentence, then add depth.
  • When unsure about a spec detail, say what you would check and where (the spec chapter, Sail, Spike).

Bugs that live here

  • Common interview mistake: describing a test that would pass on the buggy design, e.g. a slt test with only positive operands.
