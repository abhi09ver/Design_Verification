Module 0

The machine at a glance

design.sv · tomasulo_pkg.sv

The life of one instruction

Follow mul x3, x1, x2 from the demo program (measured cycle numbers in the stepper below):

  1. Fetch: read with its bundle into the fetch register, then the instruction queue, then the fetch→decode latch.
  2. Decode (cycle 5): operation key, type 10 (MUL/DIV), sources x1 and x2, destination x3.
  3. Rename / dispatch (cycle 6): gets ROB 2. Its sources are produced by ROB 0 and 1 in the same bundle, so it records tags, not values. The RAT now says x3 → ROB 2.
  4. Reservation station (cycle 7): written into MD_RS[0], waiting for tags 0 and 1. Both broadcast this cycle.
  5. Issue and execute (cycle 9 onward): selected, then 3 Booth stages and the completion buffer.
  6. Writeback (cycle 14): 42 on the CDB with tag 2. The ROB entry becomes ready, and the waiting add captures the value.
  7. Commit (cycle 15): oldest in the ROB, so it retires and writes x3 = 42 into the architectural register file.

Three orders

Instructions enter in program order (fetch, decode, rename), execute in dataflow order (whenever operands are ready), and leave in program order (commit). Everything in an OOO core exists to connect those three orders safely.

Three hazards, three answers

WAR and WAW (false dependencies): renaming. RAW through registers: tags and wakeup on the CDB. RAW through memory: the load/store queues, because addresses are only known late.

Module 1

Frontend

fetch.sv · fetch_unit.sv · branch_predictor.sv

What it does

Every cycle the frontend reads 3 consecutive instructions (12 bytes) from a byte-addressed instruction memory into a fetch register. That register feeds a 16-entry instruction queue (IQ), and the IQ feeds a fetch→decode latch. A predecoder classifies each slot as call, return or branch for the branch predictor: a 64-set × 4-way BTB with tree-PLRU, a 1K-entry gshare, a 16-deep return address stack, and a branch-prediction queue.

The PC register (fetch_pc_mux_d) normally advances by 12. The IQ decouples fetch from decode: fetch can run ahead while decode is stalled, until the queue fills.

Hidden concepts

Valid/ready is a contract

Data crosses a boundary only on valid && ready. The producer must hold both the data and its own state (here: the PC) when ready is low. Bug B09 breaks this contract in three places.

All-or-nothing bundles

If a 3-wide bundle can be partly accepted, the PC must move by the accepted amount. Accepting all or nothing (count + 3 <= depth) is simpler and keeps one invariant: decode slots are a contiguous prefix, which ROB indexing depends on (rob = ROB_head + slot).

Prediction timing

This predictor looks at the bundle already fetched, so a taken branch redirects one cycle late and the next sequential bundle is wrong-path. Real cores either predict from the PC (next-line/BTB lookup in the same cycle as the I-cache) or squash the wrong-path bundle.

Why gshare needs checkpoints

The global history register must be updated speculatively at prediction and restored on a mispredict. Updating it at resolution, as here, indexes the table with a different history than prediction used.

B09

Frontend ignores back-pressure and replays stale bundles

Wrong data

Wherefetch.sv:96, fetch_unit.sv:60, 104, 215, 257

SymptomWith a long DIV chain stalling allocation, instructions 0x70–0x80 are never executed, and 0x64–0x6c are executed twice. The original test still finished because an instruction-count cap in the core stopped allocation after 33 instructions, duplicates included.

HintDoes the PC register know when the instruction queue refused a bundle? What does the fetch→decode latch hold when the IQ is empty?

Reveal root cause and fix

Root causeThree cooperating problems. (1) fetch_pc_mux_d advances every cycle even while instruction memory is stalled on iq_full, so whole bundles are skipped. (2) The IQ accepts partial bundles (enq_ready[j] = count+j < DEPTH) while the PC moves by 3. (3) The fetch→decode latch only updates slots that have deq_valid, so a short bundle keeps stale valid instructions in the other slots. A fourth issue: at the end of the program the instruction memory freezes its last bundle as valid and re-enqueues it for 3 cycles.

original
// fetch.sv: PC moves even when imem is stalled

// fetch_unit.sv: latch keeps stale slots

fix
assign iq_room    = (iq.count + ISSUE_WIDTH) <= IQ_DEPTH;   // all-or-nothing
assign imem_stall = stall_in || !iq_room;
assign fetch_hold = imem_stall;                               // PC holds too
...
if (deq_ready[i]) fec_dec_latch[i] <= deq_valid[i] ? deq_data[i] : '0;   // bubbles
...

Interview questions

Why does an OOO core need an instruction queue between fetch and decode?

It decouples two pipelines with different stall sources. Fetch stalls on I-cache misses and redirects; decode/rename stalls on back-end resources (ROB, RS, LSQ full). The queue absorbs bursts so neither side waits for the other cycle by cycle, and it is the natural point to apply back-pressure.

A fetch register is stalled but the PC keeps moving. How would you detect that in verification?

Compare the committed PC stream with the ISS. Any skipped instruction is an ORDER mismatch at the first commit after the gap. White-box: an assertion that the PC register is stable whenever the fetch register is held (imem_stall |=> $stable(pc)), plus a scoreboard of fetched vs. enqueued PCs.

Tree-PLRU vs true LRU for a 4-way BTB?

True LRU for 4 ways needs 5 bits per set (one of 24 orderings) and an update that touches all of them. Tree-PLRU needs 3 bits, and an access only flips the bits on its path. It approximates LRU: it never evicts the MRU way, but it does not always pick the true LRU way.

How do you verify a branch predictor if a misprediction is never a functional failure?

With performance checks and unit tests: a reference model of the predictor fed the same branch stream must predict the same direction and target; then assert prediction accuracy on known patterns (always-taken loop, alternating, correlated). Full-chip: check that every mispredict is recovered (commit stream correct) and track MPKI as a regression metric.

Module 2

Decode

decoder.sv · decoder_pkg.sv · tomasulo_pkg.sv

What it does

Three parallel decoders turn each instruction word into a decode_entry_t: register fields, the immediate, a 17-bit operation key {funct7, funct3, opcode}, and a 2-bit type that picks the reservation station: 00 ALU, 01 memory, 10 MUL/DIV, 11 other (branch/jump). dst is forced to 0 for stores and branches so they never claim a register.

Hidden concepts

Format decides what bits mean

RISC-V has six formats (R, I, S, B, U, J). The same bit positions mean different things in each. [31:25] is funct7 only in R-type (and as imm[11:5] that happens to carry the srai flag in shifts). Everything downstream of the decoder trusts the key, so a decode bug looks like a back-end bug.

The immediate is always sign-extended

In RV32I, imm bit 31 is always the sign, in every format. That design choice lets hardware start sign-extension before it knows the format.

x0 is not a register

Writes to x0 are discarded and reads give 0. Here that is done by never renaming x0 (dst = 0 means 'no destination') and reading 0 at dispatch. Any path that forgets it creates a fake dependency on 'x0'.

B01

Immediate bits leak into the opcode key

Deadlock

Wheretomasulo_pkg.sv:407, decoder.sv:137-145

Symptomaddi x1, x0, 100 never retires. The ROB fills up behind it and the core hangs with 0 instructions committed. The original program passed only because every immediate in it was smaller than 32.

HintPrint decode_reg.operation for addi x1,x0,100. Which bits of the instruction ended up in the top 7 bits of the key?

Reveal root cause and fix

Root causeThe operation key is {instr[31:25], funct3, opcode}. Bits [31:25] are a real funct7 only for R-type instructions and the shift-immediates. For every other I-type, S-type and B-type instruction they are immediate bits. addi with imm=100 builds key 0x00c13, matches nothing in get_instr_type, and is classified OTHER (type 11). OTHER instructions get no reservation station, so the ROB entry is never filled in.

original
op = create_operation(fetch_instruction[i]);   // {instr[31:25], funct3, opcode}
decode_reg[i].instr_type <= get_instr_type(op);
fix
op = create_operation(fetch_instruction[i]);
unique case (fetch_instruction[i][6:0])
  7'b0110011: ;                                          // R-type: keep funct7
  7'b0010011: if (fetch_instruction[i][13:12] != 2'b01)  // OP-IMM, not a shift
                op[16:10] = 7'b0;
  7'b1101111: op[16:7]  = 10'b0;                         // jal: no funct3 either
  default:    op[16:10] = 7'b0;                          // load/store/branch/jalr
endcase

Caught byOn the original RTL, 13 of the 20 directed tests trip SVA A1 (valid instruction decoded as OTHER) before anything else, on the decode cycle.

Interview questions

Why sign-extend immediates in decode and not in the ALU?

Decode is the only stage that knows the format. After decode, the immediate is just a 32-bit operand, so the ALU, the AGU and the branch unit all share one representation. It also takes the sign-extension mux out of the execute critical path.

Your directed test suite passes, but one decode field is wrong for 90% of encodings. How?

The tests only used small immediates (here every immediate was below 32), so the aliased bits were always 0. Field-level coverage on the encoding (each bit of imm toggled, each format × each opcode) would show the hole at once. Constrained-random over the full encoding space finds it in seconds.

What decode-time information does rename need?

Source and destination architectural registers, whether each source is used, whether dst is real (not x0, not store/branch), the functional-unit class, and the immediate. Getting 'source used' wrong creates false dependencies, which are slow but correct. Getting 'dst real' wrong corrupts state.

Module 3

Rename & Dispatch

alloc_reorder_retire.sv:342-678

What it does

Dispatch takes up to 3 decoded instructions per cycle. For each one it:

  1. Allocates a ROB entry: rob = (ROB_head + slot) % 48. In this code ROB_head is the allocation pointer and ROB_tail the commit pointer, the reverse of most textbooks.
  2. Resolves each source in priority order: a producer earlier in the same bundle → the RAT (in flight, so take its ROB tag, then try to grab the value from the CDB or retire bus this cycle) → x0 → the ARF.
  3. Picks a free RS slot of the right class.
  4. Updates the RAT: RAT[dst] = rob.

The bundle goes to all-or-nothing allocation: if any resource is short (ROB, ALU RS, MD RS, LSB), the whole bundle stalls (alloc_stall).

Hidden concepts

The ROB index is the physical register

This is Tomasulo with a ROB, where data lives in the ROB. A ROB tag names the value, the RAT maps x3 → ROB5, and consumers wait on tag 5. This removes WAR and WAW hazards: in the stepper, x3 is written by the MUL (ROB 2) and the SUB (ROB 5), and the RAT simply points to the youngest. A PRF-based design (MIPS R10K, most modern cores) keeps values in a physical register file instead, so the ROB holds only pointers.

Intra-bundle dependencies

Instruction 2 in a bundle may read what instruction 0 writes in the same cycle. The RAT cannot know yet, so dispatch compares each source against earlier slots' destinations (a priority mux, youngest earlier slot wins). Cost grows as O(width²), one reason rename width is hard to scale.

Age = distance from the commit pointer

In a circular ROB, tag 3 can be younger than tag 40. True age is (tag − commit_ptr) mod N. Any raw < on tags is a bug waiting for the wrap.

One source of truth

Bug B12 had two copies of 'which RS slots are free', updated by signals one cycle apart. Derive availability from the real state plus what is in flight, and nothing else.

Interview questions

Explain register renaming in one minute.

Architectural registers are few, so independent instructions reuse the same names, creating false WAR/WAW dependencies. Rename maps each destination to a fresh physical name (here a ROB entry) and records the newest mapping in the RAT. Sources read the RAT to find their producer. Only true RAW dependencies remain, so independent work can run out of order. At commit, the value moves to the architectural state, and the mapping is cleared if it still points at that entry.

ROB-as-storage (this core) vs physical register file?

ROB-as-storage copies values twice (FU → ROB → ARF at commit), and operands may come from the ROB, the ARF or the CDB, which means more read ports and muxes. A PRF writes once; commit only frees the previous mapping. The PRF scales better, which is why modern cores (and RISC-V BOOM) use it. ROB-as-storage is simpler to build and verify, which is why teaching cores use it.

When is it safe to clear a RAT entry at commit?

Only if it still points to the committing entry. If a younger instruction already renamed the same register, the mapping belongs to the younger one and must stay. This core checks RAT_tag == retiring rob before clearing, which is correct.

How do you stall a 3-wide dispatch fairly?

All-or-nothing on the bundle is simplest and keeps decode slots a prefix. Partial dispatch is faster but then the remaining slots must shift down (or decode must handle holes), and ROB indexing can no longer be head + slot.

Module 4

Issue: wakeup & select

alloc_reorder_retire.sv:913-1197 · alu_top.sv · mul_div_top.sv

What it does

Reservation stations: 12 ALU, 4 MUL/DIV, 16 load/store (LSB). Each entry holds the operation, two operands, each with either a value or the ROB tag it waits for, and a ready bit.

Wakeup: every cycle each waiting operand compares its tag with all 3 CDB lanes. It also checks a 1-cycle-delayed copy of the CDB and the retire bus, as belt-and-braces. Select: alu_top picks up to 3 ready entries (one per ALU), oldest-ROB-index first. mul_div_top picks one MUL and one DIV per unit. A selected entry is cleared from the RS that same cycle (rs_clear).

Hidden concepts

The wakeup–select loop sets your IPC

For back-to-back dependent single-cycle ops, an instruction selected in cycle N must wake its consumer in time for the consumer to be selected in N+1. That is the critical loop of every OOO core. Here ready is re-registered from src_valid, which adds a cycle: dependent adds run at 1 per 2 cycles (see the chain in exercise E4).

Capture vs. no-capture RS

This design is data-capture: operand values are copied into the RS, from the ARF at dispatch or from the CDB at wakeup. The alternative is non-capture: the RS holds only tags and operands are read from the PRF after select. Capture needs wide RS entries and CDB-to-RS data wires. Non-capture needs PRF read ports after select.

Select must be 1:1

Every entry cleared from an RS must arrive at exactly one functional-unit input in the same cycle. Bug B03 (ALU drops op) and bug B05 (DIV overwritten) both broke this, and both lost an instruction silently.

Sentinels

Tag 0 used as 'no tag' (B04). The valid bit is the only correct qualifier.

B05

Interview questions

Walk me through wakeup and select for a 3-wide CDB.

Each RS operand has a comparator per CDB lane (12 ALU × 2 operands × 3 lanes = 72 tag comparators just for the ALU RS). On a match, the value is captured and the operand marked valid. Select is a priority arbiter over ready entries (oldest first, or position-based), one grant per functional unit. In high-frequency designs wakeup and select are in the same cycle for 1-cycle ops, often with speculative wakeup for loads (assume an L1 hit, replay on a miss).

Why might a real design not pick the oldest ready instruction?

A true age matrix costs N² bits and a wide reduction. Many designs use position-based priority (lowest RS index) or a compacting queue, where position equals age. Oldest-first matters mostly for long-latency chains and for forward-progress guarantees, so a cheap approximation plus an anti-starvation timer is common.

Name three ways an instruction can be lost between RS and ROB, and the assertion for each.

(1) Selected but the FU drops it: ex_valid |-> ##[lat] result_ready. (2) Two entries selected into one FU port: one-hot check on FU inputs, popcount(clear) = popcount(issue). (3) Wakeup missed because the broadcast came while the entry was being written: compare the tag against the CDB in the allocation cycle too (this design does). Plus a global liveness check that the ROB head retires within N cycles.

Module 5

Execute

alu_unit.sv · mul_div.sv · radix_4_multiplier.sv · radix_8_dividor.sv

What it does

3 single-cycle ALUs. 2 MUL/DIV units, each with a 3-stage radix-4 Booth multiplier (Booth encode → CSA tree → carry-propagate add) and an 11-stage radix-8 divider that does 3 quotient bits per stage, fully pipelined with the ROB tag carried along. MUL/DIV entries leave the RS at issue. Results come back tagged, and the unit keeps a per-tag table of which operation (mul vs. mulh) to finish.

Hidden concepts

Radix-4 Booth

Booth recoding looks at 3 multiplier bits at a time (overlapping by one) and turns them into a digit in {−2, −1, 0, +1, +2}. That halves the partial products (16 instead of 32 for 32 bits). The −2 digit needs −2M, so partial products need 2 extra bits, not 1 (bug B14).

Signed vs. unsigned high product

One signed 32×32 multiplier can produce all four RISC-V multiplies: mulhu = mulh + (a<0 ? b : 0) + (b<0 ? a : 0) and mulhsu = mulh + (b<0 ? a : 0), all mod 2³². This is how the fix adds mulhu/mulhsu without a second multiplier.

RISC-V does not trap on divide by zero

x/0 = all ones, x%0 = x. Overflow −2³¹/−1 = −2³¹ with remainder 0. These come straight from the spec table and are the first things to test.

Variable latency means out-of-order completion

ALU 1 cycle, MUL 3, DIV 11+. Results arrive out of order and in bursts, which is why the completion buffer exists (module 6).

Interview questions

Why radix-4 Booth instead of a plain array multiplier?

It halves the partial-product count, so the reduction tree is shallower (fewer CSA levels) and smaller, for a modest recoding cost. Radix-8 halves again but needs a hard 3M multiple precomputed with an adder, which is the classic area/delay trade-off.

How would you verify a 32-bit divider? You cannot simulate 2⁶⁴ cases.

Corner cases from the spec (0, ±1, MIN/MAX, x/0, overflow), random with a reference model, structured patterns (powers of two, all-ones, divisor > dividend), and formal equivalence against a simple behavioural divider (a == q*b + r and |r| < |b|, with sign rules) using an SVA property on the output. Formal is the real answer for datapath at Nvidia/Google scale.

A pipelined unit returns results by tag. What can go wrong?

Tag reuse (a tag freed and reallocated while an old op is still in the pipe), a flush that does not kill in-flight ops, two ops with the same tag (rename bug), and a result arriving after its ROB entry is gone. Assert that every returned tag is a live, not-yet-completed ROB entry (SVA A4).

Module 6

Writeback & CDB

completion_buffer.sv

What it does

Nine producers (3 ALU + 2×MUL + 2×DIV + 2 load ports) can finish in the same cycle, but the common data bus has only 3 lanes. The completion buffer is a 48-entry FIFO. When it is empty and at most 3 results arrive, they bypass straight to the CDB. Otherwise they are queued and drained 3 per cycle. When the count reaches 48 − 9 − 5 = 34, almost_full stalls the ALU and MUL/DIV select and the load issue.

Hidden concepts

Why a buffer at all

Without it you need either 9 CDB lanes (9 tag comparators per operand per RS entry) or arbitration that stalls functional units mid-pipeline. Pipelined MUL/DIV cannot stall cheaply. Buffering moves the cost to a FIFO.

Safety margin = credits

almost_full must fire early enough to absorb everything already in flight that cannot be stopped: up to 9 results per cycle, plus the multi-cycle pipelines. The margin is credit-based flow control done by hand. A formal proof or an assertion that the FIFO never overflows is the real check, because the enqueue silently drops results when full (completion_buffer.sv:126).

FIFO order is not age order

Results are broadcast in arrival order, not program order. That is fine because the ROB restores order at commit.

Interview questions

How many CDB lanes would you choose, and how do you decide?

Simulate: measure results per cycle on the target workloads. Most of the time it is at most the issue width. Each lane adds a tag comparator per operand per RS entry plus a write port into the ROB/PRF, so the cost grows with RS size × lanes. Choose the lane count where the queueing delay costs less IPC than the extra wakeup-loop delay and area.

What is credit-based flow control and where else does it show up in a GPU?

The sender keeps a count of free slots at the receiver, decrements it on send, and the receiver returns a credit when it frees a slot, so the sender never overruns. In GPUs: NoC/crossbar links, memory request queues, the texture and L1 return paths, and NVLink. Verification checks credit conservation (credits + in-flight + occupied = depth) as an invariant.

Module 7

Commit

alloc_reorder_retire.sv:1219-1406

What it does

Up to 3 instructions retire per cycle, in order, from ROB_tail (the commit pointer). An entry retires if it is valid && ready. The first entry that is not ready stops the group. On retire, the value is written to the ARF (unless dst = x0), the RAT mapping is cleared if it still points at this entry, and the retire info is broadcast as a late wakeup source. Stores become 'ready' when they enter the store queue, and they write memory only after they retire (module 8).

Hidden concepts

Precise state

Because commit is in order, the ARF always equals the state of a simple in-order machine at some instruction boundary. That makes precise exceptions and interrupts possible: flush everything younger than the faulting instruction, and the ARF is exactly right. This core has no exceptions yet. Implementing them uses the same mechanism as branch recovery (module 10).

The commit stream is your verification contract

Everything inside the core may reorder. The committed stream of (PC, rd, value) and the memory writes may not. That is why the lab's scoreboard compares exactly those against the ISS, commit by commit.

Retire width vs. dispatch width

If retire is narrower than dispatch, the ROB fills on long-latency stalls and never catches up. Here both are 3.

Why can't stores write memory when they execute?

Memory is architectural state. A store that executes and is later squashed (a mispredicted branch or an older exception) would have changed memory irreversibly. So stores wait in the store queue and write only after commit. Loads can still get the value early through store-to-load forwarding.

Module 8

Memory: LSB, LQ, SQ

memory_management_unit.sv · data_mem.sv · top_memory_subsystem.sv

What it does

Memory instructions wait in the 16-entry LSB until their base register (and, for stores, the data) is ready. The MMU then moves loads into an 8-entry load queue and stores into an 8-entry store queue. Loads issue on 2 read ports, either forwarded from an older store or read from data memory (1024 words, initialised so word i = i). Stores mark their ROB entry ready on entering the SQ, become senior when they retire, and drain through 1 write port in program order.

Hidden concepts

The memory RAW hazard

Registers are renamed at decode, but memory addresses are only known at execute, so a load may not know whether an older store writes its address. The options are: wait until all older store addresses are known (conservative, used by the fix), or speculate, issue anyway, check when the older store's address resolves, and replay on a violation. Real cores speculate, with a store-set or memory-dependence predictor to avoid repeat violations.

Forwarding rules

Forward from the youngest older store that overlaps. Forward only if it fully covers the load's bytes, then byte-select and extend. On a partial overlap, wait until the store has drained to memory.

Senior stores

Between 'retired' and 'written to memory' a store is architecturally done but still invisible in memory. Every load is younger than a senior store, and the ROB tag can no longer give its age (bug B13c).

Resource deadlock

If a younger instruction can take the last slot in a shared queue that an older one needs, and the younger one cannot leave before the older one, you have a deadlock (bug B13a). The fixes are in-order allocation or a reserved slot for the oldest.

Interview questions

Your test passes. Why might you still not trust it?

Because the checker might be wrong or blind. Here the original checker was keyed by ROB id with hand-written expectations (one comment was wrong), it ignored liveness (an instruction-count cap ended the test), and it could not see internal invariants (the LQ duplicate). Ask: what is the oracle, what does it compare, at what granularity, and what can fail without the oracle noticing?

Scoreboard at commit vs. at writeback: trade-offs?

Commit-level comparison is architecturally clean (it matches the ISS exactly) but reports late and cannot see transient corruption that gets overwritten. Writeback- or unit-level scoreboards localise failures but need a microarchitectural model (expected latency, ordering). Real projects do both: architectural at the top, transaction-level at each unit boundary.

How do you know you're done verifying?

Coverage closure against a verification plan (features × corner cases), assertion coverage (every property exercised, not just never failed), a bug-rate trend that has flattened across random seeds, a code-coverage review of holes, and sign-off reviews. Never 'all tests pass'.

Capstone: build branch support

every module

The backend has no branch unit. A branch gets type 11: it receives a ROB slot but no reservation station, so the ROB head waits forever (b11_branch hangs). Building branch support is the best single project for an OOO interview: it touches every module and forces you to design recovery.

  1. Branch unit

    Add type 11 to dispatch. Give branches ALU RS entries (or a separate BR RS). Compute taken and target in a branch unit: beq bne blt bge bltu bgeu, jal, jalr. jal/jalr also write rd = PC+4.

  2. Resolve and compare

    Carry the predicted next-PC with each instruction from fetch (the BPQ is a start). At execute, mispredict = (actual next-PC ≠ predicted).

  3. Recovery

    Simplest correct version: when a mispredicted branch commits, assert flush, clear everything younger (the ROB, all RS, LQ, SQ non-senior entries, the completion buffer, the MUL/DIV pipelines), restore the RAT to 'all registers in ARF', and redirect fetch to the correct PC. Faster: recover at execute with RAT checkpoints per branch.

  4. Train the predictor

    Drive update_en/pc/taken/target from commit. Checkpoint gshare history at prediction.

  5. Verify

    Extend tools/rv.py (branches are already modelled). Write loops, calls/returns and data-dependent branches. Assertions: nothing younger than a flushing branch commits; after a flush the RAT is clean; senior stores survive the flush. Coverage: mispredicts in each bundle slot, a mispredict while the ROB wraps, a mispredict with a DIV in flight.

Done means: b11_branch passes, plus your own loop, call/return and data-dependent-branch tests pass against tools/rv.py, with 0 SVA firings over 500 random seeds after you add branches to gen_random.py.

3-wide RISC-V RV32IM out-of-order core. That found 15 functional bugs across decode, issue, execute, memory and frontend, including two deadlocks that only random stimulus exposed.

What's the hardest bug you found and how did you debug it?

The store-queue deadlock and bypass (B13). Random programs hung with a store stuck at not-ready. The trace showed the SQ full of younger stores while the oldest store waited in the LSB, which is a resource deadlock. While fixing it I found that the age function broke once a store retired: its ROB tag wrapped and it looked younger than later loads. The fix was in-order SQ entry and explicit retire signals from the ROB to the MMU. The general lesson: resources shared by instructions of different ages must be allocated in age order, or reserve capacity for the oldest.

How would you build a verification plan for an OOO core from scratch?

Start with the contract: the committed stream equals the ISA reference. Then layer it. (1) An ISS-based commit scoreboard with lock-step comparison. (2) Directed tests per feature from the spec. (3) Constrained-random instruction streams with knobs for hazards, aliasing and latency mixes. (4) White-box SVA on microarchitectural invariants (ROB order, unique tags, RS free-list, LSQ order, credit counters). (5) Functional coverage: every structure full and empty, every bypass path, every corner-case matrix. (6) Unit-level tests and formal for datapath and arbiters. (7) Performance checks: IPC against a model, which catches the bugs that are correct but slow.

Correct but slow: how do you catch performance bugs?

Keep a performance model or expected-cycle budget per directed test, and track IPC per regression run. Microbenchmarks isolate one mechanism: a dependent ALU chain should be 1 IPC per dependency, independent ALU ops should reach issue width. In this core, the chain test showed 2 cycles per dependent add, which pointed straight at the registered ready bit.

What is bug masking and how do you deal with it?

One bug stops execution before others can show. Here, the decode key bug stopped 13 of 20 directed tests within the first few instructions. Each fix revealed the next layer. To deal with it: fix and re-run in small steps, keep tests narrow so each targets one mechanism, and use assertions, which report problems even when the end result is masked.

Why bind assertions instead of writing them in the RTL?

Bind keeps verification code out of the design files: designers own the RTL, DV owns the checkers, and synthesis never sees them. A bind applies to every instance of a module and can reach internal signals by name. You can also turn checker sets on and off per run.

Blocking vs non-blocking assignments in this design: what went wrong?

Several clocked blocks used blocking assignments for state that another clocked block reads at the same edge (temp_RAT, busy arrays, ROB_next), and one variable had two drivers. The result depends on which block the simulator schedules first, so behaviour can differ between Xcelium, VCS and Verilator, and synthesis builds something different again. The rule: one always_ff per state variable, written with non-blocking; next-state logic in always_comb.

GPU angle: what carries over from this CPU to a GPU SM?

Scoreboarding and dependency tracking per warp, operand collectors (like data-capture RS), result buses with limited writeback ports, credit-based flow control, LSQ-like coalescing and ordering in the LD/ST unit, and the same verification pattern: a reference model of the ISA (PTX/SASS semantics), commit- or retire-level comparison, and stress on shared-resource arbitration. GPUs mostly issue in order per warp; the out-of-order aspect is across warps.
