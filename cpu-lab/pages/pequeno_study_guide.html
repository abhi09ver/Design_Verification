Getting hold of the ISA

RV32I · formats · the assembler

What Part 1 coversPicks RISC-V's base integer ISA (RV32I: 37 instructions, 32 registers, x0 = 0), explains why a standard ISA beats inventing one, groups instructions into six formats (R, I, S, B, U, J), and introduces the author's own assembler. Read the original post.

An ISA is the menu a CPU promises to understand. Every dish (instruction) is written on a 32-box order slip in one of six layouts. The kitchen only has to learn those six layouts. The cleverness: the boxes that say which registers (rs1, rs2, rd) are in the same place on every slip, so the kitchen can start fetching ingredients before it has finished reading the order.

tools/rv32i.py is a ~200-line assembler with labels (so you can write bne x1, x0, loop) plus a golden instruction-set simulator for all 37 instructions. halt is jal x0, 0 (jump to yourself), the usual bare-metal "stop here". The encoder was checked against known encodings before any program was written.

Hidden concepts

Why are B and J immediates scrambled?

So that every immediate bit sits in the same instruction bit across formats as often as possible (bit 31 is always the sign). The hardware then needs fewer multiplexers. Software (the assembler) pays the cost of shuffling once.

No multiply in RV32I

MUL/DIV live in the M extension. On RV32I you multiply with shift-and-add, as p09_multiply.s does.

Pseudo-instructions

nop = addi x0,x0,0, mv = addi rd,rs,0, j = jal x0,…, ret = jalr x0,0(ra). They cost no hardware.

Check yourself

Where is rs1 in an S-type instruction?

Bits 19:15, the same as in every other format that has rs1.

What does addi x5, x0, -1 put in x5?

0xFFFFFFFF. The 12-bit -1 is sign-extended to 32 bits.

Which instruction is a 'free' NOP?

addi x0, x0, 0. The write to x0 is thrown away.

Interview question

Why is RISC-V popular for teaching and for industry?

Open and royalty-free, small clean base ISA with optional extensions, fixed 32-bit encoding with register fields in fixed positions (simple decoders), and a big open tool and RTL ecosystem.

Specifications and architecture

5 stages · valid / stall / flush

What Part 2 coversSets the spec: 32-bit, RV32I, single-issue, strictly in-order 5-stage pipeline (fetch, decode, execute, memory access, writeback), separate instruction and data memory interfaces, bare-metal (no CSRs, interrupts or exceptions). Each stage hands a packet to the next with a valid bit; stall goes backwards, flush kills older-stage packets. Read the original post.

A sandwich shop with one worker does everything for customer 1, then everything for customer 2. Slow. Five workers in a row (take order, read order, make, wrap, hand over) each do one step and pass the tray on. Each customer still takes 5 steps, but a finished sandwich comes out every step. That is pipelining: same latency, 5× the throughput.

pq5 follows the same spec and stage split: one module per stage, a pipeline register between stages, a valid bit in every packet (valid = 0 is a bubble), stall from decode back to fetch, and flush + redirect_pc from execute. Simplifications to stay small: memories are plain arrays (no bus handshake), and fetch has one buffer instead of two.

Hidden concepts

Δ + N − 1

With Δ = 5 stages and no hazards, N instructions finish in 5 + N − 1 cycles. pq5 measures exactly that: p01_alu has 23 instructions and takes 27 cycles.

Why not single-cycle?

The clock must wait for the slowest instruction's whole path (memory + decode + ALU + memory + write). Pipelining cuts that path into 5 short pieces, so the clock can be much faster.

A stall in one stage stalls everything older

In-order means nobody may overtake. The instructions behind a stalled one must also hold; the ones ahead keep going, and a bubble appears between them.

Check yourself

A program has 100 instructions and no hazards. How many cycles on a 5-stage pipeline?

5 + 100 − 1 = 104.

What is a bubble?

A pipeline slot carrying nothing (valid = 0). It moves through the stages like an instruction but changes no state.

Interview question

Throughput vs latency for a pipeline?

Latency per instruction stays about the same (or grows slightly because of pipeline registers). Throughput approaches 1 instruction per cycle at a higher clock frequency. The cost is area, power and hazards.

Dealing with pipeline hazards

structural · data · control

What Part 3 coversClassifies hazards. Structural ones are removed by design (split instruction and data memories, a 2-read/1-write register file, local adders). WAR and WAW cannot happen in an in-order pipeline that writes back last. RAW is handled by forwarding, except a load followed immediately by a user, which needs a one-cycle interlock. Control hazards are handled by prediction in fetch plus a flush when execute finds the guess was wrong. Read the original post.

RAW: worker 3 needs the sauce worker 4 is still finishing. Instead of waiting for it to be put on the shelf (the register file), worker 4 passes it straight back over the counter: forwarding. Load-use: the sauce comes from the store-room (memory), one step later; no amount of passing helps, so worker 3 waits one beat. Branch: the customer might change their order. We guess and keep working. If the guess was wrong, we throw away the 2 sandwiches started since and start the right one: a flush.

See it: a load-use stall (real simulation)

Each column is one clock cycle, each row a stage. lw x2 is in EX in cycle 5 while addi x3, x2, 1 waits in decode: one bubble enters EX, and the add continues a cycle later with the value forwarded from WB.

See it: a wrong guess (flush)

blt x1, x2, x1_small jumps forward, so fetch guessed "not taken". In cycle 5 execute finds it IS taken: the two instructions behind it become bubbles and fetch restarts at the right place. Cost: 2 cycles.

See it: a loop the predictor gets right

The backward bne is guessed taken, so the loop streams with no bubbles, until the very last iteration (cycle 305) where it falls through: one flush in 100 iterations.

Hidden concepts

Forwarding only goes forward in time

A value can be handed to a later instruction if it already exists. A load's value exists only after MEM, one cycle after its neighbour needs it in EX, hence the single bubble.

Penalty depends on where branches resolve

pq5 resolves branches in EX, so a wrong guess costs 2 bubbles (the instructions in IF/ID and ID). Resolving in ID would cost 1 but needs a comparator and forwarding into decode.

CPI = 1 + stall cycles per instruction

In pq5: cycles = 4 + N + load-use stalls + 2 × flushes. That predicts every measured run exactly (table above).

Check yourself

Why can't WAW happen in an in-order 5-stage pipeline?

All writes happen in the same stage (WB) in program order, so the later write always lands last.

lw x2,0(x0) then add x3,x2,x2. How many bubbles?

One. With one independent instruction in between: zero.

A loop runs 100 times. The backward branch is predicted taken. How many flushes?

One, on the final exit, when the branch falls through. p04_loop_sum shows exactly 1.

Interview question

Explain forwarding, and where the muxes go.

Muxes at the ALU inputs in EX choose between the register value read in decode, the result in EX/MEM (distance 1), or the value in MEM/WB (distance 2). The nearest producer wins. Distance 3 is covered by the register file writing before (or through to) the read. Loads in EX/MEM are not forwardable, so an interlock inserts a bubble.

What happens to CPI with 20% branches, 30% mispredicted, 2-cycle penalty?

1 + 0.2 × 0.3 × 2 = 1.12, ignoring other stalls.

Fetch unit

PC · instruction memory · static prediction

What Part 4 coversFetch sends the PC to instruction memory with a valid/ready-style request, gets {instruction, PC} back, and keeps two buffers. A static predictor looks at buffered instructions: jumps taken, backward branches taken (loops), forward branches not taken. Stall comes only from decode; flush and the correct PC come only from execute. Every stage generates its own stall/flush logic. Read the original post.

Fetch is the worker reading the recipe book. It keeps a bookmark (the PC) and normally turns one page. If the recipe says 'go back to step 3' it can turn back right away (a guess). If someone later shouts 'wrong page!', it jumps to the page they name and throws away what it had just read.

pq5 predicts straight from the instruction memory output in the same cycle: jal taken, backward branch taken, everything else (and jalr) not taken. Flush beats stall. Pequeno puts its predictor behind an extra buffer instead, so the prediction logic is not on the memory-to-PC path. It costs one cycle of startup latency and buys a shorter critical path. pq5 chose simple; a real chip would choose Pequeno's way.

The code

module pq5_fetch import pq5_pkg::*; #(parameter int IMEM_WORDS = 256) (
  input  logic        clk, rst,
  input  logic        stall,                 // from decode (load-use): hold everything
  input  logic        flush,                 // from execute: wrong path!
  input  logic [31:0] redirect_pc,           //   ... restart here
  output if_id_t      if_id
);
  logic [31:0] imem [IMEM_WORDS];
  logic [31:0] pc;
  wire  [31:0] instr = imem[pc[$clog2(IMEM_WORDS)+1:2]];

  // static prediction (needs no history):
  //   jal              -> always taken (target known from the instruction)
  //   branch, offset<0 -> taken      (backward branch = probably a loop)
  //   branch, offset>0 -> not taken  (forward branch = probably an if/else skip)
  //   jalr             -> not predicted (target is in a register; execute fixes it)
  wire [31:0] imm_j = {{12{instr[31]}}, instr[19:12], instr[20], instr[30:21], 1'b0};
  wire [31:0] imm_b = {{20{instr[31]}}, instr[7], instr[30:25], instr[11:8], 1'b0};
  logic [31:0] pred_npc;
  always_comb begin
    pred_npc = pc + 4;
    if (instr[6:0] == 7'b1101111)                     pred_npc = pc + imm_j;  // jal
    else if (instr[6:0] == 7'b1100011 && instr[31])   pred_npc = pc + imm_b;  // backward branch
  end

  always_ff @(posedge clk) begin
    if (rst) begin
      pc <= 0; if_id.valid <= 1'b0;
    end else if (flush) begin                  // flush wins over stall
      pc <= redirect_pc; if_id.valid <= 1'b0;  // the instruction we were holding is wrong-path
    end else if (!stall) begin
      pc <= pred_npc;
      if_id <= '{valid: 1'b1, pc: pc, instr: instr, pred_npc: pred_npc};
    end                                        // stall: keep pc and if_id exactly as they are
  end
endmodule

Hidden concepts

The stall must freeze the PC too

If the PC kept moving while IF/ID was frozen, an instruction would be skipped. This is exactly bug B09 in your out-of-order core. pq5 has an assertion that IF/ID never changes during a stall.

Why carry the predicted next PC?

Execute compares the real next PC with what fetch guessed. If they differ, it flushes. That one compare covers wrong direction, wrong target and unpredicted jalr.

Check yourself

Why is a backward branch predicted taken?

Backward branches usually close loops, and loops usually go round again.

Which instruction can't a static predictor guess the target of, and why?

jalr. Its target is in a register, which fetch doesn't have yet.

Interview question

Static vs dynamic branch prediction?

Static: a fixed rule from the instruction itself (backward taken), no state, ~60-70% accurate. Dynamic: learns from history (2-bit counters, gshare, TAGE), 90%+, needs tables, update logic and recovery of speculative history.

Decode unit

fields · immediates · control

What Part 5 coversDecode slices fixed fields (opcode, rs1, rs2, rd, funct3, funct7), builds a type flag per format, an ALU opcode, and the immediate for each format. Source register addresses go to the register file combinationally so the register data and the decoded packet arrive at execute in the same cycle. Only execute can stall or flush decode. Read the original post.

Decode is the worker who reads the order slip and writes it out neatly for the cook: which ingredients (registers), how much (immediate), which recipe (ALU operation). It also asks the pantry (register file) for the ingredients right away, so they arrive at the cook together with the instructions.

pq5's decode also hosts the load-use interlock: if the instruction in EX is a load whose destination this instruction reads, decode stalls fetch and sends a bubble forward. Unknown opcodes (fence, ecall) decode to harmless no-ops; rd = x0 turns off the write.

The code

module pq5_decode import pq5_pkg::*; (
  input  logic        clk, rst,
  input  logic        flush,
  input  if_id_t      if_id,
  output logic        stall,                  // to fetch
  output logic [4:0]  ra1, ra2,               // to register file
  input  logic [31:0] rd1, rd2,
  output id_ex_t      id_ex
);
  wire [31:0] in   = if_id.instr;
  wire [6:0]  opc  = in[6:0];
  wire [2:0]  f3   = in[14:12];
  wire        f7b5 = in[30];
  localparam OP=7'b0110011, OPI=7'b0010011, LD=7'b0000011, ST=7'b0100011, BR=7'b1100011,
             JAL=7'b1101111, JALR=7'b1100111, LUI=7'b0110111, AUIPC=7'b0010111;

  id_ex_t d;     // what this instruction becomes
  logic use1, use2;
  always_comb begin
    d = '0;
    d.valid  = if_id.valid;
    d.pc     = if_id.pc;   d.pred_npc = if_id.pred_npc;
    d.rs1    = in[19:15];  d.rs2 = in[24:20];  d.rd = in[11:7];
    d.funct3 = f3;
    // immediates: bit 31 is ALWAYS the sign
    unique case (opc)
      ST:          d.imm = {{20{in[31]}}, in[31:25], in[11:7]};
      BR:          d.imm = {{20{in[31]}}, in[7], in[30:25], in[11:8], 1'b0};
      JAL:         d.imm = {{12{in[31]}}, in[19:12], in[20], in[30:21], 1'b0};
      LUI, AUIPC:  d.imm = {in[31:12], 12'b0};
      default:     d.imm = {{20{in[31]}}, in[31:20]};          // I-type
    endcase
    // control
    d.alu = A_ADD;
    case (opc)
      OP:    begin d.we = 1; d.alu = alu_from(f3, f7b5); end
      OPI:   begin d.we = 1; d.b_is_imm = 1; d.alu = alu_from(f3, (f3 == 3'b101) ? f7b5 : 1'b0); end
      LD:    begin d.we = 1; d.b_is_imm = 1; d.is_load = 1; end
      ST:    begin d.b_is_imm = 1; d.is_store = 1; end
      BR:    begin d.is_branch = 1; end
      JAL:   begin d.we = 1; d.is_jal = 1; end
      JALR:  begin d.we = 1; d.is_jalr = 1; d.b_is_imm = 1; end
      LUI:   begin d.we = 1; d.is_lui = 1; end
      AUIPC: begin d.we = 1; d.a_is_pc = 1; d.b_is_imm = 1; end
      default: ;                                  // fence/ecall/ebreak/unknown: harmless no-op
    endcase
    if (d.rd == 0) d.we = 0;                      // x0 is never written
    use1 = !(opc inside {LUI, AUIPC, JAL});
    use2 = (opc inside {OP, ST, BR});
  end

  function automatic alu_t alu_from(input logic [2:0] f3, input logic sub_sra);
    case (f3)
      3'b000: return sub_sra ? A_SUB : A_ADD;
      3'b001: return A_SLL;   3'b010: return A_SLT;   3'b011: return A_SLTU;
      3'b100: return A_XOR;   3'b101: return sub_sra ? A_SRA : A_SRL;
      3'b110: return A_OR;    default: return A_AND;
    endcase
  endfunction

  // register file is read right now; values travel in ID/EX with the instruction
  assign ra1 = d.rs1;
  assign ra2 = d.rs2;

  // LOAD-USE INTERLOCK: the load in EX only gets its data in MEM. An instruction that
  // needs it right now must wait one cycle (one bubble) - forwarding cannot go back in time.
  assign stall = if_id.valid && id_ex.valid && id_ex.is_load && id_ex.we &&
                 ((use1 && id_ex.rd == d.rs1) || (use2 && id_ex.rd == d.rs2));

  always_ff @(posedge clk) begin
    if (rst || flush || stall) id_ex.valid <= 1'b0;   // bubble (flush: wrong path, stall: wait)
    else begin
      id_ex <= d;
      id_ex.rs1_val <= rd1;
      id_ex.rs2_val <= rd2;
    end
  end
endmodule

Hidden concepts

funct7 is not always funct7

For OP-IMM, bits 31:25 are immediate bits, except for the shift-immediates, where bit 30 picks srai. Your OOO core put immediate bits into its opcode key (bug B01).

'Uses rs2?' matters

An addi has bits in the rs2 position, but they are immediate bits. Stalling on them would be a false dependency: slow, not wrong. pq5 computes use1/use2 per format.

Check yourself

Which formats have no rs1?

U (lui, auipc) and J (jal).

Why does a store need rs2?

rs2 holds the data being stored; rs1 holds the base address.

Interview question

Where would you put the load-use detection and why?

In decode, because the dependent instruction is there when the load is in EX, the last moment you can hold it back cheaply, and holding decode + fetch is simple.

6

Register file

2 read · 1 write · x0

What Part 6 covers32 × 32-bit registers, two independent read ports (for rs1 and rs2) used by decode, one write port used by writeback, x0 hard-wired to zero. Reads take one cycle and are registered so the data lines up with decode's packet; during a stall the read enable is turned off so the output holds. Read the original post.

32 lockers. Two windows to peek in, one slot to drop things in. Locker 0 is glued shut.

pq5 reads combinationally in decode, and the values are captured in ID/EX together with the instruction, so a stall simply re-reads next cycle. It adds write-through: if writeback writes the register decode is reading in the same cycle, decode gets the new value.

The code

module pq5_regfile (
  input  logic        clk,
  input  logic [4:0]  ra1, ra2,
  output logic [31:0] rd1, rd2,
  input  logic        we,
  input  logic [4:0]  wa,
  input  logic [31:0] wd
);
  logic [31:0] r [32];
  always_ff @(posedge clk) if (we && wa != 0) r[wa] <= wd;
  // write-through ("internal forwarding"): if writeback writes the register decode
  // is reading in the SAME cycle, hand decode the new value. Without this an
  // instruction exactly 3 behind its producer reads a stale value.
  always_comb begin
    rd1 = (ra1 == 0) ? '0 : (we && wa == ra1) ? wd : r[ra1];
    rd2 = (ra2 == 0) ? '0 : (we && wa == ra2) ? wd : r[ra2];
  end
endmodule

Hidden concepts

The same-cycle read/write question

Instruction A in WB writes x5 while instruction D (3 behind) reads x5 in decode. Without write-through or a write-before-read register file, D reads the stale value. Removing write-through from pq5 breaks 7 of 10 directed programs.

Why stall the register file with decode?

In Pequeno the read data is registered. If decode freezes but the register file output moves on, the data no longer matches the frozen instruction. pq5 avoids the issue by not registering inside the register file.

Check yourself

How many read ports does a 2-wide superscalar CPU need?

Four (two sources each). Port count is a big area cost of wide CPUs.

Name two ways to make x0 read as zero.

Guard the read (ra == 0 ? 0 : r[ra]), or guard the write so r[0] is never written (and reset it to 0). pq5 does both.

Interview question

Write-first vs read-first register file?

Write-first returns the value being written in the same cycle (no extra forwarding path needed for distance 3). Read-first returns the old value, so the pipeline must forward from WB. FPGA block RAMs can be configured either way.

7

Execute unit

beyond Part 6 · forwarding · ALU · branches

The cook. Before cooking it checks: is a fresher ingredient being handed back from the next workers? Then it cooks (ALU). For a branch it checks whether fetch's guess was right; if not, it shouts 'wrong page!' (flush) with the right page number.

Forwarding is two priority checks per operand: the instruction one ahead (EX/MEM) wins over the one two ahead (MEM/WB). The branch unit compares registers, computes the target (pc + imm, or (rs1 + imm) & ~1 for jalr), and flushes if the real next PC differs from the predicted one. jal/jalr write the link address pc + 4.

The code

module pq5_execute import pq5_pkg::*; (
  input  logic        clk, rst,
  input  id_ex_t      id_ex,
  input  ex_mem_t     fwd_mem,               // instruction 1 ahead (now in MEM)
  input  mem_wb_t     fwd_wb,                // instruction 2 ahead (now in WB)
  output logic        flush,
  output logic [31:0] redirect_pc,
  output ex_mem_t     ex_mem
);
  // FORWARDING: take the newest value of rs1/rs2. Nearest producer wins.
  function automatic logic [31:0] fwd(input logic [4:0] r, input logic [31:0] from_rf);
    if (r != 0 && fwd_mem.valid && fwd_mem.we && !fwd_mem.is_load && fwd_mem.rd == r) return fwd_mem.result;
    if (r != 0 && fwd_wb.valid  && fwd_wb.we  && fwd_wb.rd == r)                         return fwd_wb.wdata;
    return from_rf;
  endfunction
  wire [31:0] a_reg = fwd(id_ex.rs1, id_ex.rs1_val);
  wire [31:0] b_reg = fwd(id_ex.rs2, id_ex.rs2_val);
  wire [31:0] a = id_ex.a_is_pc  ? id_ex.pc  : a_reg;
  wire [31:0] b = id_ex.b_is_imm ? id_ex.imm : b_reg;

  logic [31:0] y;
  always_comb begin
    case (id_ex.alu)
      A_ADD:  y = a + b;                 A_SUB:  y = a - b;
      A_SLL:  y = a << b[4:0];           A_SLT:  y = {31'b0, $signed(a) < $signed(b)};
      A_SLTU: y = {31'b0, a < b};        A_XOR:  y = a ^ b;
      A_SRL:  y = a >> b[4:0];           A_SRA:  y = $signed(a) >>> b[4:0];
      A_OR:   y = a | b;                 default: y = a & b;
    endcase
  end

  // BRANCH UNIT: decide the real next PC and compare with what fetch guessed
  logic taken; logic [31:0] target, actual_npc;
  always_comb begin
    case (id_ex.funct3)
      3'b000: taken = (a_reg == b_reg);                    // beq
      3'b001: taken = (a_reg != b_reg);                    // bne
      3'b100: taken = ($signed(a_reg) <  $signed(b_reg));  // blt
      3'b101: taken = ($signed(a_reg) >= $signed(b_reg));  // bge
      3'b110: taken = (a_reg <  b_reg);                    // bltu
      3'b111: taken = (a_reg >= b_reg);                    // bgeu
      default: taken = 1'b0;
    endcase
    taken  = (id_ex.is_branch && taken) || id_ex.is_jal || id_ex.is_jalr;
    target = id_ex.is_jalr ? ((a_reg + id_ex.imm) & ~32'd1) : (id_ex.pc + id_ex.imm);
    actual_npc = taken ? target : id_ex.pc + 4;
  end
  assign flush       = id_ex.valid && (actual_npc != id_ex.pred_npc);   // the guess was wrong
  assign redirect_pc = actual_npc;

  always_ff @(posedge clk) begin
    if (rst) ex_mem.valid <= 1'b0;
    else begin
      ex_mem.valid      <= id_ex.valid;
      ex_mem.pc         <= id_ex.pc;
      ex_mem.result     <= (id_ex.is_jal || id_ex.is_jalr) ? id_ex.pc + 4 :   // link address
                           id_ex.is_lui ? id_ex.imm : y;
      ex_mem.store_data <= b_reg;
      ex_mem.rd         <= id_ex.rd;
      ex_mem.we         <= id_ex.we;
      ex_mem.is_load    <= id_ex.is_load;
      ex_mem.is_store   <= id_ex.is_store;
      ex_mem.funct3     <= id_ex.funct3;
    end
  end
endmodule

Hidden concepts

Priority order matters

If two earlier instructions write the same register, the nearer one is newer. Reversing the priority fails only 2 of 10 directed tests and 5 of 100 random programs, an easy bug to miss without targeted tests (p02_forwarding writes x5 three times in a row on purpose).

jalr clears bit 0

The spec says the target is (rs1 + imm) with the lowest bit cleared.

8

Memory access and writeback

beyond Part 6 · bytes · little-endian

Wrapping and handing over. A load reads from the store-room; a store puts something in it. Some orders want only one byte or half a word, so the worker picks the right part of the box and fills the rest with the sign (lb, lh) or with zeros (lbu, lhu).

Data memory is word-addressed internally. The byte offset addr[1:0] shifts the wanted byte or half down to bit 0 for loads, and selects the byte lanes for stores. Writeback is just the register file's write port fed from MEM/WB.

The code

module pq5_mem import pq5_pkg::*; #(parameter int DMEM_WORDS = 1024) (
  input  logic    clk, rst,
  input  ex_mem_t ex_mem,
  output mem_wb_t mem_wb
);
  logic [31:0] dmem [DMEM_WORDS];
  wire  [$clog2(DMEM_WORDS)-1:0] wi = ex_mem.result[$clog2(DMEM_WORDS)+1:2];
  wire  [1:0]  off  = ex_mem.result[1:0];
  wire  [31:0] word = dmem[wi];
  wire  [31:0] sh   = word >> (8 * off);               // bring the wanted byte/half to bit 0
  logic [31:0] load_val;
  always_comb begin
    case (ex_mem.funct3)
      3'b000:  load_val = {{24{sh[7]}},  sh[7:0]};       // lb
      3'b001:  load_val = {{16{sh[15]}}, sh[15:0]};      // lh
      3'b100:  load_val = {24'b0, sh[7:0]};              // lbu
      3'b101:  load_val = {16'b0, sh[15:0]};             // lhu
      default: load_val = word;                          // lw
    endcase
  end
  always_ff @(posedge clk) begin
    if (rst) mem_wb.valid <= 1'b0;
    else begin
      if (ex_mem.valid && ex_mem.is_store) begin
        case (ex_mem.funct3[1:0])
          2'b00:   dmem[wi][8*off +: 8]  <= ex_mem.store_data[7:0];       // sb
          2'b01:   dmem[wi][8*off +: 16] <= ex_mem.store_data[15:0];      // sh (aligned)
          default: dmem[wi]              <= ex_mem.store_data;            // sw
        endcase
      end
      mem_wb.valid <= ex_mem.valid;
      mem_wb.pc    <= ex_mem.pc;
      mem_wb.rd    <= ex_mem.rd;
      mem_wb.we    <= ex_mem.we;
      mem_wb.wdata <= ex_mem.is_load ? load_val : ex_mem.result;
    end
  end
endmodule

Hidden concepts

Stores write in MEM, not WB

pq5 has no exceptions, so a store in MEM is certain to complete. In a CPU with precise exceptions, a store must not write memory before every older instruction is known to be safe. That is why your OOO core keeps stores in a store queue until commit.

9

Verify the whole CPU

beyond Part 6 · ISS · random · assertions · mutations

How do you know the sandwich shop works? You don't taste one sandwich. You compare every order handed out with what a very slow, very careful single worker (the golden model) would have made from the same orders, and you send in a thousand random customers.

Golden model

tools/rv32i.py runs the program one instruction at a time. run_pq5.py compares every retired instruction (PC, register, value), the final registers and memory.

Directed programs

10 small real programs: every ALU op, forwarding distances 1-3, load-use, loop sum 1..100 (5050), if/else, nested function calls with a stack, bubble sort, byte/half access, shift-and-add multiply (123×45, 6!), Fibonacci. All pass.

Constrained random

gen_rand.py builds hazard-dense programs (6 registers, 8 memory words, loops, forward branches, jalr) that always reach halt. 500 of 500 pass.

Assertions

x0 is never written; IF/ID never changes during a stall; stall and flush never coincide; a load's result is never needed one stage too early.

Two things the mutation table taught me

A surviving mutant is a question

Letting forwarding pass a load's address as if it were data changes nothing in 110 tests. Not a test hole: the load-use interlock guarantees no instruction ever needs a load's result one stage later, so that guard is redundant. I proved it with an assertion (a_loaduse) instead of assuming.

Random has blind spots

The first random generator never used x0 as a destination, so "x0 can be written" escaped all 100 random programs (directed tests caught it). After adding x0 destinations, random catches it in 54 of 100. Always ask what your stimulus can't produce.

Build it yourself next

  1. Move branch resolution to decode (compare + forwarding into ID). Re-measure: the flush penalty should drop from 2 to 1.
  2. Add a 2-bit dynamic predictor (a small table indexed by PC). Compare CPI on p07_bubble_sort and p09_multiply.
  3. Make memory slower: give instruction memory a 1-cycle latency with a valid/ready handshake, like Pequeno's fetch interface. What has to change in fetch?
  4. Add the M extension (mul) as a multi-cycle unit. What does the pipeline do while it waits? This is where out-of-order execution starts to pay off.

Interview questions

Design a hazard unit for a 5-stage pipeline. What inputs does it need?

Source registers and 'uses' flags of the instruction in ID; destination, write-enable and 'is load' of the instructions in EX and MEM; the branch outcome from EX. Outputs: stall IF+ID with a bubble into EX on load-use; flush IF/ID+ID/EX on mispredict; forwarding selects for each ALU operand.

How would you verify forwarding completely?

Enumerate the producer kinds (ALU, load, jal link, lui) × distance (1, 2, 3, 4+) × operand (rs1, rs2, store data, branch compare, jalr base) × same-register-twice priority. Write directed tests for each cell, measure functional coverage of that matrix in random runs, and keep a golden-model comparison at commit.

Why is the load-use penalty 1 cycle and not 2?

The load's data exists at the end of MEM, and the dependent instruction needs it at the start of its EX. One bubble lines those up, and the value is forwarded from MEM/WB.

Next: let instructions overtake

pq5 waits whenever an instruction can't go. An out-of-order CPU lets independent instructions go ahead and puts the results back in order at the end. Levels 7 to 11 of CPU From Zero build that step by step, and the Tomasulo Core Lab takes your 3-wide core apart.
