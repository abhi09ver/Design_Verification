Out-of-Order Transactions & IDs

How AXI lets fast responses overtake slow ones — and the single rule that keeps it safe.
Same ID → in issue order
Different ID → any order

1What & why

  • Out-of-order (OoO): responses come back in a different order than the requests were issued.
  • Possible because AXI has multiple outstanding transactions and tags each with an ID.
  • Why it matters: slaves have very different latencies — an SRAM answers in 2 cycles, DDR in 50+. In-order would make every fast access wait behind the slow one (head-of-line blocking).
  • DDR controllers also reorder internally (open-row hits first), so they need OoO to be efficient.
One-liner: IDs let the system return each response as soon as it's ready, while preserving order only where the master needs it.

2The ordering rules

#Rule
1Same ID, same direction → responses must return in the order the addresses were issued.
2Different IDs → no ordering requirement; may complete in any order.
3Read data may interleave between different RIDs; beats within one burst stay in order.
4Write responses (B) may return OoO for different BIDs.
5AXI4 write data must follow AW order — no interleaving (AXI3 allowed it via WID).
6No ordering between reads and writes, even with the same ID. Need it? Wait for the response first.
A master that always uses one ID gets fully in-order behaviour for free. Using several IDs is an opt-in to OoO.

4What the interconnect does with IDs

Master 0ARID = 3'b101
Master 1ARID = 3'b101
▶
Interconnectprepends port number
M0 → 0_101 · M1 → 1_101
▶
Slavesees 4-bit unique IDs
  • ID widening: slave-side ID = master-side ID + log2(#masters) bits. Two masters can reuse the same ID without clashing.
  • Response routing: the extra bits on RID/BID tell the interconnect which master to send the response to; it strips them on the way back.
  • Same ID to two different slaves: the slaves can't coordinate, so the interconnect must stall the 2nd request until the 1st completes (or reorder responses itself). This is the "single-slave per ID" rule many fabrics use.
Interview favourite: "Master sends ID0 to slave X, then ID0 to slave Y. Y is faster — what happens?" → interconnect blocks or buffers so X's response still reaches the master first.

Parameters to know for any DUT
  • ID width — how many distinct streams a master can use.
  • Read / write acceptance capability — max outstanding transactions a slave accepts.
  • Issuing capability — max outstanding a master will issue.
  • Read data reordering depth — how many different IDs a slave may reorder between.
  • Read interleaving depth — how many bursts can be active on R at once (1 = no interleave).
Reordering depth 1 = slave is in-order. Always legal, just slower.

✓Verifying OoO — per-ID scoreboard

class axi_rd_sb extends uvm_scoreboard;
  // one FIFO of expected transactions per ID
  axi_txn exp_q[bit [ID_W-1:0]][$];

  function void write_ar(axi_txn t);   // from AR monitor
    exp_q[t.id].push_back(t);
  endfunction

  function void write_r(axi_txn t);    // full burst from R monitor
    axi_txn e;
    if (!exp_q.exists(t.id) || exp_q[t.id].size() == 0)
      `uvm_error("SB", $sformatf("RID %0h not outstanding", t.id))
    else begin
      e = exp_q[t.id].pop_front();     // oldest of SAME ID
      if (!t.data_match(e)) `uvm_error("SB", "data mismatch")
    end
  endfunction
endclass
Popping the front of the same-ID queue enforces rule 1; using a queue per ID permits rule 2 automatically.
Checks & coverage
  • RID/BID always matches an outstanding ID; no response for an ID with an empty queue.
  • Monitor collects R beats per RID so interleaved bursts rebuild correctly.
  • Cover: OoO actually happened (completion order ≠ issue order), same-ID back-to-back, max outstanding, interleaved R, all ID values.
  • Slave VIP knob: random response reordering + random interleaving.

?Out-of-order interview Q&A

QuestionCrisp answer
What enables OoO in AXI?Multiple outstanding transactions + ID tags.
What is the ordering rule?Same ID in order; different IDs any order.
Can beats inside one burst reorder?No — only whole transactions with different IDs.
Can read data interleave?Yes, across different RIDs.
Can write data interleave in AXI4?No — WID removed; W follows AW order.
Is a write ordered with a later read of the same ID?No — wait for BRESP before issuing the read.
How does the response find its master?Interconnect-added ID bits route it back.
Same ID to two slaves — risk?Order violation; interconnect must stall or reorder.
Benefit of OoO?Removes head-of-line blocking; better throughput and latency.
Cost of OoO?ID tracking and reorder buffers in master/interconnect.
How do you test it?Per-ID queue scoreboard, reordering slave VIP, coverage on completion order.
