0.3Legality explorer: the one equation that drives half the testbench

The datasheet says a transfer is legal when (ALGN_DATA_WIDTH/8 + offset) % size == 0. Pick a bus width and click any cell. Watch the amber cells: they pass the datasheet equation but would put bytes past the end of the bus.

Real finding in your code · spec vs RTL vs TB

Three places implement the rule, and they don't agree:

cfs_regs.v (CTRL write) checks size≠0, the modulo rule and offset + size > W/8. cfs_rx_ctrl.v (MD RX) checks only size≠0 and the modulo rule. cfs_algn_model.sv checks all three for RX. So for size 3 at offset 2 on a 32-bit bus, the RTL would accept the RX item while the model expects ERR.

It never shows up as a failure because the TB can't generate it: cfs_md_sequence_simple_master::item_hard constrains size + offset <= W/8, the master driver uvm_fatals on it, and the coverage ignore_bins it. That's a classic hidden hole: constraints written from the TB writer's reading of the spec, not from the spec. In an interview, this is the kind of observation that marks you as senior.

0.4Spec review: questions you'd raise with the designer before writing a line

Ambiguity · IRQ output

§4.4 says the interrupt "is generated as a pulse (1 for one clock)", but Figure 11 ANDs the sticky IRQ bits with IRQEN. Is irq a level (stays high until W1C) or a one-cycle pulse? Your model and scoreboard need one answer.

Unspecified priority

CTRL.CLR written in the same cycle an illegal RX transfer arrives: does CNT_DROP end at 0 or 1? Same question for W1C on IRQ in the same cycle as a new event.

Missing rule

The overflow condition offset + size ≤ W/8 is enforced by the RTL CTRL write but never stated in the datasheet. Ask for a spec update rather than inferring it.

Edge vs level

"RX FIFO became full" is an edge: after W1C while still full, the bit must stay 0. A model that sets bits on level fails here. Easy to miss, often asked.

Doc defects

Figure 10 text says CTRL.SIZE = 11 (caption says 1). pslverr width is blank. Status/IRQ tables are titled "fields of the Control register". Small, but list them; reviewers notice.

Reset during traffic

Nothing says what happens to in-flight MD transfers or a half-done APB access on reset. Your TB needs a defined behaviour to check against.

0.5Interview drill

Q1"Here's the aligner datasheet. You have 10 minutes. How would you verify it?"+

Strong answer shape
Start from the plan, not the tools. (1) Interfaces: APB slave, MD RX (DUT is the slave), MD TX (DUT is the master), irq. That gives one APB agent, one MD master agent, one MD reactive slave agent. (2) Behaviour splits into a transform (alignment), rules (legality, APB errors, protocol) and state (FIFO levels, counters, IRQs). (3) Transforms go to a reference model plus a scoreboard. Rules go to SVA and the register predictor. State goes to the RAL mirror. (4) Coverage on the config × traffic cross. (5) Tests: register access, random legal, all-illegal, back-pressure, IRQ, reset-mid-traffic.

Cross-questions they'll push
  • Why is the TX agent reactive instead of just driving ready=1? (You need back-pressure to fill the FIFOs and to hit full/empty IRQs.)
  • Would you use formal for any of this? (Yes: the legality rule and the APB error conditions are small, closed-form properties. Formal proves all (offset, size) combos in minutes.)
  • What's the riskiest feature? (IRQ edge semantics and CNT_DROP/CLR races. These are timing interactions that a random test rarely hits by chance.)
Q2"Your constraints only generate legal-by-construction traffic. Is that a problem?"+

Yes, if the constraint is narrower than the spec. Your constraints define what the DUT is never asked to handle. Here, item_hard removes the overflow cells, so the RTL's missing overflow check in cfs_rx_ctrl.v can't be found. A senior engineer keeps constraints that model physical limits (here the bus cannot carry byte 4) apart from constraints that model legality. Legality belongs in the checker, and illegal stimulus gets its own test, as you did with rx_err.

Cross-question
  • Then how would you drive size 3 at offset 2 if the driver fatals? (Override the driver check behind a config knob, or decide with the designer that it's a protocol violation and cover it with an assertion on the DUT input.)

  1. Explicit prediction. The mirror is updated from what the APB monitor saw, not from what the register API asked for. That way it also tracks accesses you didn't start through RAL.
  2. Same adapter both ways. reg2bus for the sequencer path, bus2reg for the predictor. One bug in the adapter breaks both, and that's a common interview trap.

  6. Parameter firewall. The agent is #(32), but the vseqr stores the unparameterized base. Sequences then compile once, independent of bus width.

1.5Hidden concepts in this architecture

config_db paths are strings

run_test("") always names the test uvm_test_top, which is why testbench.sv hard-codes "uvm_test_top.env.apb_agent". A typo isn't a compile error. You only find it at the get(), which is why every agent should `uvm_fatal("NO_VIF", …) on a failed get.

Monitors feed checkers, not drivers

Expected values come from what the monitor observed, never from what the sequence intended. If the driver had a bug, intent-based checking would hide it. That's also why the model works in a passive env at SoC level.

Model ≠ scoreboard

The model predicts and the scoreboard compares. Keeping them separate lets you swap the model (C/DPI golden model, or a different config) without touching compare logic, and reuse the scoreboard for other DUTs.

Reset is a first-class event

The env's run_phase loops on reset and calls handle_reset() on model, scoreboard and coverage through an interface class (uvm_ext_reset_handler). That's SystemVerilog's way to give unrelated classes a shared API without multiple inheritance.

White-box probes trade portability

algn_if.rx_fifo_push = dut.core.rx_fifo.push_valid & … gives the model exact FIFO timing for IRQ checks, but ties the TB to RTL hierarchy. A renamed instance or a gate-level netlist breaks it. Know when to say "I'd use bind instead".

Errored writes must not update the mirror

The custom predictor checks the APB status first and only calls super.write() on UVM_IS_OK. A stock predictor would mirror an illegal CTRL write, and every later alignment prediction would be wrong.

Build order inside one build_phase

The env sets the md_tx agent's config before create("md_tx_agent"). Strictly it only has to be set before the agent's own build_phase runs, which happens later (top-down), but setting first reads correctly and survives refactors.

Optional components

Coverage is created only if has_coverage, and connect_phase null-checks it. Regressions turn coverage off for speed, and the env must still elaborate cleanly.

1.6Bug hunt: symptom → root cause

Each is a one-line change in your env. Guess the root cause first, then reveal. Better still, inject it on EDA Playground and read the log.

BUG 1After a CTRL write of SIZE=2, scoreboard reports TX size mismatches: expected 1, got 2. Meanwhile the unmapped-access test, which should check APB errors, passes with no checks at all.+

Root cause: apb_agent.monitor.output_port.connect(predictor.bus_in) removed. The mirror never sees the write, so the model aligns with the reset value SIZE=1. Worse, the predictor's write() is never called, so every pslverr check it does silently disappears. A missing connection produces both a false failure and a false pass.

Lesson: when the model disagrees with the DUT, check the model's inputs (mirror, ports) before you blame the RTL.

BUG 2Test fails at time 0 with NO_VIF fatal from md_rx_agent, but the interface is clearly instantiated.+

Root cause: path string mismatch, e.g. "uvm_test_top.env.md_rx_agnt", or the agent renamed in create(). Debug with +UVM_CONFIG_DB_TRACE, which prints every set/get and the path it matched or missed.

BUG 3A test with a mid-sim reset ends with "N expected items never received" from the scoreboard.+

Root cause: scoreboard.handle_reset() not called, or it doesn't flush its expected queues. Items predicted before the reset are still waiting, and the DUT flushed its FIFOs. The model's uvm_tlm_fifos need flushing too.

BUG 4Your cfs_algn_test_random_rx_err runs, but the log shows legal transfers with CFS_MD_OKAY.+

Root cause candidates: (a) the override is registered after the sequence was already created; (b) the sequence was built with new() instead of type_id::create(), which bypasses the factory; (c) the override names the wrong type, e.g. the parameterized vs base class. Check with factory.print() in end_of_elaboration_phase.

BUG 5Regression is 100% green, coverage is 100%, yet a silicon bug: the DUT drops the last TX chunk when RX traffic stops.+

Root cause: the scoreboard compares what arrives but never checks for missing items at end of test. Add a check_phase that errors when the expected queue isn't empty, plus a drain time before dropping the objection. Also note the coverage model covered inputs, not "all predicted outputs were seen".

Q1"Draw your testbench and walk me through it."+

Cross-questions
  • Why is the scoreboard not just inside the model?
  • What changes if this env is reused at SoC level where the CPU drives APB? (APB agent goes passive, the predictor still works because it's monitor-driven, and the white-box algn_if probes need a bind or must go.)
  • Where would a C++ golden model plug in? (Behind the model's write_in_rx via DPI-C. Ports and scoreboard stay unchanged.)
Q2"Analysis port vs TLM FIFO vs uvm_tlm_analysis_fifo: when do you use each here?"+

Analysis port: monitor broadcast, non-blocking, zero-time, any number of subscribers. uvm_tlm_fifo: inside the model, to buffer items and let a separate thread consume them with blocking get(), which is how the model mimics the DUT's FIFOs and back-pressure. uvm_tlm_analysis_fifo: when a subscriber must do time-consuming work per item, because it decouples write() from processing.

Cross-question
  • What happens if a subscriber's write() calls a task? (Compile error, since write is a function. If someone forks inside it, ordering between items is lost.)
Q3"How does your environment handle reset in the middle of traffic?"+

The env's run_phase runs forever: wait reset assert → handle_reset() on every stateful component (model flushes FIFOs and resets the mirror, scoreboard clears queues, coverage resets sampling state) → wait deassert. Agents do the same internally: drivers stop and release the bus, sequencers drop pending items, monitors abandon a half-captured item. Tests must also tolerate killed sequences.

Cross-questions
  • Why not use UVM's reset/configure/main phases? (Runtime sub-phases are fragile with multiple resets and with VIP from different vendors. Most teams use an event-driven reset like this one.)
  • How do you test it? (A test that asserts reset at random points with FIFOs non-empty, then checks registers equal reset values and traffic resumes cleanly.)

2.1One MD handshake, with the assertions that guard it

Transfer A waits 3 cycles for ready. Transfer B is illegal (size 2 at offset 1) and gets err in its single cycle. Shaded amber is where the stability assertions are active. Red dashes mark the cycles where the other assertions evaluate.

Every value in a concurrent assertion is the value sampled just before the clock edge (the Preponed region). That's why $past(ready) means "ready in the previous cycle", and why NBA-driven signals never race with the assertion.

2.2Code walkthrough: cfs_md_if.sv

property valid_high_until_ready_p;
  @(posedge clk) disable iff(!reset_n || !has_checks)
  $fell(valid) |-> $past(ready) == 1;
endproperty
VALID_HIGH_UNTIL_READY_A : assert property(valid_high_until_ready_p);

property stable_data_until_ready_p;
  @(posedge clk) disable iff(!reset_n || !has_checks)
  valid & $past(valid) & !$past(ready) |-> $stable(data) == 1;
endproperty

property err_high_at_valid_and_ready_p;
  @(posedge clk) disable iff(!reset_n || !has_checks)
  err |-> valid & ready;
endproperty

//elaboration-time parameter check (not an assertion)
if($log10(DATA_WIDTH)/$log10(2) - $clog2(DATA_WIDTH) != 0)
  $error("DATA_WIDTH is not a power of two ...");
  1. disable iff with two terms. Reset kills any in-flight attempt. has_checks lets an error-injection test switch the rules off without editing the interface.
  2. Read it backwards. "If valid just fell, ready must have been high last cycle." That's the same rule as "valid holds until ready", written so it only evaluates at the moment of a violation.
  3. Stability needs history. $past(valid) & !$past(ready) says "we're still inside the same transfer". Without it, a new back-to-back transfer with different data would falsely fire.
  4. Implication direction matters. err |-> valid & ready forbids err outside a handshake. Writing valid & ready |-> err would demand an error on every transfer.
  5. Elaboration-time checks (a generate if with $error) catch bad parameters before time 0. They're free, and catch the "someone built it with width 24" mistake.

2.3Hidden concepts

has_checks is policed

The agent config writes vif.has_checks, and its run_phase watches the signal. If someone flips it directly in the interface, it raises ALGORITHM_ISSUE. One source of truth for a knob that two worlds (class and module) can touch.

No clocking blocks, still race-free

Drivers use NBAs (vif.valid <= 1) and read right after @(posedge clk), before that edge's NBAs land, so they see the pre-edge value. It works, but it's convention-based. A clocking block makes the same timing explicit and harder to break. Expect "what's a clocking block for?" in interviews.

The monitor's 1 ns skew

The MD monitor waits sample_delay_start_tr = 1ns after the edge before testing valid. That's a hand-written input skew, the thing a clocking block's input #1 would give you.

$isunknown guards

Half the assertions are X-checks, gated by valid or psel. X on data while valid is a real RTL bug (uninitialised flop). X on data while idle is legal, so the gating is the skill.

Interfaces travel; monitors don't

At SoC level your agents may be gone, but the interface (or a bind-ed checker) keeps checking. Protocol rules belong in SVA. Data and ordering rules belong in the scoreboard.

APB phases as sequences

setup_phase_s is a named sequence reused by three properties. Building small named sequences is how you keep a 30-assertion file readable and reviewable.

2.4Findings in your interfaces

Missing rule · APB ≤ 5 wait states

The datasheet (§4.3) says more than 5 wait states is illegal. No assertion checks it. The only guard is the monitor's stuck_threshold of 1000 cycles. A DUT taking 6 wait states passes every test today.

TB-only rule in a protocol file

SIZE_PLUS_OFFSET_GT_DATA_WIDTH_A enforces size + offset ≤ W/8, the rule that isn't in the datasheet (Module 0). Applied to md_tx_if it checks the DUT. Applied to md_rx_if it forbids stimulus the RTL would accept. Know which side each assertion is policing.

No cover properties

Every rule is an assert and none is a cover. You can't prove the 3-wait-state case or err-on-first-cycle ever happened. Assertion coverage is half of protocol sign-off.

2.5Bug hunt

BUG 1You rewrite the stability check as valid & !ready |=> $stable(data). Back-to-back legal transfers now pass, but a DUT bug where data changes in the same cycle ready rises is missed.+

Root cause: |=> checks the next cycle and only while ready is low now. The original form looks at the previous cycle's handshake state, so it covers every cycle up to and including the accept cycle. Draw the waveform before choosing |-> vs |=>.

BUG 2Your error-injection test sets vif.has_checks = 0 from the test to drive illegal traffic, and gets an ALGORITHM_ISSUE error.+

Root cause: the agent config owns the knob. Call agent_config.set_has_checks(0), which updates both the class flag and the interface. Interviewers like this one: "who owns a knob that lives in two places?"

BUG 3A reset in the middle of a transfer fires VALID_HIGH_UNTIL_READY_A.+

Root cause: it would, without disable iff(!reset_n). Valid legally drops during reset. The disable iff is evaluated asynchronously, so it also aborts attempts that started before reset. Remove it and see the false failure.

2.6Interview drill

Q1"What's the difference between |-> and |=>, and when does $past beat both?"+

|-> checks the consequent in the same cycle the antecedent matches; |=> checks it one cycle later. $past lets you trigger on the effect (valid fell) and check the cause (ready last cycle), so the assertion only does work at violation points. It's cheaper and its failure message points at the exact cycle.

Cross-questions
  • What does $past return at the first clock after reset? (The initial value. Guard with reset or disable iff.)
  • Why are sampled values taken in Preponed? (So the assertion sees a stable, race-free snapshot regardless of process ordering at the edge.)
Q2"Assertions in the interface, in a bind-ed checker, or in the monitor: which and why?"+

Pure signal-level protocol goes in the interface or a bound checker: zero-time, reusable at SoC level, and formal-friendly. bind wins when you can't edit the interface, or need to reach internal RTL signals. The monitor (procedural checks) is for things needing transaction context, like the stuck-transfer threshold. Data correctness goes to the scoreboard, never SVA.

Cross-question
  • How would you formally prove the legality rule? (Assume the APB and MD protocols as constraints, assert md_rx_err == !legal(offset,size) at handshake. With 4×8 input combos, it converges in seconds.)
Q3"Why does your TB work without clocking blocks? Would you add them?"+

Drivers write with NBAs and sample right after the edge, which reads pre-edge values. The monitor adds a 1 ns skew. That's correct but fragile: a blocking assignment or a #0 somewhere breaks it. Clocking blocks encode input/output skew in one place and make the synchronisation contract explicit. I'd add them in a production VIP, and keep this pattern only for teaching.

3.1Two layers: generic engine, protocol plug-ins

3.2Driver and monitor, side by side

// cfs_apb_driver::drive_transaction
for(int i = 0; i < item.pre_drive_delay; i++)
  @(posedge vif.pclk);

vif.psel   <= 1;                    // SETUP phase
vif.pwrite <= bit'(item.dir);
vif.paddr  <= item.addr;
if(item.dir == CFS_APB_WRITE) vif.pwdata <= item.data;
@(posedge vif.pclk);
vif.penable <= 1;                   // ACCESS phase
@(posedge vif.pclk);
while(vif.pready !== 1)             // wait states
  @(posedge vif.pclk);
vif.psel <= 0; vif.penable <= 0;    // back to IDLE

// cfs_apb_monitor::collect_transaction
while(vif.psel !== 1) begin
  @(posedge vif.pclk); item.prev_item_delay++;
end
item.addr = vif.paddr;  item.dir = cfs_apb_dir'(vif.pwrite);
@(posedge vif.pclk); item.length++;
while(vif.pready !== 1) begin
  @(posedge vif.pclk); item.length++;
  if(item.length >= agent_config.get_stuck_threshold())
    `uvm_error("PROTOCOL_ERROR", "stuck")
end
item.response = cfs_apb_response'(vif.pslverr);
if(item.dir == CFS_APB_READ) item.data = vif.prdata;
output_port.write(item);
  1. Delays live in the item. pre_drive_delay/post_drive_delay are random fields with soft ≤5 limits, so a test can stretch idle gaps with one inline constraint and no driver change.
  2. NBA everywhere. Every pin write is <=. Mixing in one blocking write creates a race with the DUT's flops at the same edge.
  3. !== 1, not != 1. With X on pready, != 1 evaluates to X (treated false), so the loop exits on an unknown. !== keeps waiting, and the X assertion reports it.
  4. The monitor is independent of the driver. It rebuilds the transfer from pins alone, which is why it works in passive mode and why it catches driver bugs.
  5. The monitor measures, it doesn't judge. length and prev_item_delay are recorded for coverage. The only check it makes is the stuck threshold.
  6. Response data sampled at completion. prdata/pslverr are only valid in the cycle pready is high. Sampling them earlier is the classic monitor bug (Bug 2).

3.3Hidden concepts

Agent config is a component

uvm_ext_agent_config extends uvm_component, not uvm_object. That gives it phases, so it can run the has_checks watchdog and host wait_reset_start/end. The cost is that it appears in the topology and can't be created freely at run time.

Reset by killing processes

The driver saves process::self() and kill()s it in handle_reset(), then pins go to idle. The sequencer calls stop_sequences() and drops stray objections. Without both halves you get "get_next_item called twice without item_done".

vif arrives in connect, used after end_of_elab

The base agent fetches the vif in connect_phase and set_vif fatals if it's set twice. Subclasses $cast the config in end_of_elaboration_phase. Each phase has one job, and errors surface before time 0.

Active vs passive is one if

Passive mode skips creating the driver and sequencer. Monitor and coverage always exist. At SoC level the same agent becomes a pure observer, and the predictor, model and scoreboard keep working.

Per-bit coverage wrappers

uvm_ext_cover_index_wrapper samples "bit i was 0" and "bit i was 1" for every address and data bit, i.e. toggle coverage at transaction level. It proves every address line and data lane moved.

The driver never returns a response

There's no put_response, so frontdoor RAL calls always return UVM_IS_OK. Bus errors are judged only by the predictor (Module 5). That's a design choice worth defending, or criticising, in an interview.

3.5Interview drill

Q1"Walk me through what's inside a UVM agent and what changes in passive mode."+

One object, two meanings

Response is unconstrained

Back-pressure is a test knob

Parameter firewall again

5.3Hidden concepts

Desired · mirrored · actual

Desired is what you intend (set by set()/randomize()). Mirrored is what the TB believes the DUT holds. Actual is in the RTL. update() writes only where desired ≠ mirrored. A read with check_on_read compares actual vs mirrored, and that's how STATUS gets checked for free.

The mirror is the model's state

The model never keeps its own CNT_DROP or FIFO levels. It calls STATUS.CNT_DROP.predict(n+1). Every later STATUS read then checks the model's prediction against the DUT. One state store, two uses.

check_on_read is on

default_map.set_check_on_read(1) makes every frontdoor read compare against the mirror. Turn it off and STATUS bugs become invisible, with no other change in the log.

Frontdoor status is always OK

The APB driver returns no response, so CTRL.write(status, …) reports UVM_IS_OK even when the DUT said pslverr. Never branch test logic on that status here. The predictor is the judge.

void'(randomize()) in reg2bus

If the inline constraints ever conflict, randomization fails silently and a random APB item goes out. Use if(!item.randomize() with {…}) `uvm_fatal(…). That's a one-line review comment that marks you as careful.

lock_model() before use

Locking builds the address lookup tables. Skip it and get_reg_by_offset returns null, so the predictor would call every access "unmapped".

5.4Finding: the RAL is not parameterized

Real finding · breaks at ALGN_DATA_WIDTH = 64

The RTL computes field widths: ALGN_SIZE_WIDTH = $clog2(W/8)+1 and ALGN_OFFSET_WIDTH = $clog2(W/8). At W=64 that's SIZE 4 bits and OFFSET 3 bits. cfs_algn_reg_ctrl hard-codes .size(3) and .size(2), so at 64 bits the mirror can't hold SIZE=8 or OFFSET≥4. The functional coverage bins are also fixed to [0:3]/[1:4]. Changing `CFS_ALGN_TEST_ALGN_DATA_WIDTH compiles but verifies the wrong thing.

Also: ALGN_DATA_WIDTH inside the register defaults to 8 until the model's end_of_elaboration_phase sets it. Randomize CTRL any earlier and you only get width-8 legal values.

5.6Interview drill

Q1"Explain implicit, explicit and passive prediction. Which do you use and why?"+

Implicit (auto-predict) updates the mirror from the register call itself. It's simple, but blind to accesses not made through RAL and to bus errors. Explicit: a predictor fed by the bus monitor updates the mirror from observed transfers, so it catches everything on the bus. Passive is the same predictor with no RAL-driven traffic, i.e. SoC level. This env uses explicit prediction with a custom predictor that also checks the response and skips errored accesses.

Cross-questions
  • What's mirror() vs read()? (mirror(UVM_CHECK) reads and compares against the mirror. read() returns the value and, with check_on_read, also compares.)
  • Backdoor access: when is it dangerous? (It bypasses the bus, so you skip protocol and side effects like W1C, read-clear and CLR.)
  • How do you handle a volatile field? (Mark it volatile and update via predict from a model, or exclude it from compare with set_compare(UVM_NO_CHECK).)
Q2"How would you verify a sticky W1C interrupt register?"+

Model sets the bit on the triggering event (edge, not level) via predict(1). W1C policy clears the mirror on write-1. Reads compare via check_on_read. Coverage: set → read → clear while condition persists → confirm it stays 0 → re-trigger → confirm set. Plus the same-cycle race: clear and set in the same cycle. Ask the designer which wins and code the model to match.

protected virtual function void set_rx_fifo_full();
  fork begin
    process_set_rx_fifo_full = process::self();
    repeat(2) begin
      uvm_wait_for_nba_region();
    end

      exp_irq = 1;
  end join_none
endfunction

// ...and cancel it if a pop happens in the same time step

    uvm_wait_for_nba_region();
    kill_process(process_set_rx_fifo_full);
  end join_none

// borrow timing from the RTL, with a safety net
fork
  @(posedge vif.clk iff(vif.rx_fifo_push));
  begin
    repeat(10) @(posedge vif.clk iff(RX_LVL < rx_fifo.size()));
    `uvm_warning("DUT_WARNING",
                 "RX FIFO push did NOT synchronize with RTL")
  end

disable fork;
  1. Same-timestep ordering. Push and pop can happen at the same edge in different threads. Waiting two NBA regions lets every thread at that time step finish before the "became full" verdict is taken.
  2. Cancel by kill. If a pop arrives in the same step, the pending "set full" process is killed. The FIFO was never observably full, so there's no IRQ. That's the "became" (edge) semantics from Module 0, done in a TLM model.
  3. Borrowed timing. The model waits for the DUT's own push strobe to decide when it happened, so cycle-level IRQ timing lines up without a cycle-accurate model. The fallback branch prevents a hang if the DUT never pushes.

6.4Hidden concepts and findings

Finding · a DUT bug becomes a warning

If the RTL never pushes, the sync fallback only prints DUT_WARNING and the model carries on as if it had. A stuck RX FIFO shows up later, and indirectly, as a TX watchdog error, or not at all if the test ends first. Rule: grep DUT_WARNING in every regression, or promote it to an error.

Finding · hard-coded FIFO depth

rx_fifo = new("rx_fifo", this, 8). FIFO_DEPTH is a DUT parameter (§2), but the TB copies the default. Build the DUT with depth 16 and the model predicts FIFO-full IRQs at 8.

Predict at start, compare at end

The model reacts to the start of the RX transfer (is_active()) because the DUT decides err in that same cycle. The scoreboard compares at the end. The model is never later than the DUT.

Every thread has a handle

Each forked loop stores process::self(), and handle_reset() kills them all, flushes the FIFOs, resets the reg block and restarts the threads. Forgetting one handle means a zombie thread from before reset keeps producing expectations.

Transaction-level, cycle-aware

No clocks inside the algorithm, only around it (probe syncs, negedge irq). That's the usual compromise: easier to write than cycle-accurate, tighter than pure TLM. Be ready to defend it.

Reconfig mid-traffic is untested

align() re-reads CTRL every loop. A CTRL write while bytes sit in the buffer changes the rule half-way through a TX word. The spec is silent, and cfs_algn_test_random avoids it with if(model.is_empty()). Ask the designer.

6.5Interview drill

Q1"Cycle-accurate or transaction-level reference model?"+

Transaction-level for data (what bytes, in what order), plus cycle-awareness only where the spec defines timing (here: IRQ pulses and FIFO levels visible through STATUS). Cycle-accurate models duplicate the RTL's micro-architecture, so they get the same bugs and break on every pipeline change. When timing is loosely specified, check windows (watchdogs) rather than exact cycles.

Cross-questions
  • Is using DUT probes for timing cheating? (It's a trade-off. The data is still predicted independently, but a probe bug or RTL rename silently desynchronises the model. Keep the fallback and make its warning an error.)
  • How would you plug in a C model? (DPI-C call inside align() taking the byte stream and CTRL and returning TX words; keep the SV threads for timing.)
Q2"Push and pop hit a full FIFO in the same cycle. Is a FIFO_FULL interrupt raised?"+

It depends on the definition of "became full". If it means the level register reached MAX at a clock edge, then simultaneous push+pop at MAX−1 never reaches MAX: no interrupt. The model enforces it by deferring the decision with uvm_wait_for_nba_region() and cancelling on a same-step pop. The senior part of the answer is naming the ambiguity and getting the spec to state it.

7.3Findings in your scoreboard

No end-of-test check

There's no check_phase. If the test drops its objection within 10 cycles of a prediction, the watchdog thread dies with the run phase and a missing item is never reported. Today's tests happen to wait long enough (100 clocks + 500 ns), but nothing enforces it.

Unexpected item = crash, not error

If the DUT emits a TX item nobody predicted, exp_tx_items.pop_front() on an empty queue returns null and the compare dereferences it, giving a null-object fatal. Similarly process_exp_tx_item_watchdog[0] on an empty queue. The real DUT bug gets reported as a TB crash.

Checks off ≠ silent

has_checks=0 skips compares but still pops queues, so the bookkeeping stays aligned and checks can be turned back on mid-test. That's a good pattern to copy.

7.4Interview drill

Q1"In-order vs out-of-order scoreboard: how do you build each?"+

In-order: a queue per stream, push expected, pop and compare on actual. Out-of-order: an associative array keyed by a match key (ID, address, tag), with a search on arrival and an error for an unknown key. Both need end-of-test emptiness checks, plus timeouts if latency is bounded. The hard part is choosing the key when the DUT can merge or split items, as this one does. Then compare at byte-stream level, not item level.

8.4Hidden concepts

illegal_bins are checkers

Hitting an illegal_bins raises a run-time error. Use them only for things the DUT must never do, never for "the TB doesn't generate this". illegal_bins length_lt_1 in MD coverage is a checker hiding in the coverage model.

ignore_bins with with

Expression filters (all with (…)) state the rule once instead of enumerating bins, and they scale with parameters. They're the fix for both the TODO and the hard-coded 32-bit bins.

per_instance + set_inst_name

Two MD agents share one covergroup type. Without per_instance = 1 the tool merges RX and TX coverage into one number, and you can't tell which side is missing.

Sample the right event

Coverage must be sampled at the moment the behaviour is complete and checked: end of transfer, after compare, after IRQ observed. Sampling at the start covers stimulus intent, not verified behaviour.

Transition bins

(CFS_APB_READ, CFS_APB_WRITE => CFS_APB_READ, CFS_APB_WRITE) covers all 4 direction sequences. Write-after-read hazards live there, and value bins can't see them.

Closure loop

Run a regression, then merge, then review holes with the plan, then for each hole decide: unreachable (ignore with justification), missing stimulus (constraint or directed sequence) or missing check. Coverage percentage is a conversation, not a target.

8.5Interview drill

Q1"You have 100% functional and code coverage, and a bug escaped to silicon. How?"+

Coverage proves stimulus reached a state, not that a checker looked at it. Typical escapes: (1) the plan missed the feature, so there's no bin; (2) the bins were sampled at the wrong time or double-counted (your MD coverage); (3) crosses missing the dangerous combination (same-cycle CLR and err); (4) checks disabled or too weak; (5) the bug is in an interaction across features each covered alone. Fix the process: tie each bin to a check, review the plan with designers, and add cross and temporal coverage for interactions.

Q2"Code coverage vs functional coverage: which do you sign off on?"+

Both, for different questions. Code coverage asks "did we execute the RTL?" and finds dead code and untested branches, but knows nothing about the spec. Functional coverage asks "did we exercise the spec's scenarios?" but only what you thought to write. A line never hit is a real hole. A functional bin never hit is a hole or a wrong bin. Sign-off needs both reviewed, with documented waivers.

9.3Hidden concepts and findings

Finding · void'(randomize()) everywhere

Every test and vseq ignores the randomize result. Your rx_err constraint is unsatisfiable at ALGN_DATA_WIDTH = 8: with 1 byte, size 1 at offset 0 is the only possible item, and it's legal. Randomize fails silently, the item keeps its constructor defaults (empty data, so size 0), and the run reports SIZE_EQ_0_A, a misleading error far from the cause. Always if(!x.randomize()) `uvm_fatal(…).

Objections: one owner

Only the test raises and drops, around the whole scenario. The #(500ns) before the drop is a hand-made drain time. phase.phase_done.set_drain_time(this, 500ns) says the same thing in a way reviewers recognise.

Reconfig guarded by is_empty()

if(env.model.is_empty()) skips CTRL changes while data is in flight. It keeps tests passing, and it also means "reconfigure under traffic" is never tested. Know which of your guards are hiding scenarios.

Soft defaults, hard limits

Items use soft for preferences (delays ≤5, size 1) and the sequence turns some off with constraint_mode(0) in its constructor. Hard constraints encode physics (fits on the bus). Tests override soft ones freely with inline with.

Two sequences, one sequencer

test_reg_access forks the random-register and unmapped-address vseqs on the same APB sequencer. The default FIFO arbitration interleaves them per item. Use lock()/grab() when a multi-item operation must not be interrupted.

Unmapped test skips misaligned mapped addresses

get_reg_addresses() excludes all 4 byte addresses of each register (0x01, 0x02, 0x03…). The register test uses aligned ones. So the datasheet's "paddr[1:0] ignored" rule is never exercised: a guaranteed escape (Module 10, bug 8).

9.4Interview drill

Q1"Virtual sequence vs virtual sequencer: do you need the sequencer?"+

A virtual sequence only needs handles to the real sequencers. It can get them from a virtual sequencer (p_sequencer, as here), from fields set by the test, or from config_db. The virtual sequencer is convenient and lets vseqs nest, but it's an extra component. Some teams pass handles directly and start vseqs with start(null). Either is fine; consistency matters.

Cross-questions
  • p_sequencer vs m_sequencer? (m_sequencer is the base handle that's always set. `uvm_declare_p_sequencer adds a typed, cast copy for access to custom fields.)
  • How do you stop a forever sequence at end of test? (Let the phase end kill it, or sequencer.stop_sequences(); never hold an objection inside it.)
Q2"How would you write a test that reconfigures CTRL while traffic is in flight?"+

First get the spec to define it: does a new CTRL apply to bytes already in the buffer? Then the model must snapshot CTRL per TX word (or per RX item, as the spec says). The test forks MD traffic and a delayed CTRL write without the is_empty() guard, and coverage records "CTRL changed with N bytes buffered". Without the spec decision this test can only find disagreements, not bugs.

10.3Second real issue: CDC that the testbench can't see

cfs_aligner_core.v · cfs_synch.v · cfs_rx_ctrl.v

The core has three clock domains (md_rx_clk, pclk, md_tx_clk) with async FIFOs between them, but cfs_aligner.v ties all three to one clk. CNT_DROP (8 bits) crosses domains through cfs_synch, which is a single flop on a multi-bit bus. With real asynchronous clocks that can capture a mix of old and new bits. It's also cleared by clr_cnt_dop used as an asynchronous reset from another domain.

Your testbench drives one clock, so none of this can fail in simulation. Interview answer: "I'd parameterize the TB with independent clocks and random ratios, run a structural CDC tool, and either Gray-code the counter or hand it across with a handshake."
