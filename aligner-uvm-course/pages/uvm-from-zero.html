      What is verification?

      Why chips need testers, and what a testbench does · 8 min

      Think of it like…

      A toy company makes a new robot. One team builds it (designers). Another team tries to break it before it reaches shops (testers). If a broken robot reaches a child, the company must recall thousands of toys. That's expensive and embarrassing.

      Chips are the same, only worse: once a chip is manufactured, you cannot fix it. A new set of masks can cost millions of dollars and months of time. So chip companies pay verification engineers to find every bug while the chip is still just code.

      Two kinds of engineers, one chip

      The designer writes the chip in a hardware language (Verilog or SystemVerilog). This code is called RTL (Register Transfer Level). The chip under test is called the DUT (Design Under Test).

      The verification engineer writes a second program, the testbench, that plays with the DUT in a simulator and checks that it behaves exactly as the specification (the "spec" or datasheet) says.

      Every testbench in the world, from a 10-line school project to NVIDIA's GPU testbenches, does these three jobs. UVM is just a well-organised way to do them.

      Remember: Drive → Watch → Judge. If you forget everything else, keep these three words. Every UVM part you'll meet does one of them.

      Clock and reset: the chip's heartbeat

      Why everything happens "on the tick" · 10 min

      Think of it like…

      A rowing team. The coach shouts "ROW!" again and again, and every rower pulls at the same moment. Nobody rows between shouts. The clock is that shout. It goes 0, 1, 0, 1… and on each rising edge (0 → 1) every memory cell in the chip updates at once.

      Reset is the coach saying "everyone back to the start position". Our chip's reset is called reset_n. The _n means "active low": reset happens when the wire is 0.

      Try it · a 4-bit counter

      This counter adds 1 on every rising clock edge, unless reset is held. Press Tick a few times, then hold reset and tick again.

      clk
      0
      reset_n
      1
      count (4 bits)
      0
      clock history
      count: 0

      The same counter in Verilog

      module counter(input clk, input reset_n, output reg [3:0] count);
  always @(posedge clk or negedge reset_n) begin  // wake up on a rising clock (or reset)
    if (!reset_n)                                 // reset is active when reset_n == 0
      count <= 0;                                 // go back to the start
    else
      count <= count + 1;                         // otherwise add 1 on every tick
  end
endmodule
// 4 bits can hold 0..15, so after 15 it "wraps" back to 0
      Common mistake: using = instead of <= inside a clocked block. <= (non-blocking) means "everyone updates together on the tick", like the rowers. = updates immediately and can make two flip-flops race each other. In clocked logic and when driving DUT pins from a testbench, use <=.

      Meet our chip: the Aligner

      What it does, and how it talks · 15 min

      Think of it like…

      A candy-packing machine. Bags of candy arrive in different sizes: 1, 2 or 4 candies. The machine must put them into boxes that all have the same size (the setting is called CTRL.SIZE). If a bag doesn't fit in the space left in a box, the machine cuts the bag: part goes in this box, the rest starts the next box. Order never changes.

      Why would a chip do this? Memories like writes of one fixed size. The Aligner turns messy, uneven data into neat, equal chunks.

      How data moves: the valid/ready handshake

      Every bag travels over a set of wires called the MD interface. The sender raises valid ("I'm holding a bag out"). The receiver raises ready ("my hands are open"). The bag moves only on a clock tick when both are 1. The sender must keep holding the bag (keep valid high, data unchanged) until it's taken.

      The one rule that decides "good bag" or "bad bag"

      On a 4-byte bus, each bag says where it starts (offset, 0–3) and how many bytes it has (size). The datasheet rule: (4 + offset) % size == 0. Size 1 is always fine. Size 2 must start at 0 or 2. Size 4 must start at 0. A bad bag is refused with err = 1 and a counter called CNT_DROP goes up by one.

      1✅ good❌ err❌ err
      2✅ good✅ good❌ err
      3✅ good❌ err❌ err
      Remember: The Aligner has three doors. APB is the control door (registers like CTRL and STATUS). MD RX is where bags come in. MD TX is where boxes go out. A testbench needs one helper per door.

      Your first testbench, without UVM

      Drive, watch, judge with plain Verilog, and why it stops working · 12 min

      Before UVM, let's test something tiny: a module that adds two numbers. A testbench is just another module with no ports. It creates the DUT, wiggles its inputs and checks its outputs.

      module tb;                               // a testbench has no ports
  reg  [7:0] a, b;                       // things WE drive
  wire [8:0] sum;                        // things the DUT drives

  adder dut(.a(a), .b(b), .sum(sum));    // put the DUT on the table

  initial begin
    a = 3;  b = 4;                       // 1. DRIVE
    #10;                                 //    wait 10 time units
    if (sum !== 7)                       // 2. WATCH + 3. JUDGE
      $display("BUG! 3+4 gave %0d", sum);
    else
      $display("pass");
    $finish;
  end
endmodule

      That works. So why do we need UVM?

      Imagine doing this for the Aligner: three doors, a handshake on each, 4 registers, random bag sizes, back-pressure, interrupts, reset in the middle of traffic. With plain code you would:

      Copy-paste forever

      Every test re-writes the same "wiggle valid, wait for ready" code. Fix a bug in one place, it stays broken in twenty others.

      Hand-pick every value

      You'd test only the cases you thought of. Bugs live in the cases nobody thought of. You want the computer to pick random values, within the rules.

      Checks tangled with stimulus

      The "is it right?" logic lives inside each test. A new test means rewriting the judge too.

      Nothing reusable

      Your APB code can't be reused on the next chip, or at the full-chip level, because it's glued to this one test.

      UVM's big idea: split the testbench into small, reusable members, each with one job. Tests then just say what to do; the members know how.

      SystemVerilog classes and randomness

      The only programming ideas UVM needs · 18 min

      Think of it like…

      A class is a cookie cutter. An object is a cookie you cut with it. You can cut many cookies from one cutter, each with its own sprinkles (values). A handle is a sticky note with the cookie's location written on it; two notes can point at the same cookie.

      Inheritance means making a new cutter that's the old one plus something extra: "a star cutter, but with a hole in the middle".

      class bag;                         // the cookie cutter
  rand bit [1:0] offset;           // "rand" = let the computer pick it
  rand int       size;

  constraint good_size { size inside {1, 2, 4}; }        // rule 1
  constraint fits      { (4 + offset) % size == 0; }     // rule 2 (the datasheet rule!)

  function void show();
    $display("bag: offset=%0d size=%0d", offset, size);
  endfunction
endclass

bag b1;                 // a handle (sticky note), points to nothing yet
b1 = new();             // cut a cookie: now b1 points to a real object
if (!b1.randomize())    // pick random values that obey ALL constraints
  $fatal("could not satisfy the rules!");
b1.show();              // e.g. "bag: offset=2 size=2"

class bad_bag extends bag;          // inheritance: a bag, plus one more rule
  constraint must_fail { (4 + offset) % size != 0; }     // always breaks the datasheet rule?
endclass
      Trap in that last class: bad_bag keeps the parent's fits rule and adds the opposite. Both can't be true, so randomize() fails. To make an always-bad bag, turn the parent rule off: b.fits.constraint_mode(0), or override the constraint by giving it the same name in the child.
      Try it · a die with rules

      A constraint is a rule the random value must obey. Tick rules and roll. Try ticking rules that can't all be true at once.

      One more word: virtual

      When a function is virtual, calling it through a parent-type handle runs the child's version. UVM uses this everywhere: the UVM library calls run_phase() on your component, and your version runs. Without virtual, the parent's empty version would run.

      Transactions: from wires to parcels

      Thinking in "items" instead of 0s and 1s · 10 min

      Think of it like…

      When you send a parcel, you don't describe the truck's engine, the road and the gear changes. You write a label: to, from, contents. A transaction is that label for a bus transfer. Instead of "valid went high at 35 ns, data was 0x44332211…", you say "an MD item: offset 0, 4 bytes, response OKAY".

      class md_item extends uvm_sequence_item;    // UVM's base class for transactions
  rand bit [7:0] data[$];                    // a list of bytes (1, 2 or 4 of them)
  rand int       offset;                     // where on the bus the bytes start
  md_response    response;                   // OKAY or ERR, filled in by the monitor

  `uvm_object_utils(md_item)                 // register with the UVM factory (Level 7)

  function new(string name = "md_item");
    super.new(name);
  endfunction

  virtual function string convert2string();  // how to print me in the log
    return $sformatf("offset=%0d size=%0d resp=%s", offset, data.size(), response.name());
  endfunction
endclass
      Remember: the driver turns items into wires; the monitor turns wires back into items. Everything in between (sequences, scoreboard, coverage) only ever sees items. That's what makes it easy to think about.

      The UVM team: a restaurant

      Every UVM part, and who passes what to whom · 18 min

      Think of it like…

      A restaurant. The test picks today's menu. A sequence is an order slip ("3 random bags, then 1 bad bag"). The sequencer is the waiter who queues order slips. The driver is the chef who actually cooks: it puts real signals on the wires. The monitor is a food critic at the table who writes down exactly what was served. The scoreboard is the judge: it compares what was served with what the recipe book (the reference model) says should be served. Coverage is a checklist of dishes tried so far.

      uvm_sequence_item

      Item

      One parcel (Level 5).

      uvm_sequence

      Sequence

      Makes items, often random, in a planned order. Drive.

      uvm_sequencer

      Sequencer

      Queues items and hands them to the driver one at a time.

      uvm_driver

      Driver

      Turns an item into wire wiggles that follow the protocol. Drive.

      uvm_monitor

      Monitor

      Only listens to wires, rebuilds items, shouts them to everyone. Watch.

      uvm_agent

      Agent

      A box holding sequencer + driver + monitor for one door of the chip.

      model

      Reference model

      Predicts what the chip should output, from what went in.

      uvm_scoreboard

      Scoreboard

      Compares predicted vs. actual. Prints UVM_ERROR on mismatch. Judge.

      uvm_env

      Environment

      The whole restaurant: all agents + model + scoreboard + coverage.

      uvm_test

      Test

      Builds the env and picks which sequences to run.

      How members talk: analysis ports

      The monitor doesn't know who's listening. It has an analysis port, like a radio station. Anyone with a matching receiver (an analysis imp) that's connected gets a copy of every item. One monitor can feed the model, the scoreboard and coverage at the same time, without knowing any of them.

      Building the team: phases, config_db, factory

      The three UVM "magic" words, without magic · 15 min

      Think of it like…

      Putting on a school play. First you build the set and cast actors (top to bottom: director, then groups, then each actor). Then you connect: run cables, give everyone their walkie-talkies. Then the run: the play happens, and time moves. Finally you report: who forgot lines?

      build_phaseBuild the set

      Create children with type_id::create. Runs top-down: the test first, then the env, then the agents.

      connect_phaseRun the cables

      Connect monitor ports to scoreboard and model. Runs bottom-up.

      run_phaseThe show

      The only phase where simulation time passes. Drivers drive, monitors watch, tests start sequences.

      check / reportApplause or boos

      Final checks and the summary: how many UVM_ERRORs?

      config_db: the notice board

      The top module owns the real wires (interfaces), but classes can't see modules. So the top pins a note on a shared notice board: "the APB wires are here, for whoever is at uvm_test_top.env.apb_agent". The agent later reads the board.

      // in the top module (testbench.sv): pin the note
uvm_config_db#(virtual cfs_apb_if)::set(null, "uvm_test_top.env.apb_agent", "vif", apb_if);

// in the agent: read the note
if (!uvm_config_db#(virtual cfs_apb_if)::get(this, "", "vif", vif))
  `uvm_fatal("NO_VIF", "Nobody pinned my wires on the notice board!")

      The factory: the substitute player

      When you create objects with type_id::create instead of new, you let the UVM factory make them. A test can then say "whenever anyone asks for a normal RX sequence, give them the error version instead", without changing any other file. That's exactly how your cfs_algn_test_random_rx_err test works.

      // in the test's build_phase: swap the player
cfs_algn_virtual_sequence_rx::type_id::set_type_override(
    cfs_algn_virtual_sequence_rx_err::get_type());

// later, deep inside cfs_algn_test_random:
seq = cfs_algn_virtual_sequence_rx::type_id::create("seq");  // you actually get the _err one!
      Common mistake: writing seq = new("seq");. new skips the factory, so the swap silently doesn't happen. Always use type_id::create.

      Writing each team member

      Tiny real code for driver, monitor, sequence, scoreboard · 20 min

      These are shortened versions of the real files in your Aligner testbench. Read the comments like a story, top to bottom.

      The sequence (writes the order slip)

      class my_rx_sequence extends uvm_sequence #(md_item);
  `uvm_object_utils(my_rx_sequence)
  function new(string name = "my_rx_sequence"); super.new(name); endfunction

  virtual task body();                       // body() is what runs when the sequence starts
    repeat (5) begin                         // make 5 random bags
      md_item item = md_item::type_id::create("item");
      start_item(item);                      // ask the waiter (sequencer) for a turn
      if (!item.randomize()) `uvm_fatal("RAND", "randomize failed")
      finish_item(item);                     // hand it over; waits until the driver is done
    end
  endtask
endclass

      The driver (the chef)

      class my_md_driver extends uvm_driver #(md_item);
  virtual cfs_md_if vif;                         // the wires (from the notice board)

  virtual task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);          // wait for the next order slip
      vif.valid  <= 1;                           // "I'm holding a bag out"
      vif.data   <= pack_bytes(req);             // put the bytes on the bus
      vif.offset <= req.offset;
      vif.size   <= req.data.size();
      @(posedge vif.clk);
      while (vif.ready !== 1) @(posedge vif.clk); // wait until the receiver takes it
      vif.valid  <= 0;                           // let go
      seq_item_port.item_done();                 // tell the waiter: done, next please
    end
  endtask
endclass

      The monitor (the critic)

      class my_md_monitor extends uvm_monitor;
  virtual cfs_md_if vif;
  uvm_analysis_port #(md_item) output_port;      // the radio station

  virtual task run_phase(uvm_phase phase);
    forever begin
      md_item item = md_item::type_id::create("item");
      @(posedge vif.clk iff vif.valid);          // a transfer has started
      item.offset = vif.offset;                  // copy what's on the wires
      // ...unpack data bytes...
      while (vif.ready !== 1) @(posedge vif.clk);
      item.response = md_response'(vif.err);     // was it refused?
      output_port.write(item);                   // broadcast to everyone listening
    end
  endtask
endclass

      The scoreboard (the judge)

      class my_scoreboard extends uvm_scoreboard;
  md_response expected[$];                       // a queue of predictions

  function void write_expected(md_response r);   // the model calls this
    expected.push_back(r);
  endfunction

  function void write_actual(md_item item);      // the monitor calls this
    md_response exp = expected.pop_front();
    if (item.response != exp)
      `uvm_error("DUT_ERROR", $sformatf("expected %s, got %s", exp.name(), item.response.name()))
  endfunction
endclass
      Notice: the driver never checks anything, and the scoreboard never touches a wire. Each member does one job. That's why you can reuse the same agent on the next chip.

      Tests: running the show

      Objections, test names, and reading the log · 12 min

      Think of it like…

      A party that ends when the last person leaves. Each part of the testbench that's still busy raises an objection ("don't turn off the lights, I'm still here"). When everyone has dropped their objection, the run phase ends. Forget to raise one and the party ends at time 0: nothing happens, and the test "passes".

      class my_test extends cfs_algn_test_base;            // base test builds the env
  `uvm_component_utils(my_test)
  function new(string name = "", uvm_component parent); super.new(name, parent); endfunction

  virtual task run_phase(uvm_phase phase);
    my_rx_sequence seq = my_rx_sequence::type_id::create("seq");
    phase.raise_objection(this);                     // lights ON
    seq.start(env.md_rx_agent.sequencer);            // run the order slip on the RX door
    #500ns;                                          // let the last boxes come out
    phase.drop_objection(this);                      // lights OFF
  endtask
endclass

      Running it

      On EDA Playground you add +UVM_TESTNAME=my_test to the run options. The top module calls run_test(), which creates the test by name. At the end the log prints a summary. This one is from your own run:

      Your first real task: send only bad bags

      The "Illegal RX Traffic" exercise, step by step · 15 min

      The job: make a test where every RX bag breaks the datasheet rule, send 300 of them, and check the chip refuses all of them.

      Step 1. Ask: what already exists?

      There's already a test (cfs_algn_test_random) that sends random good bags using a sequence called cfs_algn_virtual_sequence_rx. We won't copy it. We'll make children of both and change only what's different.

      Step 2. A sequence that only makes bad bags

      class cfs_algn_virtual_sequence_rx_err extends cfs_algn_virtual_sequence_rx;  // child = parent + 1 rule
  local int unsigned data_width_in_bytes;           // 4 on a 32-bit bus

  constraint rx_err {                                // the NEW rule: break the datasheet rule
    ((data_width_in_bytes + seq.item.offset) % seq.item.data.size()) != 0;
  }

  `uvm_object_utils(cfs_algn_virtual_sequence_rx_err)
  function new(string name = ""); super.new(name); endfunction

  function void pre_randomize();                     // runs just before randomize()
    super.pre_randomize();
    data_width_in_bytes = p_sequencer.md_rx_sequencer.get_data_width() / 8;
  endfunction
endclass

      Step 3. A test that swaps the sequence and sends 300

      class cfs_algn_test_random_rx_err extends cfs_algn_test_random;
  `uvm_component_utils(cfs_algn_test_random_rx_err)

  function new(string name = "", uvm_component parent);
    super.new(name, parent);
    num_md_rx_transactions = 300;                    // the parent's knob
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    cfs_algn_virtual_sequence_rx::type_id::set_type_override(   // the substitute player
        cfs_algn_virtual_sequence_rx_err::get_type());
  endfunction
endclass

      Step 4. Tell the packages the new files exist

      Add `include "cfs_algn_virtual_sequence_rx_err.sv" in cfs_algn_pkg.sv and `include "cfs_algn_test_random_rx_err.sv" in cfs_algn_test_pkg.sv, then run with +UVM_TESTNAME=cfs_algn_test_random_rx_err.

      Step 5. What should you see?

      Every RX line in the log ends with response: CFS_MD_ERR. CNT_DROP counts up and stops at 255 (it never wraps). If an interrupt error appears for some random seeds, that isn't your mistake: it's a real chip bug, explained in the senior course.

      The habit to keep: change the smallest thing. You wrote about 30 lines and reused thousands, because the original authors built for reuse (classes, factory, knobs).

      V1

      What is design verification?

      Where module-level UVM work fits in a chip's life

      A chip is printed many times on a round silicon wafer. Testing the real chips on the wafer is post-silicon verification. This course is about pre-silicon verification: checking the RTL code before any wafer exists, when bugs are still cheap to fix.

      The highlighted path is this course: pre-silicon → module level → simulation → SystemVerilog + UVM.

      Facts to remember
      • DUT = Device (or Design) Under Test. You may also see DUV, Device Under Verification. Same thing.
      • RTL = Register Transfer Level: the Verilog/VHDL the designers write.
      • An agent drives and monitors one interface. The model computes the correct outputs from the same inputs. The scoreboard compares and reports a DUT error when they differ. The designer fixes the RTL.
      • Verification's goal: find inputs for which the DUT's function is wrong.
      Q"Pre-silicon vs post-silicon verification?"

      Pre-silicon checks the RTL in simulation, formal or emulation, before tape-out. Bugs are cheap to fix and you have full visibility of every signal. Post-silicon tests the manufactured chip (on the wafer, then packaged). Visibility is limited to pins and debug logic. It catches manufacturing defects and bugs that escaped pre-silicon, and a fix needs a respin. That's why pre-silicon effort is so large.

      Q"Module-level vs system-level: why do both?"

      Module level gives you full control of a block's inputs, so you can hit corner cases (illegal transfers, FIFO full, counter saturation) quickly. At system level those are hard to reach through other blocks. System level finds integration bugs: wrong connections, address maps, clock/reset interactions, end-to-end flows. Module-level components (agents in passive mode, models, scoreboards) are reused at system level.

      Q"Simulation vs formal verification?"

      Simulation drives chosen (often random) inputs and checks outputs. It scales to big designs and long scenarios, but only proves the cases you ran. Formal mathematically checks assertions against all possible inputs within bounds. It's exhaustive for small, control-heavy logic (arbiters, protocol rules, the Aligner's legality check) but struggles with deep data paths. Teams use both: formal for small exhaustive properties, simulation for end-to-end data.

      Q"Why separate the model from the scoreboard?"

      The model predicts; the scoreboard compares. Keeping them apart lets you replace the model (e.g. with a C++ golden model) without touching compare logic, reuse the scoreboard, and tell "prediction bug" apart from "compare bug" when debugging.

      V2

      The Aligner DUT in depth

      Every feature you'll have to verify (27-minute video)

      Lecturer's advice

      "Go through the datasheet on your own." In a real job nobody explains the DUT to you. Reading the spec and listing every feature is the first task on any project, and interviewers test it: "here's a spec, what would you verify?"

      1. Lanes, size and offset

      Both the RX and TX data buses are 32 bits = 4 byte lanes (0 to 3). size = how many lanes carry valid bytes, offset = the first valid lane.

      The 7 legal combinations. Size 3 is illegal at every offset. Any other combination must be rejected with an error, and your tests must send those too.

      2. Alignment, controlled by CTRL

      CTRL.SIZE = bytes per TX transfer, CTRL.OFFSET = first TX lane. With OFFSET=2, SIZE=2 the Aligner places the first received byte on lane 2, waits for one more byte, then sends lanes 2–3. With OFFSET=0, SIZE=4, once 5 bytes are inside it must split the last RX transfer: send 4 bytes, keep 1 for the next TX transfer. The lecturer calls splitting "an important feature that we will have to verify". Try it in Level 2's candy packer.

      3. Registers

      4. Drop counter

      Every illegal RX transfer gets an error response and STATUS.CNT_DROP goes up by 1. It's 8 bits, so it stops at 255 and never wraps to 0. Writing CTRL.CLR = 1 clears it.

      5. FIFO levels

      Legal RX transfers go into the RX FIFO. The Controller pops them, aligns, and pushes into the TX FIFO. The TX Controller pops and sends. RX_LVL/TX_LVL count transactions, not bytes. Play with it:

      Try it · FIFO levels and interrupts
      CTRL.SIZE next RX size
      RX FIFO · RX_LVL = 0
      TX FIFO · TX_LVL = 0
      Push a few RX transfers, then let the Controller work.

      6. Interrupts

      Five events: CNT_DROP reached max, TX FIFO became full, TX FIFO became empty, RX FIFO became full, RX FIFO became empty. Each event sets its sticky IRQ bit (W1C). The irq output is a one-cycle pulse: each event is ANDed with its IRQEN bit, then all five are ORed.

      7. Register access: APB

      A transfer has a Setup phase (PSEL=1, PENABLE=0, always one cycle) and an Access phase (PSEL=1, PENABLE=1) that lasts until PREADY=1. Extra Access cycles are wait states. Address, PWRITE and PWDATA must stay constant for the whole transfer. PRDATA and PSLVERR are only valid when PREADY=1.

      Try it · APB waveforms

      The three APB error cases (memorise)
      • Access to an unmapped address.
      • Write to STATUS (read-only register).
      • Illegal SIZE/OFFSET written to CTRL, e.g. SIZE=3 OFFSET=1 or SIZE=2 OFFSET=1.

      The lecture's key scenario: write CTRL = (1,1) → OK. Read → (1,1). Write CTRL = (2,1) → error. Read again → still (1,1). A test must prove the errored write changed nothing.

      8. MD protocol (RX and TX)

      A made-up protocol for this course (no online docs). A transfer starts when valid=1 and ends when ready=1. It can last one cycle (both high together) or longer, in which case valid, data, offset and size must stay constant. err is valid when ready=1. The example: RX receives 11, 22, then 33 44 in separate transfers; with SIZE=4, OFFSET=0, TX sends 11 22 33 44 in one transfer.

      Q"What is a W1C sticky register, and how would you verify it?"

      The bit is set by hardware when an event happens, stays 1 after the condition goes away (sticky), and is cleared only by writing 1 (W1C). Writing 0 does nothing. Verify: trigger the event and read 1; remove the condition and still read 1; write 0 and still read 1; write 1 and read 0; clear while the condition persists and check it doesn't immediately re-set (it's an edge event); re-trigger and check it sets again.

      Q"Why must your tests send illegal transfers?"

      Rejecting them is a spec feature: error response, drop counter increment, saturation at 255, MAX_DROP interrupt. Legal-only traffic leaves all of that unverified. Error-handling paths are where bugs hide because designers test them least.

      Q"After an APB write returns PSLVERR, what do you check?"

      That the register kept its old value: read it back and compare against the value before the failed write. In UVM, the predictor must not update the register mirror for an errored access. Otherwise every later prediction is wrong.

      Q"Do FIFO levels count bytes or transactions? Why does it matter?"

      Transactions. A 2-byte RX transfer adds 1 to RX_LVL. With CTRL.SIZE=1 it becomes two TX entries, so TX_LVL grows by 2. Your model must count the same way, or every STATUS read and FIFO-full interrupt prediction will be off.

      Q"Explain APB setup and access phases, and wait states."

      Setup: PSEL=1, PENABLE=0 for exactly one cycle, with address/direction/data valid. Access: PENABLE=1, and the transfer completes on the first cycle PREADY=1. Each cycle with PREADY=0 is a wait state. Signals must stay stable until completion. The Aligner spec says no more than 5 wait states, which is a good assertion to write.

      Q"The IRQ output is a pulse but the IRQ register is sticky. How do you check both?"

      Two checks. The register: the model predicts the IRQ bit (set on event, W1C clear) and register reads compare. The pin: on each event, if its IRQEN bit is 1, expect exactly one one-cycle pulse within a small window. If IRQEN is 0, no pulse, but the IRQ bit is still set. Cover every event × enable combination.

      Environment architecture

      What gets built, and in which order

      The course builds the environment in this order. Each step reuses the previous ones, which is also a good order for your own projects.

      1. APB agentinterface (signals) → sequencer + driver (drive transactions) → monitor (collect transactions into a class, broadcast them) → coverage (database of what happened on this interface) → config (tweak the agent).
      2. MD RX and TX agents, togetherSame protocol, so common code is written once and inheritance adds the RX (master) and TX (slave) differences.
      3. UVM extension libraryAfter three agents, the shared code becomes a library (uvm_ext_pkg) and all agents are rebuilt on it. New agents then take minutes.
      4. Model + register model + predictorThe model predicts the Aligner's outputs from agent data. UVM's register layer models the 4 registers, and the predictor updates and checks them.
      5. ScoreboardCompares DUT outputs with model outputs and raises errors on differences.
      6. Environment coverageThe full picture of Aligner scenarios, unlike agent coverage, which only knows one interface.
      7. Virtual sequencerOne place to control all agents together from a sequence.
      8. Environment configKnobs for the whole environment.
      9. Tests + testbenchA base test creates the env; every test inherits from it. The testbench module holds the DUT and starts UVM.
      Q"Agent coverage vs environment coverage: what's the difference?"

      Agent coverage is protocol-level and reusable: APB read/write, error responses, wait-state lengths, MD sizes and offsets. Environment coverage is DUT-feature level: alignment cases (CTRL setting × RX transfer × split), drop counter saturation, interrupts. Agent coverage proves the bus was exercised. Environment coverage proves the features were. You need both.

      Q"Why a virtual sequencer?"

      Real scenarios coordinate several interfaces: configure CTRL over APB, then send RX traffic, while the TX side applies back-pressure. A virtual sequencer holds handles to all agent sequencers (and, in this project, the model), so one virtual sequence can drive them in order or in parallel.

      Q"How would you structure two agents for the same protocol, one master and one slave?"

      Common base classes for item, monitor, coverage, config and agent, parameterized where needed (e.g. data width). Then master and slave subclasses for the driver, sequencer and drive item. The monitor is identical on both sides because it only watches. Factory overrides inside each agent pick the right subclasses.

      Q"What goes in a base test?"

      Creating the environment and anything every test shares: default config, common objections and drain time, a topology print, end-of-test checks. Specific tests extend it and only change stimulus and knobs. That avoids copying env setup into every test.

      Facts from the lecture
      • Every class in the environment diagram is a component: it inherits from uvm_component (so does uvm_test).
      • Components can only be created in the build phase. After that, the structure is fixed until the end of simulation.
      • Naming convention: <company>_<dut>_<name>, here cfs_algn_…. It avoids name clashes when many teams' code is compiled together.

      Q"List the UVM phases. Which consume time?"

      build, connect, end_of_elaboration, start_of_simulation, run, extract, check, report, final. Only run (and its optional sub-phases) is a task that consumes time; the rest are zero-time functions. Build is top-down, most others bottom-up.

      Q"How does UVM know which test to run?"

      run_test() reads +UVM_TESTNAME (it wins over the string argument), asks the factory to create that class by name as uvm_test_top, then starts the phases. The class must be registered with `uvm_component_utils and extend uvm_test. A misspelt name gives a fatal "cannot create a component" error.

      Q"Why can components only be created in build_phase?"

      UVM needs a fixed hierarchy before connecting ports and running. Connections, config lookups by path and phase scheduling all depend on it. Objects that come and go during simulation (transactions, sequences) are uvm_objects, not components, and can be created any time.

      Q"uvm_component vs uvm_object?"

      Components are permanent parts of the testbench tree: they have a parent, a hierarchical name and phases (agents, drivers, scoreboards). Objects are temporary data: no parent and no phases (transactions, sequences, config objects). Components use the constructor new(string name, uvm_component parent); objects use new(string name).

      Facts from the practice
      • Mandatory in every component: `uvm_component_utils(<class>) plus a constructor new(string name, uvm_component parent) calling super.new(name, parent).
      • Create with type_id::create("env", this), not new. Use the same string as the handle name (good practice). this is the parent.
      • Objections are a counter: raise = +1, drop = −1, and UVM ends the run phase when it reaches 0.
      • `uvm_info(ID, message, verbosity) beats $display: filename, time, component path, filterable by ID and verbosity (UVM_NONE, LOW, MEDIUM, HIGH, FULL, DEBUG).
      • Two packages: one for tests, one for the environment. Include guards (`ifndef/`define/`endif) on every file.
      Q"What does `uvm_component_utils do?"

      It registers the class with the factory (creating the type_id proxy so type_id::create and overrides work) and adds utility methods like get_type_name(). Objects use `uvm_object_utils. For parameterized classes you use the _param_ variants.

      Q"Why type_id::create instead of new?"

      create goes through the factory, so a test can override the type (e.g. swap a sequence for an error-injecting one) without editing the code that creates it. new bypasses the factory and overrides silently don't apply.

      Q"Explain objections. What goes wrong if you get them wrong?"

      The run phase ends when the objection count reaches zero. Never raised: the test ends at time 0 and "passes" with nothing done. Never dropped: the simulation hangs until a timeout. Dropped too early: traffic still in flight isn't checked. Fix with drain time (set_drain_time) or by waiting for the scoreboard to empty before dropping.

      Q"`uvm_info vs $display? How do you control verbosity?"

      `uvm_info adds file, line, time and component path, and is filtered by verbosity: a message prints only if its level is ≤ the component's setting. Change globally with +UVM_VERBOSITY=UVM_HIGH, or per component/ID with +uvm_set_verbosity, as your messages.f does. Errors use `uvm_error/`uvm_fatal, which are counted in the final report.

      Q"Why include guards and packages?"

      Guards stop a file being compiled twice when several packages include it, which would cause duplicate-definition errors. Packages give a namespace and a single compile unit: tests import the env, the testbench imports tests, and names don't leak or clash.

      Q"How do you decide what goes in a sequence item?"
      Everything the stimulus side controls and nothing the protocol fixes. Remove signals driven by the other side and signals whose behaviour is fully determined by the protocol (PSEL/PENABLE). Add timing knobs (delays) so tests can create back-to-back and idle traffic. Response fields go in the monitor item, not the drive item.
      
        
      Q"Soft vs hard constraints?"
      A soft constraint is a default that's dropped if it conflicts with another constraint, e.g. a test's inline with {pre_drive_delay == 50;}. A hard constraint can't be overridden. A conflict means randomize fails. Use soft for preferences and hard for legality and physical limits.
      
        
      Q"Why separate drive and monitor items?"
      They carry different information. The driver needs intent (delays); the monitor records what happened (response, length, gap since the previous item). A shared base avoids duplicating address, direction and data. It also stops anyone from accidentally checking intent against intent.
      
        
      Q"What is convert2string for, versus print()/sprint()?"
      convert2string is a user-written, compact one-line summary for logs. print/sprint use UVM's printer and field macros to produce tables, which are verbose and slower. Most teams implement convert2string by hand.

      Q"Walk me through what happens when finish_item is called."
      start_item waits for the sequencer to grant this sequence (arbitration). Then you randomize or set fields. finish_item hands the item to the sequencer and blocks. The driver's pending get_next_item returns that item. The driver drives it and calls item_done, which unblocks finish_item, and body continues to the next item.
      
        
      Q"`uvm_do vs `uvm_send vs `uvm_do_with?"
      `uvm_do: create, randomize, start/finish. `uvm_do_with: the same with inline constraints. `uvm_send: just start/finish, so it keeps whatever values the item already has. Using `uvm_do on an item a caller already constrained silently discards those constraints. Many teams avoid the macros and write start_item/randomize/finish_item explicitly so it's clear what happens.
      
        
      Q"What does local:: do in an inline constraint?"
      Inside obj.randomize() with {…}, names resolve to the object being randomized first. local::x forces x to resolve in the calling scope (the sequence). Without it, addr == addr compares the item's addr with itself, which is always true and constrains nothing.
      
        
      Q"m_sequencer vs p_sequencer?"
      m_sequencer is the generic uvm_sequencer_base handle, always set by start(). p_sequencer exists only if you use `uvm_declare_p_sequencer(T). It's the same object, cast to T, so you can reach custom fields (e.g. the virtual sequencer's handles to other sequencers).
      
        
      Q"Several sequences on one sequencer: what decides order, and how do you keep one atomic?"
      Arbitration per item: default FIFO (request order), or weighted, random, strict priority (set_arbitration). To keep several items uninterrupted, lock() or grab() the sequencer, then unlock/ungrab. In the video's fork, the read and write of the rw sequence get separated by other sequences' items.
      
        
      Q"Active vs passive agent?"
      Active creates sequencer + driver + monitor and drives the bus. Passive has only the monitor (and coverage) and just observes, e.g. at SoC level where a CPU or another block drives that bus. Controlled by get_is_active() or a config field like here.

      The APB driver
      Turning an item into a real APB transfer · lecture + practice
      
      
      The structure prepares for reset handling (A8): run_phase calls drive_transactions() (initialize signals, then loop forever), which calls drive_transaction(item) once per item. The driver reaches the interface through a pointer to the agent config, connected in the agent's connect_phase.
      
      
      protected virtual task drive_transaction(cfs_apb_item_drv item);
  cfs_apb_vif vif = agent_config.get_vif();
  for(int i = 0; i < item.pre_drive_delay; i++) @(posedge vif.pclk);   // 1. idle before

  vif.psel   <= 1;                                     // 2. SETUP phase
  vif.pwrite <= bit'(item.dir);
  vif.paddr  <= item.addr;
  if(item.dir == CFS_APB_WRITE) vif.pwdata <= item.data;
  @(posedge vif.pclk);

  vif.penable <= 1;                                    // 3. ACCESS phase
  @(posedge vif.pclk);
  while(vif.pready !== 1) @(posedge vif.pclk);         // 4. wait states until PREADY

  vif.psel <= 0; vif.penable <= 0; vif.pwrite <= 0;   // 5. back to idle defaults
  vif.paddr <= 0; vif.pwdata <= 0;

  for(int i = 0; i < item.post_drive_delay; i++) @(posedge vif.pclk);  // 6. idle after
endtask
      
      
      Facts to remember
        
        
      • "Always use non-blocking assignments when driving signals from the driver." This ensures the DUT samples correctly at the clock edge.
        • 
        
      • Initialize all master signals to 0 before the first item. Otherwise they're X until the first transfer, which you can see on the waveform.
        • 
        
      • The waveform check from the video: post-drive delay 4 + next pre-drive delay 3 = 7 idle cycles between transfers. Verify your own driver this way.
        • 
        
      • Random addresses mostly hit unmapped space, so the DUT correctly returns PSLVERR. Constrain to 0x0 (CTRL) and 0xC (STATUS): reading STATUS is OK, writing STATUS gives an error. That's two spec rules seen on the first run.
        • 
        
      • EDA Playground: tick Open EPWave after run → Get Signals → dut → pick signals.
        • 
      
      
      
      
        
      Q"Why non-blocking assignments in the driver?"
      The DUT's flops sample on the same clock edge the driver wakes up on. A blocking write could land before or after the DUT samples, depending on process order: a race. NBAs update in the NBA region after all active-region sampling, so the DUT always sees the previous value at the edge. Clocking blocks formalize the same thing.
      
        
      Q"Why split drive_transactions and drive_transaction?"
      The outer task owns the loop and the process that reset can kill and restart. The inner task owns one protocol transfer. Subclasses override only drive_transaction for protocol variants, and the reset plumbing stays in one place. That's exactly how the later uvm_ext_driver base class is built.
      
        
      Q"How would you add a response back to the sequence?"
      Clone the request, fill in response fields (PRDATA, PSLVERR), call set_id_info(req), then item_done(rsp) or seq_item_port.put(rsp). The sequence calls get_response(rsp). This driver doesn't, so RAL frontdoor calls always return OK and bus errors are judged by the predictor instead (see the senior course).

      Design decisions worth explaining in an interview
        
        
      • has_checks lives in two places (agent config and interface) and is kept in sync: the config's setters push the value to the interface, and the config's run_phase reports an error if someone changes the interface copy directly.
        • 
        
      • $error instead of `uvm_error in interfaces: the same assertions can be reused in formal tools, which may not load the UVM package.
        • 
        
      • Prove every assertion can fail: the lecturer breaks the driver on purpose (PENABLE in setup, no PENABLE in access, flipping PWRITE) and watches each assertion fire. An assertion never seen failing might be checking nothing.
        • 
        
      • +UVM_MAX_QUIT_COUNT=1 stops the simulation at the first error, so you debug the cause, not the echoes.
        • 
      
      
      
      
        
      Q"|-> vs |=>?"
      a |-> b: if a matches, b must hold in the same cycle. a |=> b: b must hold in the next cycle (same as a |-> ##1 b). Rule 1 uses both: in setup, PENABLE==0 now (|->) and ==1 next (|=>).
      
        
      Q"Why does the setup-phase sequence need the back-to-back case?"
      With back-to-back transfers PSEL never drops, so "PSEL rose" doesn't mark the new setup cycle. The second term catches "PSEL was high and PREADY was high last cycle", i.e. the previous transfer just ended and a new one starts now. Miss it and every back-to-back transfer escapes the PENABLE checks.
      
        
      Q"Why are some X-checks gated by PSEL?"
      The protocol only cares about address and data while a transfer is happening. X on PADDR when idle is legal, and flagging it would be noise. PSEL itself must never be X. PRDATA only matters on a successful read once PREADY is high. The skill is knowing when each signal must be valid.
      
        
      Q"Where should a check live: assertion, monitor or scoreboard?"
      Cycle-level signal rules → assertions in the interface (reusable, formal-friendly). Rules needing transaction context or counters (stuck transfer length) → monitor. Data correctness vs a model → scoreboard. Protocol checks belong in the agent so they travel with it to every project.
      
        
      Q"How do you know an assertion actually works?"
      Make it fail: inject the violation (as the lecturer does in the driver), see it fire, then revert. Add cover property for the antecedent so you know it was evaluated with real traffic. A vacuously passing assertion is a common hole.
      
      
      
      
    
      

    
    
      
      
      A6
      The APB monitor
      Pins back into items, broadcast to the environment · lecture + practice
      
      
      The monitor item adds what only an observer can know: response (PSLVERR), length of the transfer in cycles (minimum 2 for APB), and prev_item_delay (idle cycles since the previous transfer). Direction, address and data move to item_base, shared with the drive item. For data, the monitor picks PWDATA on writes and PRDATA on reads.
      
      
      uvm_analysis_port#(cfs_apb_item_mon) output_port;   // created in new(): output_port = new("output_port", this);

protected virtual task collect_transaction();
  cfs_apb_vif vif = agent_config.get_vif();
  cfs_apb_item_mon item = cfs_apb_item_mon::type_id::create("item");

  if(item.dir == CFS_APB_WRITE) item.data = vif.pwdata;

  @(posedge vif.pclk); item.length++;
  while(vif.pready !== 1) begin @(posedge vif.pclk); item.length++; /* + stuck check (A5) */ end

  @(posedge vif.pclk);                                          // step past this transfer

      Facts to remember
        
        
      • uvm_monitor adds nothing to uvm_component, but use it anyway: it documents the role and tools recognise it.
        • 
        
      • uvm_analysis_port#(T): write(item) broadcasts to every connected subscriber (0, 1 or many). It's a function, so it doesn't consume time.
        • 
        
      • The video's check: the monitor reports prev_item_delay = 7, which matches post 4 + pre 3 from the driver. Use your driver's known values to verify the monitor.
        • 
        
      • Bug from the video: convert2string forgot to print data. Logs are your first debug tool, so make them complete.
        • 
      
      
      
      
        
      Q"Why must the monitor be independent of the driver?"
      It must report what really happened on the pins, including driver bugs and transfers from other masters. It must also work in a passive agent where no driver exists. Taking data from the driver would make the checkers trust the stimulus.
      
        
      Q"Analysis port vs TLM put/get port?"
      An analysis port is one-to-many, non-blocking, with no acknowledgement: perfect for broadcasting observations. Put/get ports are one-to-one and can block (flow control between producer and consumer). Monitors always use analysis ports. A slow consumer adds a uvm_tlm_analysis_fifo on its side.
      
        
      Q"Why record length and prev_item_delay at all?"
      For coverage. They prove you exercised back-to-back transfers, long idle gaps and wait-state lengths, the timing corners where DUT bugs hide. The monitor measures; coverage decides if it was enough.
      
        
      Q"Where exactly do you sample PRDATA and PSLVERR?"
      In the cycle where PSEL, PENABLE and PREADY are all 1, the transfer's completion. Sampling earlier works with zero wait states but returns stale data with wait states. That's a classic monitor bug, found only if your stimulus has wait states.

      Clever tricks from the practice video
        
        
      • Why a wrapper component for bit coverage? One item must sample many bins (every address bit), and the six tables differ only in size. A covergroup can't take a class parameter for its range, so it's wrapped in a component parameterized by MAX_VALUE_PLUS_1 and instantiated 6 times.
        • 
        
      • Why a non-parameterized virtual base for the wrapper? Each parameter value is a different class, so you can't $cast to "any wrapper". A virtual base with pure virtual sample()/coverage2string() lets get_children() + one $cast find them all.
        • 
        
      • Coverage needs the compile option -coverage functional on Xcelium, otherwise you get 0% plus a tool warning.
        • 
        
      • coverage2string() printing percentages is for EDA Playground only. Real projects use the vendor's coverage GUI.
        • 
        
      • Verification plan: coverage tables are organised into a tree (vPlan: XML, mind map, or Cadence's vPlanx), with each leaf mapped to a covergroup instance name. There's no standard; every company does it differently. Watch table sizes: crosses grow multiplicatively.

      Q"Coverpoint, cross, transition: give an example of each."
      Coverpoint: values of one field (direction READ/WRITE). Cross: combinations of coverpoints (a write that got an error). Transition: order over consecutive samples (a read followed by a write). Crosses multiply bin counts, so filter with ignore_bins/binsof and cross only what matters to the spec.
      
        
      Q"Why cover address bits rather than address values in an agent?"
      The agent doesn't know the DUT's address map. Toggling every bit to 0 and 1 proves every address line was exercised, which is protocol-level and reusable. Covering specific registers belongs in DUT-level (environment or RAL) coverage.
      
        
      Q"What does option.per_instance do?"
      It keeps coverage per covergroup instance instead of merged per type. With two agents of the same type (e.g. MD RX and MD TX) you can see which interface missed a bin. You also name instances (set_inst_name) to map them in the verification plan.
      
        
      Q"What's a verification plan and how does coverage connect to it?"
      A tree of features from the spec, each leaf with how it's checked and which coverage proves it. Leaves map to covergroups, coverpoints or assertions. Merged regression coverage is annotated back onto the tree, so sign-off reviews show per-feature percentages, not one meaningless total.
      
        
      Q"Why cover 'reset during a transfer'?"
      Reset mid-transfer is a classic corner: the DUT must abort cleanly and the testbench must not hang or mis-report. If coverage never sees it, you have no evidence it was tested. In the video it stays 50% until a test actually injects reset during an access.
      
      
      
      
    
      

    
    
      
      
      A8
      Reset handling in the agent
      Stop, clean up, restart · lecture + practice
      
      
      Without reset handling, the driver keeps driving through reset and the monitor stitches the start of an old transfer to the end of a new one. In the video it reports a transfer to B1A4 that never completed. Wanted behaviour: at reset the driver stops immediately and drives defaults, the sequencer is cleared, the monitor drops its half-collected item, and all restart when reset ends.
      
      
      
        
        
      Each component declares implements cfs_apb_reset_handler. The agent never hard-codes which children need reset. Note: get_children() returns sub-components in the hierarchy, not subclasses.
      
      
      
      
      // driver: restartable loop
virtual task run_phase(uvm_phase phase);
  forever begin
    fork
      begin
        wait_reset_end();          // don't drive while in reset
        drive_transactions();      // saves process::self(); runs forever
        disable fork;              // kill anything drive_transactions spawned
      end
    join
  end
endtask

virtual function void handle_reset(uvm_phase phase);
  if(process_drive_transactions != null) begin
    process_drive_transactions.kill();             // stop mid-transfer, immediately
    process_drive_transactions = null;
  end
  vif.psel <= 0; vif.penable <= 0; ...             // signals to their defaults
endfunction

// sequencer: forget the half-finished handshake

  int objections_count;
  stop_sequences();                                 // kill running sequences, clear the queue
  objections_count = uvm_test_done.get_objection_count(this);
  if(objections_count > 0)
    uvm_test_done.drop_objection(this, "Dropping objections at reset", objections_count);
  start_phase_sequence(phase);                      // restart the default sequence, if any
endfunction

      1. X on PSEL at 5 ns: the first clock edge came before reset was asserted, and the driver now initializes signals only at reset. Fixed by asserting reset earlier (3 ns) or initializing at time 0.
      2. "get_next_item called twice without item_done": the killed driver never called item_done. Fixed by resetting the sequencer too.
      3. Test ended right after reset: resetting the sequencer also ended the test's sequences. The test must restart traffic after reset.
      4. Monitor reported a phantom transfer: fixed by killing its collect process at reset.
      
      
      Facts to remember
        
        
      • Reset start is detected asynchronously (@(negedge preset_n)). Reset end is detected synchronously (wait for a clock edge with reset released).
        • 
        
      • process::self() inside a fork gives a handle you can kill() later.
        • 
        
      • An interface class can be implemented by any number of classes alongside their normal parent: SystemVerilog's answer to multiple inheritance.
        • 
        
      • The test injects reset mid-transfer by waiting for the 3rd rising edge of PSEL, then 11 ns, then holding reset for 4 clocks.
        • 
      
      
      
      
        
      Q"How does your agent handle reset in the middle of a transfer?"
      The agent's run_phase loops: wait for reset assertion (async), call handle_reset on every child implementing the reset-handler interface class, wait for release (sync). The driver kills its drive process and drives idle values. The sequencer stops sequences and drops stray objections. The monitor kills its collect process. Coverage samples "transfer in progress at reset". After release, driver and monitor restart their loops.
      
        
      Q"Why must the sequencer be reset too?"
      The driver was killed between get_next_item and item_done, so the sequencer still thinks an item is outstanding. The next get_next_item errors ("called twice without item_done") or the sequence hangs. stop_sequences() clears that state.
      
        
      Q"What is an interface class and why use it here?"
      A class with only pure virtual methods that other classes implements, in addition to their one extends. Driver, monitor, sequencer and coverage have different UVM parents but share a handle_reset() contract. The agent loops over children, $casts to the interface class, and calls it. Adding a new resettable child needs no agent change.
      
        
      Q"Why not use UVM's reset_phase?"
      Run-time sub-phases assume reset happens once at the start and are awkward to jump back to. A mid-test reset needs every component to react at any time. An event-driven loop on the reset signal handles any number of resets and works with VIPs that don't use sub-phases. Most teams do it this way.
      
        
      Q"process::kill vs disable fork?"
      kill() terminates one process you hold a handle to, from anywhere (e.g. from the reset function). disable fork terminates all child processes of the current process, used here to clean up anything drive_transactions might have forked, so no zombie threads keep driving after reset.

      M1
      The MD protocol: extracting rules from a DUT spec
      No protocol document exists, so you build one · lecture
      
      
      Real-life skill
      "Not all the time your DUT will have standard interfaces." The recipe the lecturer gives: (1) identify the signals, (2) identify the rules that govern them, by reading the DUT's datasheet sentence by sentence. Each sentence like "it must remain constant until ready becomes high" becomes one rule, and later one assertion.
      
      
      
        
      RX side
      Agent = master, DUT = slave
      The agent drives valid, data, offset, size. The DUT answers with ready, err.
      
        
      TX side
      DUT = master, agent = slave
      The DUT drives valid, data, offset, size. The agent answers with ready, err.
      
        
      widths
      All from DATA_WIDTH
      offset = max(1, log2(W/8)) bits, size = log2(W/8)+1 bits. At W=32: offset 2 bits, size 3 bits.
      
      
      
      
      
        
      #RuleSource
      
        
          
      1DATA_WIDTH is a power of 2datasheet, ALGN_DATA_WIDTH
      
          
      2DATA_WIDTH ≥ 8
      
          
      3Once valid is high, it stays high until ready is highmd_*_valid
      
          
      4–5data is valid while valid is high · data constant until readymd_*_data
      
          
      6–7offset valid while valid · constant until readymd_*_offset
      
          
      8–10size valid while valid · constant until ready · size ≠ 0md_*_size
      
          
      11–12err valid only when valid & ready · err high only when valid & readymd_*_err
      
          
      13valid never X/Zadded by the verifier; "check with the designer and architect"
      
          
      14ready valid (not X) while valid is high
      
          
      15offset + size ≤ DATA_WIDTH/8
      
          
      16a transfer can't last forever (stuck threshold)
      
        
      
      
      The key distinction: the (W/8 + offset) % size == 0 rule is not a protocol rule. It's the Aligner's own behaviour. The protocol allows size 3 at offset 0; the Aligner rejects it and increments CNT_DROP. So the agent must be able to drive "Aligner-illegal" transfers, otherwise you can't test the rejection. Rule 15 (offset + size fits on the bus) is a physical limit, so the agent enforces it.
      
      
      Three transfer shapes to remember
        
        
      • No wait states: ready already high when valid rises, so the transfer starts and ends in one cycle.
        • 
        
      • With wait states: the slave holds ready low; the master keeps valid, data, offset and size constant.
        • 
        
      • With error: err high together with ready, e.g. offset 1, size 2 on the Aligner's RX side.
        • 
      
      
      
      
        
      Q"Your DUT has a custom interface with no spec. How do you build its VIP?"
      Extract the protocol from the DUT spec: list signals with direction and width, then turn every behavioural sentence into a numbered rule. Separate protocol rules (true for any device on this bus, go into the agent) from DUT rules (this device's behaviour, go into the model/scoreboard). Add implied rules (no X, bounded length) and confirm them with the designer. Then build the agent so it can also violate DUT-level rules, for negative testing.
      
        
      Q"Why shouldn't an agent refuse to send transfers the DUT considers illegal?"
      Because rejecting them is DUT behaviour you must verify (error response, counter, interrupt). The agent's legality must match the protocol, not the DUT. Bake the DUT's rules into the agent and the error-handling logic can never be stimulated.
      
        
      Q"Who decides an implied rule like 'offset + size ≤ bus bytes' is real?"
      The designer and system architect, not the verifier. Write the assumption down, ask, and record the answer in the spec or vPlan. In this project the rule isn't in the datasheet; the RTL enforces it on CTRL writes but not on the RX port. That's a gap you only find by asking (see the senior course).

      Agent architecture: one family, two aspects
      What's shared, what's split · lecture
      
      
      
        
      
      
      
      Why the split falls where it does
        
        
      • Monitor and coverage are common: observing a bus is the same whichever side drives it.
        • 
        
      • The driver is split: the base holds the loop, reset handling and process control; subclasses implement only drive_transaction().
        • 
        
      • The config is split because each side may need its own knobs (e.g. ready value at reset).
        • 
        
      • DATA_WIDTH is a parameter, not a `define like APB. It's more flexible (two widths in one simulation), but every class that touches the interface must carry it.
        • 
      
      
      
      
        
      Q"How would you structure a VIP that supports both master and slave modes?"
      Shared interface, monitor, coverage and sequencer base. Driver, drive item, config and agent each get a common base and two subclasses. The agent subclass uses factory instance overrides to pick its driver, config and sequencer. The env just instantiates agent_master or agent_slave. Shared code is written once, and a fix applies to both modes.
      
        
      Q"`define vs parameter for a bus width?"
      A `define is global and compile-time: simple, but one value for the whole simulation. A parameter is per instance, so two agents of different widths can coexist. The cost is that every dependent class must be parameterized too, and mistakes cause type-mismatch compile errors (which the course runs into). Rule of thumb: parameters for reusable VIP, defines for one-off code.

      The parent's build_phase calls create() on its children, and the override must already exist at that moment. A component's constructor runs while its parent is in build, before this component's own build_phase. Overrides registered after the create silently do nothing.

The agent code stays generic and doesn't need to know whether it's RX or TX.
      
      
      
      
    
      

    
    
      
      
      M4
      Master driving: items without parameters
      A byte list, a parameter firewall, a common driver · lecture + practice
      
      
      The design problem
      A natural item would have bit [DATA_WIDTH-1:0] data, offset, size. But items are created in sequences, outside the agent, so every sequence would need the width parameter too. The fix: store the bytes as a list (rand bit[7:0] data[$]). Size becomes data.size() and the width disappears from the item.
      
      
      class cfs_md_item_drv_master extends cfs_md_item_drv;

      Q"How do you keep a parameter out of sequences?"
      Make the item width-independent (a byte list), put width-dependent constraints in the sequence using a value read at pre_randomize, and type p_sequencer as a non-parameterized base whose virtual get_data_width() is implemented by the parameterized subclass. Sequences then compile once for any width.
      
        
      Q"Where should constraints live: item or sequence?"
      The item has universal defaults (soft, safe at any configuration) and true invariants (size > 0). The sequence has context-dependent limits (bus width, DUT state) and scenario intent. The item stays reusable, and each sequence can disable soft defaults with constraint_mode(0).
      
        
      Q"What is pre_randomize used for?"
      It's called automatically just before the solver runs. Use it to compute non-random state that constraints depend on: here, reading the bus width from the sequencer into a local variable. It also avoids calling functions inside constraints, which one simulator rejected (M7).
      
      
      
      
    
      

    
    
      
      
      M5
      The MD monitor: two broadcasts per transfer
      begin_tr / end_tr / is_active, and sampling 1 ns late · lecture + practice
      
      
      Unlike APB, the MD monitor calls output_port.write(item) twice: at the start of a transfer (so the slave can respond and the model can predict early) and at the end (complete with response and length). Subscribers tell them apart with uvm_transaction's timing API.
      
      
      item.offset = vif.offset;                         // known at the START
for(int i = 0; i < vif.size; i++)
  item.data.push_back((vif.data >> ((item.offset + i) * 8)) & 8'hFF);
void'(begin_tr(item));                            // sets begin_time → is_active() == 1
output_port.write(item);                          // broadcast #1: "a transfer started"

@(posedge vif.clk);
while(vif.ready !== 1) begin @(posedge vif.clk); item.length++; end
item.response = cfs_md_response'(vif.err);
end_tr(item);                                     // sets end_time → is_active() == 0
output_port.write(item);                          // broadcast #2: "it finished"
      
      
      
        
        
      With zero wait states, ready is already high when valid rises, so start and end land in the same cycle. If the monitor saw "start" exactly at the edge, the slave would have no time to choose a response. Sampling sample_delay_start_tr (1 ns) after the edge reports the start in the cycle before the handshake completes.
      
      
      
      
      Facts to remember
        
        
      • The monitor item has prev_item_delay, length, data (byte list), offset and response.
        • 
        
      • get_end_time() returns −1 while active, so convert2string prints the end time only when !is_active().
        • 
        
      • Video check: item begins at 116 ns (the edge at 115 plus 1 ns) and ends at 125 ns.
        • 
        
      • The 1 ns is a config field, not hard-coded: "having this one nanosecond here is not ideal".
        • 
        
      • begin_tr/end_tr also enable transaction recording: simulators can draw items as "bubbles" on the waveform. That's not available on EDA Playground; the lecturer wrote an article, "Debugging tip: look at the bubbles".
        • 
      
      
      
      Senior note: because every transfer is written twice, every subscriber must filter on is_active(). Your MD coverage doesn't, so it samples each transfer twice, the first time with a default OKAY response and length 1. That inflates those bins. (Senior course, Module 8.)
      
      
      
        
      Q"Why would a monitor publish a transaction at its start?"
      Reactive agents and predictive models need to act during the transfer: a slave must decide ready/err latency based on the request; a model can predict the response or occupancy right away. End-only publication works for passive checking, but not for reacting.
      
        
      Q"How do subscribers tell the start event from the end event?"
      With uvm_transaction::is_active(): true after begin_tr and before end_tr. Alternatives are two separate analysis ports, or a phase field in the item. Note that both writes pass the same object handle, which keeps changing, so subscribers that store it must clone it.
      
        
      Q"Why sample 1 ns after the clock edge? Isn't that a hack?"
      It gives the testbench a decision window in the same cycle a transfer starts, needed for zero-latency responses. It's the same thing as a clocking-block input skew, done by hand. Making it a config field keeps it adjustable. The risk: it must be smaller than the clock period and robust to timescale changes.
      
      
      
      
    
      

    
    
      
      
      M6
      The reactive slave: answering the DUT
      The hardest part of the course so far · lecture + practice
      
      
      Why a normal sequence fails here
      The slave item has length (cycles before ready; 0 = one-cycle transfer), response (err) and ready_at_end (keep ready high after the transfer, like a "FIFO not full" signal). If a sequence sends such items at random times, two things break. It decides the response before it knows what the DUT is sending (it can't answer an offset-2 size-1 transfer with OKAY on purpose). And a length-0 item arriving mid-transfer looks identical to a longer one, so you lose control of timing.

uvm_tlm_fifo#(cfs_md_item_mon) pending_items;          // new("pending_items", this, 1): one transfer at a time

    if(pending_items.is_full())
      `uvm_fatal("ALGORITHM_ISSUE", "FIFO is full - no sequence pulls from it?")
    void'(pending_items.try_put(item));
  end
endfunction
virtual function void handle_reset(uvm_phase phase);
  super.handle_reset(phase); pending_items.flush();     // forget requests on reset
endfunction

  p_sequencer.pending_items.get(item_mon);              // blocks until the DUT starts a transfer

      Q"Design a slave agent whose response depends on the request."
      The monitor publishes the request at its start. An analysis imp in the slave sequencer pushes it into a TLM FIFO. A forever "responder" sequence blocks on get(), then randomizes a response item constrained by the request (e.g. err for illegal offset/size, latency from a distribution) and sends it to the driver. Tests change behaviour by overriding the responder sequence. The FIFO depth matches the protocol's maximum outstanding requests (1 here).
      
        
      Q"Why put the analysis imp in the sequencer rather than the sequence?"
      Analysis imps are TLM components that need a uvm_component parent and must be connected in connect_phase. Sequences are short-lived uvm_objects created at run time. The sequencer is a component, lives in the agent next to the monitor, and every sequence reaches it through p_sequencer.
      
        
      Q"What is uvm_tlm_fifo and which methods matter?"
      A bounded FIFO component with TLM put/get interfaces. Blocking put/get (tasks), non-blocking try_put/try_get (return success), peek, is_full, is_empty, used, flush. The lecturer notes that some methods appear in the source code but not the HTML reference: read the source.
      
        
      Q"What's variable hiding and when is it acceptable?"
      A subclass declares a member with the same name as a parent member. Inside the subclass the new one is used; the parent's code still sees its own. Here it gives a more specific type for the same object (filled via $cast). It works, but it's error-prone: two handles must be kept in sync. A typed getter or a parameterized base is cleaner.

      Expect it: language support differs in corners (system functions in constant contexts, functions in constraints, formatting in elaboration tasks). Keep a regression on every supported simulator, stick to widely supported constructs, isolate tool workarounds behind macros (`ifdef VCS…), and prefer simple equivalent forms like the $log10/$clog2 trick.

Add a cover property for "valid high, ready low" to prove the scenario happens in regressions.

      Q"Your team builds a new agent every project. How would you speed that up?"
      Two steps. (1) A base-class library: parameterized base agent, config, driver, monitor, sequencer and coverage that implement reset handling, active/passive, vif plumbing and wiring once. (2) A code generator: templates for common agent shapes (master-only, master+slave) and a script that stamps out the files with the right prefixes. Engineers then write only the protocol: items, drive and collect logic, coverage. Fewer lines, fewer copy-paste bugs, consistent structure.

      No. UVM provides generic roles (uvm_driver has no reset handling and no idea where the vif lives). The extension layer encodes your team's conventions on top: how reset works, how config is passed, how checks and coverage are switched. It's the layer every mature DV team ends up building.

      RAL: a mirror of the Aligner's registers
      
      
      The Aligner has four registers: CTRL, STATUS, IRQEN and IRQ. This chapter models them with the UVM register layer (RAL) and connects the model to the APB agent twice. The monitor path keeps the model's copy (the "mirror") up to date and checks every read and every APB response. The sequencer path lets tests write CTRL.write() instead of building APB sequences. The chapter ends with the course's first real bug, in both the RTL and the spec.
      
      
      
        
        
      Every access starts on path ① or in a plain APB sequence, and the monitor then sees it on path ②. That's why the mirror stays correct without the register model predicting its own writes: auto-predict stays off, which is the default.
      
      
      
    
      

    
    
      
      
      R1
      What is a register model?
      Introduction to the UVM register layer · lecture
      
      
      Think of it like…
      You keep a notebook of what's in your friend's lunchbox. When you see them put an apple in (a write), you note "apple". When they open it in front of you (a read), you check it matches your note. If it says banana, something's wrong. The register model is that notebook for the chip's registers. Its notes are called the mirror.
      
      
      
        
      job 1
      Track writes
      Every OK write seen on APB updates the mirrored field values. For example, 0x101 to address 0 sets SIZE=1 and OFFSET=1.
      
        
      job 2
      Check reads
      Every read compares the RTL's data with the mirror. A mismatch raises an error automatically, with no code in the scoreboard.
      
        
      job 3
      Abstract the tests
      CTRL.write(), read() and update() replace APB sequences. If APB is swapped for AHB or I2C, you change the agent and the tests stay the same.
      
        
      helper
      The predictor
      Translates monitor items into register operations, and here also checks that each APB response (OKAY or SLVERR) is the expected one.

      Q"Mirrored vs desired value?"
      Mirrored is what the testbench believes the DUT contains; it's updated by observed bus traffic or predict() and used to check reads. Desired is what the test wants the DUT to contain; it's changed by set()/randomize() and pushed by update(). update() only issues a bus access when needs_update() sees desired ≠ mirrored.
      
        
      Q"When do you set volatile = 1, and what does it cost?"
      When the hardware changes the field in ways you can't predict cycle-accurately, such as a free-running counter. The cost is that read checks are skipped for that field, so you lose checking. The Aligner keeps CNT_DROP non-volatile and models it precisely instead; your model calls CNT_DROP.predict(+1) on every dropped transfer, saturating at 255.
      
        
      Q"Why is 'reset' an associative array?"
      Designs can have several resets (HARD, SOFT, warm…) with different reset values per field. Each kind is a key. configure() fills "HARD"; set_reset(val, "SOFT") adds others; reg_block.reset("SOFT") applies one.
      
        
      Q"What does individually_accessible mean?"
      Whether the bus can access just that field without touching its neighbours, for example byte-enabled writes where the field fills whole byte lanes. APB without PSTRB always writes the full register, so it's 0 for every Aligner field, and a field-level write() becomes a full-register write.

        •

      Q"Why must custom members of a uvm_reg be uppercase?"
      uvm_reg already has hundreds of lowercase members (read, write, get, set, reset, predict…). A field called reset or a method called write would silently shadow them and break the register layer. Uppercase is guaranteed collision-free. Register generators follow the same rule.
      
        
      Q"Map rights vs field access: what's the difference?"
      Field access (RW, RO, WO, W1C, RC, …) defines per-field behaviour on read and write. Map rights (RW, RO, WO only) describe the whole register as seen through that map. STATUS is RO in the map because every field is RO. IRQ is RW in the map even though its fields are W1C, because it can be written.
      
        
      Q"Would you hand-write these classes on a real project?"
      Rarely. Register descriptions usually live in IP-XACT, SystemRDL or a spreadsheet, and a generator emits the RAL classes, RTL register file, C headers and documentation from one source. Hand-writing them once, as here, is how you learn what the generator produces and how to debug it.

      Q"Front-door vs back-door access?"
      Front door goes through the real bus via the map's sequencer and adapter: realistic, takes simulation time, exercises the bus logic. Back door reads or writes the RTL storage directly through HDL paths (uvm_hdl_deposit/read): zero time, used for fast initialization, and for checking that the front door wrote the right flops. It needs correct hdl_paths, and bypasses side effects such as W1C or clear-on-read logic.
      
        
      Q"What does lock_model() do and when do you call it?"
      After building the whole hierarchy, on the top-level block only. It prevents further structural changes and builds the internal address-to-register lookup tables used by get_reg_by_offset() and the predictor. Forgetting it makes those lookups fail, and some versions error when you start using the model.
      
        
      Q"Why check reg_block == null before creating it?"
      Vertical reuse. At block level this env owns the register model. At subsystem or SoC level, the top env builds the full block hierarchy (this block becomes a sub-block at some base address) and assigns the pointer before build. The module env must use that shared instance, not create its own private one.

      Q"Explicit vs implicit (auto) vs passive prediction?"
      Implicit: map.set_auto_predict(1), so the model updates itself when its own API completes an access. It's simple, but misses traffic from other masters or plain sequences. Passive: no sequencer connected at all; only the monitor path runs, typical at SoC level where the register bus is driven by a CPU. Don't enable auto-predict together with an explicit predictor, or you predict twice.

      A custom predictor that also checks the response
      Custom register predictor · lecture + practice
      
      
      Two jobs. Filter: only OK accesses reach the mirror. Check: the RTL's OK/ERROR answer can be wrong too, so compare it with an expected response computed from the datasheet rules.
      
      
      class cfs_algn_reg_predictor#(type BUSTYPE = uvm_sequence_item)
      extends uvm_reg_predictor#(.BUSTYPE(BUSTYPE));   // stay generic
  cfs_algn_env_config env_config;                     // has_checks, algn_data_width

  virtual function void write(BUSTYPE tr);            // bus_in's imp calls this
    uvm_reg_bus_op operation;
    adapter.bus2reg(tr, operation);
    if(env_config.get_has_checks()) begin
      cfs_algn_reg_access_status_info exp = get_exp_response(operation);
      if(exp.status != operation.status)
        `uvm_error("DUT_ERROR", $sformatf("Mismatch ... expected: %0s, received: %0s on access: %0s - reason: %0s",
                   exp.status.name(), operation.status.name(), tr.convert2string(), exp.info))
    end

      Q"The default predictor updated the mirror on a SLVERR write. How do you fix it?"
      Extend uvm_reg_predictor, override the public virtual write() (the imp method behind bus_in), convert the item with adapter.bus2reg(), and call super.write(tr) only when status == UVM_IS_OK. Keep BUSTYPE as a parameter so the predictor stays bus-independent.
      
        
      Q"Why not just trust PSLVERR?"
      The response is DUT output, so it's something to verify, not an input. If the RTL wrongly returns OK for an illegal CTRL write, filtering alone would happily update the mirror and you'd never notice the missing error path. Computing the expected response from the spec turns every APB access into a checked access.
      
        
      Q"How do you find which register an address maps to, and its rights?"
      map.get_reg_by_offset(offset, read) returns the uvm_reg or null. map.get_reg_map_info(rg) returns a uvm_reg_map_info whose rights string is what you passed to add_reg(). Field position comes from get_lsb_pos() and get_n_bits().

      Q"Walk me through what happens when a test calls CTRL.write(status, 'h202)."
      The register builds a uvm_reg_item and asks its map. The map turns it into a uvm_reg_bus_op (kind=WRITE, addr=0x0 from the map, data), calls adapter.reg2bus() to get a cfs_apb_item_drv, and runs start_item/finish_item on the sequencer from set_sequencer(). The driver drives APB. The map then calls bus2reg() on the same item to fill in the status. Meanwhile the monitor sees the transfer, and the explicit predictor checks the response and updates the mirror.
      
        
      Q"Why does bus2reg() need to handle the driver item too?"
      After the access, the map calls adapter.bus2reg() on the item it sent (or on the response, if provides_responses = 1) to get the final status and read data. Without a branch for cfs_apb_item_drv, the $cast fails and the fatal fires.
      
        
      Q"Can you trust the status returned by CTRL.write() in this testbench?"
      No. The driver item has no response field, so bus2reg reports UVM_IS_OK even when PSLVERR was 1. The predictor's check is what catches bad responses. To make the API status real, have the driver copy PSLVERR (and PRDATA) back into the item, or send a response with provides_responses = 1, and translate it in bus2reg. This is a good senior-level observation to bring up.
      
        
      Q"write() vs update() vs set()?"
      set() only changes desired values; no bus traffic. update() writes the register only if desired ≠ mirrored, combining all field values into one access. write() always performs the access with the full value you give, so you need the bit layout. Use set+update in tests, so the tests don't depend on bit positions.
      
      
      
      
    
      

    
    
      
      
      R8
      The first real bug: SIZE 5 on a 4-byte bus
      From the bus-sequencer practice video
      
      
      With the first constraint in place, CTRL.randomize() produced SIZE = 5, OFFSET = 1. It satisfies the datasheet formula, (4 + 1) % 5 = 0, and the RTL accepted it with OKAY. But you can't output 5 bytes on a 4-byte bus.
      
      
      
        
      StepWhat happened
      
        
          
      1. SmellA legal-by-formula value that's physically impossible. The read-back returns 0x105, so the RTL really stored it.
      
          
      2. ProvokeStart the TX responder, then send two 4-byte RX transfers.
      
          
      3. CatchThe MD interface SVA fires: size + offset is greater than the data width (in cfs_md_if.sv). The RTL tried to output a size-5 transfer.
      
          
      4. ConfirmTemporarily comment out the assertion and look at the waves: the TX output has size 5. Restore the assertion afterwards.
      
          
      5. Root causeThe spec is incomplete (it lacks OFFSET + SIZE ≤ bytes), so the RTL is too.
      
          
      6. Fix all four placesDatasheet v1.1 · cfs_regs.v returns SLVERR · predictor rule 4c · constraint in legal_size_offset.
      
        
      
      
      Lessons the lecturer draws
        
        
      • Finding RTL and spec bugs while still building the environment is normal. The concept engineer and the designer both missed this case.
        • 
        
      • The assertion caught it, and it was written "because it made sense", not because the spec required it. Your own protocol knowledge is a checker too.
        • 
        
      • After the fix the predictor fired immediately ("expected OK, got NOT_OK") until rule 4c was added. A model that disagrees with fixed RTL is a model bug.
        • 
        
      • In a real project the designer fixes the RTL; here the lecturer does it so the course can continue.
        • 
      
      
      
      Interview answer: "tell me about a bug you found"
      "While integrating the register model, I randomized the control register under the datasheet's alignment formula. One seed produced SIZE 5, OFFSET 1 on a 32-bit bus. The formula allowed it and the RTL accepted it. Sending traffic tripped an interface assertion I'd added on the output: size plus offset exceeded the bus width. The spec was missing a constraint, OFFSET + SIZE ≤ bus bytes, so the RTL didn't reject the write. We updated the spec, the RTL now returns SLVERR, and I added the rule to the predictor and to the register constraints. Constrained-random found a case nobody had written down."
      
      
      
        
      Q"The spec and the RTL agree, but you think they're both wrong. What do you do?"
      Build a minimal reproducing test and waveform. Explain the physical impossibility (5 bytes can't fit a 4-byte bus) and its consequence (an illegal output transfer). Then raise it with the spec owner and the designer together, because only the spec owner can decide the intended behaviour. Don't silently "fix" your model to match the RTL, and don't wait: track it as a spec bug with an owner.
      
        
      Q"Why did constrained-random find this when directed tests didn't?"
      Directed tests encode what people already thought of, which here were exactly the spec's rules. Random generation within the stated rules explored combinations nobody enumerated, and an independent checker (the interface SVA) judged the result on physical grounds. Good random tests need both broad stimulus and checks that don't share the spec's blind spot.

      Register field callback: CLR clears CNT_DROP
      Register field callback · lecture + practice
      
      
      A callback is "a function stored as data and designed to be called by another function". In SystemVerilog that means a method inside a class, plus a stored handle to an object of that class. The function that calls it is uvm_reg_field::predict(), which calls post_predict() on every callback registered for the field.
      
      
      class cfs_algn_clr_cnt_drop extends uvm_reg_cbs;   // uvm_reg_cbs → uvm_callback → uvm_object
  uvm_reg_field cnt_drop;                           // pointer to STATUS.CNT_DROP
  virtual function void post_predict(input uvm_reg_field fld, input uvm_reg_data_t previous,
                                     inout uvm_reg_data_t value,   // INOUT: you may change it
                                     input uvm_predict_e kind, input uvm_path_e path, input uvm_reg_map map);
    if(kind == UVM_PREDICT_WRITE && value == 1) begin
      void'(cnt_drop.predict(0));   // model the hardware side effect
      value = 0;                    // CLR is a pulse: don't leave 1 in the model
    end
  endfunction
endclass

      How the practice test proves it
        
        
      • Send two illegal RX transfers (size 3). The RTL drops both, so CNT_DROP = 2 in the RTL. Reading STATUS gives a mismatch, because the model doesn't count drops yet.
        • 
        
      • As a temporary hack, the test calls CNT_DROP.predict(2). The lecturer labels it "Don't do this in a real project": prediction is the model's job (your final cfs_algn_model.sv does it).
        • 
        
      • Write CLR = 1 and read again: the RTL returns 0 but the mirror still says 2, which is a mismatch. Add the callback: the mismatch is gone, and the log shows "Clearing …CNT_DROP" at UVM_HIGH.
        • 
        
      • uvm_callbacks#(T, CB)::add(obj, cb, ordering): T = object type (uvm_reg_field), CB = callback type. ordering decides the order when several callbacks are attached.
        • 
      
      
      
      
        
      Q"How do you model a register side effect, e.g. writing one field clears another?"
      A uvm_reg_cbs subclass whose post_predict() detects the triggering write and calls predict() on the affected field, attached with uvm_callbacks#(uvm_reg_field, MyCb)::add(field, cb). It runs on every predicted write, whether from the explicit predictor or auto-prediction, so the side effect follows any source of traffic. Alternatives are a custom field class overriding do_predict, or handling it in the reference model; callbacks keep it local to the register layer.
      
        
      Q"Why set value = 0 inside post_predict?"
      CLR is a self-clearing pulse in the RTL; it never holds 1. If the mirror stored 1, the model would disagree with the hardware, and update() logic based on desired vs mirrored would behave oddly the next time someone sets CLR. Because value is inout, the callback can correct what gets stored.
      
        
      Q"Name other UVM callback uses."
      Driver or monitor hooks such as error injection (`uvm_register_cb / `uvm_do_callbacks), register pre/post read/write hooks (pre_write, post_read in uvm_reg_cbs), and report catchers (uvm_report_catcher, a callback that demotes or rewrites messages). The trade-off versus factory overrides: callbacks add behaviour to existing instances without replacing the class.

      Model, scoreboard, coverage, virtual sequencer
      
      
      The environment's "brain". The model watches the Aligner's inputs and predicts its three outputs: the RX response, the TX transfers and the IRQ pulses. The scoreboard compares those predictions with what the agents see. A coverage component records which split scenarios were exercised, and a virtual sequencer coordinates the APB, RX and TX agents from one sequence. The most valuable part for interviews is the middle of the chapter: three synchronization bugs in the testbench itself, and how each was debugged and fixed.
      
      
      
        
        
      The model copies the datasheet's block diagram (RX controller → RX FIFO → controller → TX FIFO → TX controller), not the RTL code. Dashed boxes are "logic clouds": tasks and functions inside one cfs_algn_model component, not separate classes. Every push or pop also updates RX_LVL/TX_LVL and the IRQ flags in the register model.

      Lecturer's advice
        
        
      • Read the datasheet's "Flow Control" and "Interrupt requests" chapters before modeling. Knowing the spec thoroughly is part of the job.
        • 
        
      • The model's structure mirrors the spec's block diagram, so each piece of logic is easy to locate and debug.
        • 
        
      • FIFOs use uvm_tlm_fifo because its blocking put()/get() model back-pressure for free.

      Q"What's the difference between a reference model and a scoreboard?"
      The model predicts: it consumes DUT inputs and produces expected outputs, and it holds behavioural state (FIFOs, buffer, registers). The scoreboard compares: it pairs expected with actual, handles ordering and timing (queues, watchdogs) and reports mismatches. Keeping them separate means you can swap the model (for example for a C model through DPI) or reuse the comparison logic.
      
        
      Q"How do you decide the model's structure?"
      Start from the spec's functional blocks and their observable effects, not the RTL's implementation. Model at transaction level where the spec allows it, and add timing only where an output depends on it (here, the IRQs depend on FIFO levels). Keep it as untimed as possible, because every bit of timing you add is a chance to get out of sync with the RTL.

      Q"Why `uvm_analysis_imp_decl?"
      An analysis imp calls a method named write() on its parent. With two inputs of the same type you'd need two write() methods, which SystemVerilog forbids. The macro declares a new imp class, uvm_analysis_imp_in_rx, that calls write_in_rx() instead. The alternative is uvm_tlm_analysis_fifos with a run_phase that calls get(), which changes the timing semantics.
      
        
      Q"Analysis port vs imp vs export?"
      The port is the initiator; it calls write() and can broadcast to zero or more subscribers. The imp is the terminal, implemented by the component that owns the write(). An export forwards through hierarchy, for example an agent exposing its monitor's port. write() is a function, so subscribers must not block. That's why the model starts tasks with fork/join_none.

protected virtual function void inc_cnt_drop(cfs_md_response response);
  uvm_reg_data_t max_value = ('h1 << reg_block.STATUS.CNT_DROP.get_n_bits()) - 1;   // 255
  if(reg_block.STATUS.CNT_DROP.get_mirrored_value() < max_value) begin         // saturate
    void'(reg_block.STATUS.CNT_DROP.predict(reg_block.STATUS.CNT_DROP.get_mirrored_value() + 1));
    if(reg_block.STATUS.CNT_DROP.get_mirrored_value() == max_value) set_max_drop();
  end
endfunction
      
      
      Behaviour being modeled
        
        
      • Illegal: size 0, (bytes + offset) % size ≠ 0, or offset + size > bytes (the rule added after the R8 bug). The RTL drops the transfer, answers ERR and increments CNT_DROP.
        • 
        
      • CNT_DROP saturates at 255. The 254 → 255 step sets IRQ.MAX_DROP. If IRQEN.MAX_DROP is 1, an irq pulse is expected.
        • 
        
      • max_value comes from get_n_bits(), not a hard-coded 255, so the model follows the register definition if it changes.
        • 
        
      • This is the "proper" place for the CNT_DROP.predict() that R9's test temporarily hacked in.
        • 
      
      
      
      Connects to a real bug. In this project's RTL, the MAX_DROP source never reaches the irq output (found in the senior Aligner lab). The model above predicts the pulse, and the IRQ check in C10 is what flags the missing one. You need a test that drops 255 transfers with IRQEN.MAX_DROP = 1, which is what the rx_err exercise does.
      
      
      
        
      Q"How do you model a saturating hardware counter in RAL?"
      Keep the field non-volatile and call predict() from the model on each event, with a guard at the maximum computed from get_n_bits(). Trigger side effects (like the MAX_DROP flag) on the transition to max, not on every event at max, which matches the "becomes 255" wording in the spec.
      
        
      Q"When should the model predict the RX response: at the start or the end of the transfer?"
      At the start, as soon as the inputs are known (it only depends on offset and size). But the OKAY prediction is only sent after the RX FIFO accepts the item, because a full FIFO delays the RTL's ready. The scoreboard compares at the end of the transfer. Predicting early and comparing late is a common, robust pattern.

      The "_nb + process pointer" pattern used throughout this chapter
        
        
      • The task does the timed work. A function xxx_nb() starts it with fork/join_none, because analysis write()s are functions.
        • 
        
      • A process pointer lets handle_reset() kill the task mid-flight, and lets a null check catch a second, impossible instance (the MD protocol never overlaps transfers).
        • 
        
      • kill_process(ref process p): kill it if it's not null, then set it to null. ref is required so the caller's pointer is cleared.
        • 
        
      • IRQ flags are sticky: they stay 1 after the condition goes away, until software writes 1 to clear (W1C, as in R3).
        • 
        
      • Afterwards the lecturer made rx_fifo protected: internal state shouldn't be public.
        • 
      
      
      
      
        
      Q"How do you model back-pressure in a transaction-level model?"
      Use a bounded blocking channel, for example uvm_tlm_fifo with the DUT's depth. The producer's put() blocks while it's full, so the "accepted" event (here, the OKAY response) happens only when space frees up, just like the RTL's ready. No cycle counting is needed in the model.
      
        
      Q"Why can't you just call a task from write()?"
      write() is a function, and functions can't consume time or call blocking tasks. Wrap the call in fork … join_none inside a function. Keep a handle (process::self()) so reset can kill it and you can assert that there's only one instance.

protected virtual task build_buffer();
  cfs_algn_vif vif = env_config.get_vif();
  forever begin
    int unsigned ctrl_size = reg_block.CTRL.SIZE.get_mirrored_value();
    if((buffer.sum() with (item.data.size())) <= ctrl_size) begin   // not enough bytes yet
      cfs_md_item_mon rx_item;
      pop_from_rx_fifo(rx_item);    // get() + RX_LVL-- (== 0 → set_rx_fifo_empty())
      buffer.push_back(rx_item);
    end
    else @(posedge vif.clk);        // enough: wait a cycle, let align() consume
  end
endtask
      
      
      Infrastructure added
        
        
      • A new cfs_algn_if with just clk for now (it later gains reset_n, irq and four FIFO probes). Because it's an interface, its file is included outside the package.
        • 
        
      • A types file holds typedef virtual cfs_algn_if cfs_algn_vif;. The testbench puts the vif in config_db, the env gets it into env_config, and start_of_simulation checks that it's set.
        • 
        
      • build_buffer_nb() is called at the end of handle_reset(): kill on reset, restart afterwards.
        • 
        
      • buffer.sum() with (item.data.size()) is the SystemVerilog array-reduction idiom for "bytes in the buffer".
        • 
      
      
      
      
        
      Q"Why does a forever loop that never waits hang the simulator?"
      It never yields, so simulation time can't advance. Every path through a forever loop must block: here either pop_from_rx_fifo (which blocks in get() when empty) or @(posedge clk). That's why the else branch exists.
      
        
      Q"Why does the model need a clock at all?"
      The data path could be untimed, but polling loops need a time base, and later the IRQ prediction needs cycle-level alignment with the RTL (C11–C13). A minimal "env interface" carrying the clock (plus probes later) is the usual approach.
      
      
      
      
    
      

    
    
      
      
      C6
      align() and split(): the core algorithm
      Model align logic · lecture + practice
      
      
      The candy packer from Level 2, as code. While the buffer holds at least SIZE bytes, build a TX item at OFFSET. Take whole buffer items while they fit. When one doesn't fit, split it, push both halves back to the front (second half first), and loop again.
      
      
      forever begin
  int unsigned ctrl_size = reg_block.CTRL.SIZE.get_mirrored_value();
  uvm_wait_for_nba_region();                    // let build_buffer() push first at this edge
  if(ctrl_size <= (buffer.sum() with (item.data.size()))) begin
    while(ctrl_size <= (buffer.sum() with (item.data.size()))) begin
      tx_item = create; tx_item.offset = CTRL.OFFSET;
      while(tx_item.data.size() != ctrl_size) begin
        buffer_item = buffer.pop_front();
        if(tx_item.data.size() + buffer_item.data.size() <= ctrl_size) begin
          tx_item.data += buffer_item.data;         // whole item fits
          if(tx_item.data.size() == ctrl_size) push_to_tx_fifo(tx_item);
        end else begin
          num_bytes_needed = ctrl_size - tx_item.data.size();
          split(num_bytes_needed, buffer_item, splitted_items);
          buffer.push_front(splitted_items[1]);     // remainder goes back first...
          buffer.push_front(splitted_items[0]);     // ...so the exact-fit half is popped next
          port_out_split_info.write(info);          // → coverage (C14)
        end
      end
    end
  end else @(posedge vif.clk);
end
      
      
      split(num_bytes, item, ref items[$])
        
        
      • It's an algorithm error (fatal) if num_bytes == 0 or num_bytes ≥ item.data.size(), since there'd be nothing to split.
        • 
        
      • Half 0: same offset, first num_bytes bytes. Half 1: offset + num_bytes, the remaining bytes.
        • 
        
      • Both halves copy prev_item_delay, length, response, and the begin/end times from the original.
        • 
        
      • Check from the practice log: SIZE 1, OFFSET 1, one 4-byte RX item → four TX pushes FE, 60, B4, 3B, which match what the TX monitor later reports.
        • 
      
      
      
      
        
      Q"What does uvm_wait_for_nba_region() do and why use it here?"
      It waits until the current time step's NBA region has passed (implemented with a nonblocking update and a wait), so the code resumes after same-time activity has settled. Here it orders two threads that both wake at the same clock edge: build_buffer pushes first, and align then sees the updated buffer. Without it, the result depends on the scheduler's arbitrary thread order, a classic same-time race.
      
        
      Q"Why push the split halves back in reverse order?"
      push_front prepends, so pushing half 1 and then half 0 leaves the buffer as [half0, half1, …]. The next pop_front returns half 0, which by construction fits exactly and completes the TX item. Byte order is preserved, which is the Aligner's main promise.
      
        
      Q"What would you randomize to stress this algorithm?"
      Every legal (SIZE, OFFSET) setting crossed with RX size and offset sequences that force splits at every possible num_bytes_needed, reconfiguring CTRL while data is buffered, and back-to-back traffic with a slow TX side so both FIFOs fill. Then measure it with exactly the split coverage built in C14.

      foreshadowing
      "Problems with synchronization"
      The data path already matches the RTL byte for byte. The lecturer hints that IRQ prediction won't, which C10–C13 cover.
      
      
      
      
      
        
      Q"uvm_event vs SystemVerilog event?"
      A uvm_event is an object, so it can be passed around, stored in a pool (uvm_event_pool, shared by name), and reset. It can carry data with the trigger, supports callbacks, and offers both edge (wait_trigger) and persistent (wait_ptrigger, avoids the same-time race when the trigger fires just before the wait) styles. A plain ->/@ event can miss a trigger that happens in the same time step before the wait starts.
      
        
      Q"Why wait for the TX transfer to complete before popping the next item?"
      The RTL's TX controller holds one item until the slave asserts ready, then pops the next. Mirroring that hand-off keeps the model's TX_LVL, and therefore its TX empty/full flags, close to the RTL's. The data order alone wouldn't need it.

      • The env connects five ports (3 from the model, 2 from the agents) plus the env_config pointer.

      Q"Design a scoreboard for a DUT with latency."
      Store expected transactions in an ordered queue (or per-ID associative arrays if the DUT can reorder). On each actual: pop and compare, with an error if nothing was expected. Add a per-entry timeout so a stuck DUT fails instead of hanging, bound the queue depth to catch runaway prediction, check that every queue is empty in check_phase (end-of-test leftovers), and clear everything on reset.
      
        
      Q"In-order vs out-of-order scoreboards?"
      In-order: a FIFO compare, as here, valid because the Aligner preserves order. Out-of-order: key expected items by ID or address in an associative array and match on arrival. You still need timeouts, and usually a way to detect duplicates. Pick based on the spec's ordering guarantees, never on what the RTL happens to do.

      Details
        
        
      • The watchdog task: repeat(threshold) @(posedge vif.clk); then DUT_ERROR "expected from time %t, not received after N clocks". It's killed when the matching actual arrives.
        • 
        
      • A queue of process pointers (one per pending entry), not a single pointer. The _nb() wrapper fatals if the queue is unexpectedly empty when a watchdog ends.
        • 
        
      • The TX check is the same structure with exp_tx_items. It compares data (the whole queue, so the size too) and offset.
        • 
        
      • Forced-failure test: make the model send ERR instead of OKAY and confirm "expected ERR, received OKAY", then revert.
        • 
        
      • exp_rx_response_threshold, exp_tx_item_threshold and exp_irq_threshold live in env_config (default 10, with getters and setters).
        • 
      
      
      
      Bug hunt in your scoreboard. write_in_agent_rx and write_in_agent_tx never check that something is expected. If the RTL produces a TX transfer the model didn't predict, pop_front() on the empty queue returns null and process_…[0].kill() dereferences a null handle. You get a simulator crash instead of a clear "Unexpected TX item" DUT_ERROR. Add if(exp_tx_items.size() == 0) begin `uvm_error("DUT_ERROR", "Unexpected TX item …"); return; end. The IRQ check (C10) already does this correctly. Also worth adding: a check_phase that reports leftover expected entries at the end of the test.
      
      
      
        
      Q"How do you detect a DUT that just stops responding?"
      Use a timeout per expected item: start a watchdog thread when the prediction is queued, kill it when the actual is matched, and error if it expires. Make the threshold configurable, and size it from the spec's worst-case latency plus margin. Also have an end-of-test check for anything still pending, and a global timeout (set_timeout) as a last resort.
      
        
      Q"Why does write_in_agent_rx only act when !is_active()?"
      The monitor publishes each transfer twice, at start and at end. The response is only valid at the end, so acting on the start publication would compare a not-yet-sampled response and also pop the queue twice.

      C11
      Sync fix #1: no flag on same-time push and pop
      Model synchronization: FIFO flags · lecture + practice
      
      
      Push and pop are independent threads, and the simulator orders same-time threads arbitrarily. The fix: delay each flag-setter by 2 "ticks" in a killable process, and have the opposite operation kill it 1 tick later. Push kills a pending "empty"; pop kills a pending "full".
      
      
      protected virtual function void set_rx_fifo_empty();
  fork begin
    process_set_rx_fifo_empty = process::self();
    repeat(2) uvm_wait_for_nba_region();     // 2 ticks: room for a same-time push to cancel us
    void'(reg_block.IRQ.RX_FIFO_EMPTY.predict(1));
    if(reg_block.IRQEN.RX_FIFO_EMPTY.get_mirrored_value() == 1) exp_irq = 1;
    process_set_rx_fifo_empty = null;
  end join_none
endfunction

protected virtual function void kill_set_rx_fifo_empty();   // called right after rx_fifo.put()
  fork begin
    uvm_wait_for_nba_region();               // 1 tick: the setter may not have started yet
    kill_process(process_set_rx_fifo_empty);
  end join_none
endfunction
      
      
      
        
      Same-time orderWhy it still works
      
        
          
      pop first, then pushThe setter is waiting (tick 1 of 2) when the killer wakes at tick 1, so it's killed before setting the flag.
      
          
      push first, then popA kill right now would find a null pointer (the setter doesn't exist yet). Waiting 1 tick lets the setter start, and then it's killed.
      
        
      
      
      Rules and the result
        
        
      • The only real requirement: setter delay > killer delay. With different push and pop clocks, use small real delays (e.g. #1ps) that are still less than a clock period.
        • 
        
      • Applied to all four flags. RX/TX × empty/full.
        • 
        
      • Rerun with the same seed: it now fails earlier, "Unexpected IRQ". At 256 ns the model pushes and pops RX in the same time step, but the RTL pops one clock after the push (it can't pop data that isn't stored yet). So the RTL's level goes 1→0 and it raises RX-empty. The model is "too fast": it even pushes 4 items into the TX FIFO and pops 1 at 265 ns, which no real FIFO can do. That's issue #2.
        • 
      
      
      
      
        
      Q"How do you resolve a race between two threads at the same simulation time?"
      Don't rely on scheduler order. Options: impose an explicit order with delta delays (uvm_wait_for_nba_region, #0 is weaker), merge the decision into one thread that sees both events, use a semaphore or mailbox handshake, or (as here) a deferred, cancellable action. Then verify both orderings by reasoning, as the lecturer does, not just by one passing seed.
      
        
      Q"Why did the fix make the test fail earlier?"
      It removed one symptom and exposed a deeper cause. The model and RTL disagree about when FIFO operations happen, not just about how flags are computed. Fixing symptom-level discrepancies often reveals the structural one. That's progress, not regression.

      Q"Is it OK for a testbench to probe DUT internals?"
      For synchronization hints, yes, carefully: use the internal event to align timing but keep an independent fallback (a timeout plus a warning or error), so a broken or missing RTL event can't silently drive the prediction.       Q"Why are the data checks unaffected by this whole issue?"
      Data order and content don't depend on timing. Only level-derived outputs (FIFO flags, and therefore IRQs) do.       Sync fix #3: overlapping IRQs become one pulse

      class cfs_algn_virtual_sequencer extends uvm_sequencer;   // no item type: drives nothing itself
  uvm_sequencer_base           apb_sequencer;    // nothing special needed → base type
  cfs_md_sequencer_base_master md_rx_sequencer;
  cfs_md_sequencer_base_slave  md_tx_sequencer;  // typed: need its pending_items FIFO
  cfs_algn_model               model;            // for env_config + register mirror
endclass
// base vseq: `uvm_declare_p_sequencer(cfs_algn_virtual_sequencer)

virtual task body();                              // cfs_algn_virtual_sequence_slow_pace
  fork
    begin   // RX: one legal transfer, at least CTRL.SIZE bytes, so it fully leaves the buffer
      `uvm_do_on_with(rx_sequence, p_sequencer.md_rx_sequencer, {
        ((algn_data_width / 8) + item.offset) % item.data.size() == 0;
        (item.data.size() + item.offset) <= (algn_data_width / 8);
        item.data.size() >= ctrl_size; })
    end
    begin   // TX: answer every resulting transfer, ERR only on the last one
      do begin
        p_sequencer.md_tx_sequencer.pending_items.get(item_mon);     // wait for the TX start
        num_tx_items = rx_sequence.item.data.size() / CTRL.SIZE;
        `uvm_do_on_with(tx_sequence, p_sequencer.md_tx_sequencer, {
          num_tx_items == 1                                    -> item.response == CFS_MD_OKAY;
          num_tx_items > 1 && tx_item_idx <  num_tx_items - 1 -> item.response == CFS_MD_OKAY;
          num_tx_items > 1 && tx_item_idx == num_tx_items - 1 -> item.response == CFS_MD_ERR; })
        tx_item_idx++;
      end while(tx_item_idx < num_tx_items);
    end
  join
endtask
      
      
      Notes
        
        
      • Definition: "a sequencer that is not attached to a driver and does not process items itself". A virtual sequence is any sequence started on it: seq.start(env.virtual_sequencer).
        • 
        
      • The env connects the handles in connect_phase. The MD sequencers need a $cast because the agent declares its sequencer with the uvm_ext base type.
        • 
        
      • `uvm_do_on(seq, sqr) and `uvm_do_on_with(seq, sqr, {constraints}) run a sub-sequence on a specific sequencer.
        • 
        
      • Practice check with 100 iterations: RX_LVL never goes above 1 ("slow pace"). SIZE 1 + a 4-byte RX gives 4 TX transfers, with ERR only on the 4th.
        • 
      
      
      
      Hidden assumption: num_tx_items = rx_size / SIZE is only correct because this sequence guarantees the intermediate buffer is empty when the RX transfer starts (slow pace, and rx_size ≥ SIZE with legal sizes 1/2/4 always dividing evenly). In a back-to-back scenario, leftover buffered bytes change the count. That's why it's a dedicated, reusable scenario and not a general responder.
      
      
      
        
      Q"Virtual sequencer vs just passing sequencer handles to the sequence?"
      Both work. The virtual sequencer centralizes the handles (and shared helpers like the model) in one component that the env wires once, so every virtual sequence finds them through p_sequencer, and system-level environments can re-point them. Passing handles directly (a "virtual sequence without a virtual sequencer") avoids p_sequencer casts but spreads the wiring into every test.
      
        
      Q"What is p_sequencer and how is it declared?"
      m_sequencer is the generic uvm_sequencer_base the sequence runs on. `uvm_declare_p_sequencer(T) adds a typed handle p_sequencer and a $cast from m_sequencer (fatal if the type is wrong), giving typed access to the sub-sequencer handles.
      
        
      Q"Why does the TX branch wait on pending_items before choosing the response?"
      The MD slave is reactive. It must not answer until the master (the Aligner) has started a transfer, which its monitor reports through the sequencer's pending_items FIFO (see the MD chapter). Only then is it valid to compute how many TX items this RX produced and which one is last.

      Q"How do you get transactions visible in the waveform viewer?"
      Make the item record its fields (do_record or UVM_RECORD field flags). In the component, open a stream (get_tr_stream), and call begin_tr and end_tr at the protocol's start and end.       Q"do_record vs `uvm_field_* macros?"

The do_* overrides (do_copy, do_compare, convert2string, do_record) are explicit, faster and fully customizable. Many teams ban field macros for performance and debuggability; the lecturer prefers do_record for format control.

      Q"How do you structure tests in a UVM environment?"
      A base test that builds and configures the env. A small number of random "traffic" tests that start virtual sequences and expose knobs. Then targeted tests that only change constraints, knobs or factory overrides, never the traffic logic. Directed tests are kept for bring-up, very specific corners, or timing-sensitive features (like IRQ timing). Sequences carry the behaviour and tests stay thin, which makes regression lists easy to build.
      
        
      Q"How do you add a new targeted test without touching existing code?"
      Extend the virtual sequence that generates the relevant traffic, adding a constraint block, and in the new test's constructor or build_phase call parent_vseq::type_id::set_type_override(child_vseq::get_type()). Any type_id::create of the parent now returns the child. This is the open/closed principle, applied with the UVM factory.

      Bug #2 of the course: IRQEN resets to 0x1F
      Run 1 passed. Run 2 failed: the read of IRQEN returned 0x1F but the mirror said 0x00. It was the first IRQEN access in that seed, so both sides were showing reset values. The datasheet says reset = 0, so the RTL is wrong (cfs_regs.v, the reset branch set every irqen bit to 1). Run 1 passed only because its first IRQEN access happened to be a write. The lecturer pinned the seed, fixed the RTL, and confirmed access #5 now reads 0. (Your project copy already contains this fix.)
      
      
      
        
      Q"Why did one seed find the bug and another not?"
      The bug was only observable if a read of IRQEN came before any write to it. Random ordering makes that a probability per seed. That's why you run many seeds, and why coverage should include "first access after reset is a read" for every register. A built-in UVM sequence, uvm_reg_hw_reset_seq, checks all reset values directly. It's a good first test in any register bring-up.
      
        
      Q"Which built-in UVM register sequences do you know?"
      uvm_reg_hw_reset_seq (reset values), uvm_reg_bit_bash_seq (walks 1s and 0s through every RW bit), uvm_reg_access_seq (front door vs back door consistency, which needs HDL paths), uvm_mem_walk_seq and uvm_mem_access_seq for memories, and uvm_reg_mem_built_in_seq to run them all. Exclude registers with side effects using resource attributes like NO_REG_BIT_BASH_TEST.

      The random traffic test, and two traps it uncovered
      Random traffic test · lecture + practice
      
      
      repeat(2) begin                                   // loop: CLR and W1C clears get exercised too
  if(env.model.is_empty()) begin                  // never reconfigure while data is inside
    cfs_algn_virtual_sequence_reg_config seq = ...;  // writable regs ("RW"/"WO"), shuffled, randomize + update

    seq.set_sequencer(env.virtual_sequencer);     // before randomize: constraints read p_sequencer
    void'(seq.randomize()); seq.start(env.virtual_sequencer);
  end
  repeat(100) @(posedge vif.clk);                 // let TX drain: levels are volatile right after traffic
  cfs_algn_virtual_sequence_reg_status ...;       // read-only regs ("RO"), shuffled, read
end
      
      
      Trap 1: "IRQ is never written." update() after randomize() never touched IRQ (W1C fields). Root cause in UVM's uvm_reg_field::configure(): for non-writable-style accesses (including W1C) it forces is_rand = 0 and value.rand_mode(0), silently ignoring your is_rand = 1. Randomize leaves desired == mirrored, so update() sees nothing to do. Fix: after configure, call FIELD.value.rand_mode(1) for every IRQ field (it's in your cfs_algn_reg_irq::build()). The lecturer: "even experienced verification engineers are not aware of this".
      
      
      Trap 2: TX data mismatch on seed 11. The second loop iteration reconfigured CTRL while bytes still sat in the intermediate buffer (waiting for enough bytes to align). Changing SIZE or OFFSET with data inside is unpredictable, so the test must not do it. Fix: cfs_algn_model::is_empty() (RX FIFO, TX FIFO and buffer all empty) guards the config step.
      
      
      Senior-level follow-ups
        
        
      • The guard silently skips work. Leftover bytes smaller than SIZE never drain, so when they're present the second config is skipped, not delayed. Reconfiguration coverage then depends on luck. Better: drain on purpose (send filler bytes until is_empty(), with a timeout), then reconfigure, and cover "reconfigured with an empty pipeline".
        • 
        
      • What's still untested (the lecturer's challenge): multiple resets mid-traffic (does the DUT recover?), and the two features fixed by the loop, which are clearing CNT_DROP via CTRL.CLR and clearing IRQ flags via W1C.
        • 
        
      • EDA Playground limits: wave dump size, about 5000 log lines, about 1 minute of CPU. That's why num_md_rx_transactions was cut to 100 there.
        • 
        
      • The lecturer's honest summary: tests pass on a few seeds and fail in regressions on cases nobody anticipated. Incremental test fixes are part of the job, and coverage may still show untested features afterwards.
        • 
      
      
      
      
        
      Q"randomize() + update() on a register does nothing. Why?"
      Three usual causes. The randomized value equals the mirror, so needs_update() is 0. The field isn't randomizable: its access is RO or W1C-like and configure() turned rand_mode off, or is_rand was 0. Or randomization failed and the result was voided. Check get() vs get_mirrored_value() and FIELD.value.rand_mode(), and always check the randomize result.
      
        
      Q"Why wait before reading the status registers?"
      Right after traffic, RX_LVL and TX_LVL change every few cycles, and the model and RTL can legitimately differ by a cycle in when they update. Reading in a quiet period makes the read check deterministic. Reading during traffic is also valuable, but needs volatile-tolerant checking or tighter synchronization.
      
        
      Q"Your random test passes 10 seeds. What would you add before calling it good?"
      Reset in the middle of traffic. Reconfiguration with the pipeline drained. Back-pressure extremes (a slow TX slave, all-max RX). Interrupt clears and CLR. Error-response mixes. Then a regression of thousands of seeds with coverage, triaging every failure.

      Background the lecture assumes
        
        
      • Code coverage types: line/statement, branch, condition/expression, toggle, FSM state and transition. 100% code coverage with weak checkers still misses bugs, which is why functional coverage and qualification exist.
        • 
        
      • Qualification = mutation analysis. Commercial tools (Synopsys Certitude is the best known) classify each injected fault as not activated (a stimulus gap), activated but not propagated (an observability gap), or propagated but not detected (a checker gap). The last is the most damning.
        • 
        
      • In this course: three RTL bugs were found by re-running seeds by hand. The lecturer is explicit that without real regressions, nobody can claim there are no more.
        • 
      
      
      
      
        
      Q"Walk me through how you'd verify a new block from day one."
      Spec study with an open-questions list to the architect. A testbench architecture document and a verification plan (features → checks, coverage, tests), reviewed with design and architecture. Reuse or build agents, then RAL, model, scoreboard and coverage, bringing them up with simple directed tests. Then random tests and regressions, triaging failures until everything passes. Close functional and code coverage, with waivers reviewed. Mutation qualification if required. Sign off with coverage reports, the test/seed list and the bug summary.
      
        
      Q"When are you done verifying?"
      When the agreed criteria in the plan are met: all regression tests passing over a statistically meaningful number of seeds, functional coverage closed (with holes explained or waived in review), code coverage closed by design (exclusions reviewed), the bug-discovery rate flattened, and qualification clean if required. "Done" is a reviewed decision against evidence, not a feeling.
      
        
      Q"100% code coverage but a bug escaped to silicon. How?"
      Code coverage only shows the lines executed. It doesn't show that the effect was checked, or that the right combination of conditions occurred. Typical causes: a missing or weak checker (exactly what mutation qualification exposes), functional coverage missing the corner (e.g. reconfiguring with data inside), or a spec gap where both RTL and model were wrong in the same way, like the SIZE + OFFSET bug in R8.
      
        
      Q"Who reviews the verification plan, and why does that matter?"
      Verification, design and concept/architecture. Design knows the implementation risks (arbiters, clock crossings, corner states), and architecture knows the intended system use. Their sign-off means everyone agrees on what will and won't be verified, so a missing feature is caught at review time, not after tape-out.
