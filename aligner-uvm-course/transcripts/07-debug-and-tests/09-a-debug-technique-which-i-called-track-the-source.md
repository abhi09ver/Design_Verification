# A debug technique which I called "Track the source"

*Chapter: Debug and tests · source: attached*

Hi!
My name is Cristian Slav and in this tutorial we are going to talk about a debug technique which I called "Track the source".
Let's start by looking over an example of a failing test.
We have here the block diagram of our Aligner RTL and in this failing test we drove some RX traffic and we saw that the RTL started to output some traffic on the TX interface.
At some point during the simulation we get an UVM error with data mismatch on the TX interface.
The error message generated by our scoreboard looks more or less something like this: Mismatch detected for TX data and then we print the expected data and the received data.
So, our environment was expecting this 12, 34, but the RTL output it 12, AB.
So, at this point we start to debug our test and the first thing that we need to do is to double-check that the expected data generated by the environment is the correct one.
And to do this, we start looking in the RX stream for this data 12, 34.
If we find these two bytes in the RX input stream then it would be easier to track that information through the RTL and through the environment all the way on the output interface.
But when we look for this data in the RX information we actually find it in two places.
So we need to figure out which of these ones were responsible for this expected data.
One approach to figure this out is to look on the TX interface on the bytes outputted just before this mismatch.
And let's say that we had this C4, 3B.
We know that these bytes were correct as the scoreboard did not trigger an error for those.
So we need to look on the RX interface to see if we see this C4, 3B either here or here.
And when we look, actually in none of these occurrences this C4, 3B appeared.
So, this might be a clue that actually our expected data might be wrong, as the only places in which we found this 12, 34 was here and here, and the data in front of this one never matched with the data outputted on the TX interface.
Then comes the hard part in which we have to trace back either these data in RTL or our expected data in the environment.
Once we go through all this time-consuming process of backtracking the information through the environment and RTL, we managed to find our expected data in the RX stream.
We realized that our expected data 12, 34 was actually built based on two RX MD transactions.
And when we search for this 12, 34 in our log or on the waveforms, we could not see this easily because the information was splitted over two transactions.
We also can identify this C4, 3B in front just like on the TX interface and at this point we can report to the design team that there is indeed an RTL bug.
But to come to this conclusion, we actually spent a lot of time debugging and checking that our expected information from the environment is the correct one.
In this debug session, we actually spent a lot of time trying to identify what were the sources of this expected data.
But we could have saved this time if our error message from the scoreboard would have contained this information.
It would have been much more easier for us if the error message from the scoreboard simply pointed us on the MD RX transactions which caused this expected information.
From such an error message we can immediately identify the time and the data of the MD RX transactions which caused this.
We can easily see from here that this 12 was build from this transaction and this 34 was taken from this one.
And if we know the time at which to look for these transactions on the MD RX interface, then we can easily identify the MD transaction driven just before this one.
So we can easily confirm that this C4, 3B was outputted on the TX interface here.
And in this way we can prove to the design team that this is indeed an RTL bug and also this is a great help for them as we can provide to them the point on the MD RX interface from which they can start the debug and try to track this information through the RTL and see where the bug came from.
We can print such an error message in our scoreboard only if in the expected data we save at some point the sources of this information.
In the next slides, I will show you how you can do this in the environment.
This is not something technically difficult, but it does involve a fair amount of coding, and for this reason we will not implement it as a practice session in our training, but you will have all the necessary steps to implement this on your own.
To figure out how we can do this in the environment, let's look at the block diagram of our environment.
Right now, our MD agents are sending to the model and to the scoreboard the information packed in this class.
We can add in this class a field in which to store that source information.
But in a real project most of the times the agent that you will use will not be developed by you so you will not be able to add some new fields in this class.
So we need to put all this information into some other class which belongs to our environment.
And in order to accomplish this we need to put an adapter between our agents and the rest of the environment.
The main purpose of this adapter is to have inside a function, let's call it mon2env(), and this mon2env() function can transform the information coming from the agents to a class that we develop in our environment.
The implementation of this mon2env() function is quite simple.
The input argument is the information coming from the MD agent, and its purpose is to copy all the information from this class to our new class.
So, its body will look something like this.
First, we will create an instance of this data item, then we start copying all the fields, and then we return the result.
In this way, the rest of our environment, in particular the model and the scoreboard no longer works with the information coming from the MD agent, but it will work with our new class.
And because this class belongs to our environment, we can add any fields that we want in here.
In our case, we are interested in adding the sources of this information.
Because we can have multiple sources for this information, we will need here a queue, and because the type of the sources can be different we can declare it as a queue of uvm_object.
We can actually have two types of sources for this data.
First, in our mon2env() function from the adapter, after we copied all the fields we can save the source.
In this case, the source of this data item is actually the information coming from the MD monitor.
But we can have another type of information set up in our model.
Remember that in the align() task sometimes we need to split the MD RX transaction in order to only take several bytes out of it.
And once we finish building the TX expected item in our model we can save the sources of that information.
So at this point we need to push in this sources queue objects of this new data item type, as in this case our model will only work with this data item class.
Of course, the code in our align() task is not that simple.
There are several places in which we need to pay attention in order to correctly save the source of our expected item.
I just want to point to you that this align() task is the place in which we have to save the sources of our expected TX item because there we are building this information.
Once we have this information in our sources queue from the expected item, then in our scoreboard we can update the error message.
So, we can add here the information about the sources of this expected item.
And for each object from our sources queue we can simply call the function convert2string().
Of course, this is not a correct implementation in SystemVerilog.
You'd have to build this string in a foreach loop, as not all the time you'll have exactly two entries in this sources queue.
But I just want to give you an idea how this might look like.
