The Scoreboard component is responsible for verifying that the outputs from the RTL are matching with the expected data generated by our model.
And in the case of the Aligner RTL, we have three types of output data.
First, we have the response on the MD RX interface and our scoreboard will get the data returned by the RTL via the monitor inside the RX agent.
And of course, the expected data will be sent to the scoreboard by our model.
Another output data is the MD TX transaction.
In the same way, the information outputted by the RTL will be sent to the scoreboard via the TX agent, and the expected data will be sent to the scoreboard by our model.
But besides these two types of information that we have, we also have a third one which is not represented here in the picture, but we can draw some lines, and this represents the interrupt requests.
The RTL has an output signal called "irq", which becomes 1 whenever the RTL signals an interrupt request, and in our model we have that output port through which we inform the scoreboard that it should wait for an interrupt request.
So, our scoreboard will have to verify these three types of information: the response on the MD RX interface, the transaction on the MD TX interface, and the interrupt request.
And in each of these three cases our scoreboard will implement the checks in the same way.
And let's see a short animation to better understand how the checks for each of those types of information will be implemented in the scoreboard.
This is our scoreboard component and for each of those types of information that we want to verify we have two ports.
One through which the scoreboard will get the expected information from our model and another port through which the scoreboard will get the DUT output information and we can call this received information.
And let's see what should happen with the expected and received information in our scoreboard.
Let's say that our model is sending some expected information to the scoreboard.
Because our model will always be faster than the DUT, we need a queue inside the scoreboard to store this expected information until the DUT also get a chance to send its information.
And because we want to catch the scenario in which the DUT is stuck and never sends some information on its output port, whenever we push some information in this queue, we want to start a timer.
And if this timer goes past a certain threshold, then we trigger an error so that we detect the scenario in which the DUT gets stuck and never outputs any data.
Depending on the type of information that we verify, it can happen that the model will send more of this expected info and we should store that expected info in our scoreboard.
And one important thing to notice here is that for each of those entries in this internal queue, we should start a counter to know when that entry was pushed in this queue.
At some point during the simulation, also the DUT will output some information.
And at that point we should stop the counter of the first entry in the queue, take out that entry and compare these two data.
If everything matches then we move forward, if not we trigger an error.
And in this way we can catch RTL bugs.
But if everything is okay, we discard this information and all these entries will be moved throughout our queue and the process is started all over again.
So let's see exactly what checks we need to implement for this in the scoreboard.
The most obvious one is this one.
We need to check that the expected information is equal to the received information.
So these two entries here.
Another check that we need to implement is this one.
We need to check that the expected information does not stay too long in the queue.
And the purpose of this check is to catch scenarios in which the RTL gets stuck and never outputs any information.
The third check that we need to implement is this one.
We need to check that the number of entries in this expected queue does not pass a certain threshold.
Because depending on the type of information that we verify, there should be a limited number of entries in this expected queue which can happen.
For example, for the MD RX response, our model sends to the scoreboard an expected information every time an MD RX transaction starts or is pushed in that RX FIFO.
And the received information from the DUT should come when that transaction is ended.
But the end of the MD RX transaction cannot come after a new one starts on the bus, as the protocol does not allow two overlapping transactions.
So for the MD RX response, we will trigger an error if there are more than one entries in this expected queue.
However, for the interrupt requests, our model can send a lot of expected interrupts until the DUT has time to send the first one.
So in that case we should allow in this expected queue to have more than one entries.
But when we will implement the checks we will see in each scenario how many entries we should allow for each type of information that we are verifying.
So we will have to implement all these three checks for all three types of information that we will have to verify in our scoreboard.
And once again the three types of information that we will verify are the MD RX response, the MD TX transaction, and the interrupt requests.
