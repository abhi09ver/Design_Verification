Overrun Error

The wire was perfect — the software was too slow. A character arrives with nowhere to go.

Definition: a new character completes in the receive shift register while the holding register / FIFO is still full. One character is lost and LSR.OE (bit 1) is set. Nothing is wrong on the wire — so a line monitor alone can never detect it.

Which character is lost? (16550-style)

FIFO off
New char overwrites the unread one in RBR. Old data lost.
FIFO on
Char in the shift register is overwritten and never enters the FIFO. FIFO contents stay valid.
OE timing
Flag rises as soon as the overrun happens; cleared by reading LSR.
Exactly which char is dropped, and at which count (N+1 or N+2) OE rises, is spec-specific — make the model take it from the spec, and cover the boundary.

How systems prevent it

  • RX FIFO trigger level (1 / 4 / 8 / 14): interrupt early enough for software to drain.
  • Character timeout interrupt so a few leftover bytes don't sit unread.
  • Hardware flow control: auto-RTS deasserts near full so the sender pauses (CTS).
  • DMA for sustained high baud rates.
  • Verify each mechanism: with auto-RTS on, a burst must never overrun.

Predict it in the scoreboard — two inputs, one model

uart_item  rx_q[$];      // model of the DUT RX FIFO
bit        exp_oe;

function void write_line(uart_item it);      // from line monitor (frame complete)
  if (rx_q.size() < cfg.fifo_depth) rx_q.push_back(it);
  else begin exp_oe = 1; n_lost++; end      // FIFO-mode rule: newest char dropped
endfunction

function void write_bus(bus_item b);        // from APB/AXI monitor or RAL predictor
  if (b.is_read && b.addr == RBR) begin
    uart_item exp = rx_q.pop_front();
    if (b.data[7:0] !== exp.data) `uvm_error("UART_SB", "RBR data mismatch")
  end
  if (b.is_read && b.addr == LSR) begin
    if (b.data[1] !== exp_oe) `uvm_error("UART_OE", $sformatf("OE=%b exp %b", b.data[1], exp_oe))
    exp_oe = 0;                              // OE clears on LSR read
  end
endfunction
Overrun lives inside the DUT, so it needs both sides: the serial monitor (chars in) and the register-bus monitor (chars out). Use uvm_analysis_imp_decl to give the scoreboard two write methods.

Test plan & coverage

  1. No reads; burst N, N+1, N+2, N+10 chars. OE exactly at the spec'd count, FIFO keeps the first N.
  2. FIFO disabled (depth 1): two chars without a read.
  3. Reader slower than arrival rate — steady-state overruns.
  4. Race: RBR read lands in the same cycle the new char completes.
  5. Read LSR → OE clears; second overrun sets it again.
  6. Auto-RTS on: same burst, zero overruns, TX pauses.
  7. Cover: FIFO level at arrival {0, mid, N−1, N} × FIFO on/off × flow control × error-tagged char.

Modelling pitfalls

  • Same-cycle race: a transaction-level model can't know if the read or the push won. Either model at cycle level, or accept both outcomes within a small window and cover which one happened.
  • "Char complete" point: RTL may push at mid-stop-bit, your monitor at end of stop. Align the model with the RTL's push point.
  • Wrong lost-char assumption (oldest vs newest) → every later compare mis-aligns.
  • Forgetting that an LSR read clears OE and other sticky bits.

Interview Q&A

Q. Why can't a protocol checker on the line catch overrun?
The serial stream is perfectly valid. The loss happens between the FIFO and the CPU — you need the bus side too.
Q. Overrun vs underrun?
Overrun: RX data arrives faster than it's read. TX "underrun" just means TX empty — the line idles, THRE interrupt fires, not an error.
Q. How do you force overrun in a test?
Mask RX interrupts, stop the reader sequence, and drive more than FIFO depth back-to-back frames.
Q. How would you verify the read/arrive race?
Constrain read timing relative to the stop bit, sweep the offset by a cycle at a time, and cover the exact-coincidence bin.
