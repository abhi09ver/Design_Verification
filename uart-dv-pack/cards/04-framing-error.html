Framing Error Check

The stop bit is the frame's closing bracket. If it reads 0, the receiver lost its place.

Framing error
Precise definition: the receiver samples the stop bit at its middle and reads 0 instead of 1. It is a statement about the stop bit, not about matching "codes" at both ends — a common fuzzy explanation interviewers will push on.

Root causes

  • Baud mismatch — sample points slide until the stop sample lands in the next start bit.
  • Format mismatch — TX 7E1 vs RX 8N1: RX reads one bit too many or too few, so "stop" is really data.
  • Noise on the stop bit.
  • Break — line held low for a whole frame or more (part 06).
  • TX reset / disable mid-frame, or a premature next start (TX sends less than 1 stop bit).
  • Lost sync — RX locked onto a 1→0 inside data after an earlier error.

What the DUT should do (16550-style)

  • Set LSR.FE (bit 3) for that character; it's tied to the char at the FIFO head, revealed when that char is read.
  • Still store the character (marked as errored); LSR bit 7 = "error somewhere in RX FIFO".
  • Raise the receiver line status interrupt (highest priority) if enabled.
  • Resync policy is spec-specific: some UARTs treat the low "stop" as the next start bit, others wait for the line to go high first. The checker must mirror whichever the spec says.
  • With 2 stop bits, many receivers check only the first; TX must still send both.

Checker + error-injection hooks

// monitor: after data (+ parity)
for (int s = 0; s < cfg.stop_bits; s++) begin
  #(cfg.bit_time);
  it.stop[s] = vif.rx;
end
it.fe = (it.stop[0] !== 1'b1);               // RX rule: first stop bit decides

// checker: write() from monitor
if (it.fe) begin
  if (it.fe_expected) `uvm_info ("UART_FE_EXP", "injected framing error seen", UVM_MEDIUM)
  else                `uvm_error("UART_FE",     $sformatf("stop=0 after data 0x%0h", it.data))
end
if (cfg.check_all_stops && it.stop[1] === 1'b0)  // TX-side rule for 2 stop bits
  `uvm_error("UART_FE2", "second stop bit low")

// driver knob: corrupt the stop bit on purpose
vif.rx <= (tr.inject_fe) ? 1'b0 : 1'b1;  #(cfg.bit_time);
Carry intent in the item (inject_fe → fe_expected) so negative tests pass cleanly and unexpected FEs still fail.

Test plan & coverage

  1. Directed: single FE frame, then read LSR via RAL — FE set, data present, clears on read.
  2. Random mix of valid / errored frames at a set injection rate; scoreboard tracks expected flags per char.
  3. Recovery: FE frame immediately followed by a valid frame (no idle) — must decode correctly.
  4. FE with each format: data 5–8 × parity × stop 1/2.
  5. Format mismatch test: TB 7E1 into DUT 8N1.
  6. Coverage cross: fe × format × back-to-back × FIFO on/off × interrupt enabled.

Edge cases that find bugs

  • Framing error vs false start: a glitch rejected at mid-start is not an FE — no flag, no char.
  • 0x00 with a low stop bit is exactly a frame of zeros → candidate break; duration decides.
  • FE on the char that fills the FIFO — does the error flag land on the right entry?
  • Cascades: one FE can mis-sync the next frames. Count root causes, not every downstream error.
  • Reset asserted mid-frame: no FE should be reported for the cut-off frame after reset.

Interview Q&A

Q. Framing error vs parity error?
Framing = structure broken (stop bit). Parity = structure fine, content suspect. They can occur together.
Q. Why do baud mismatches show up as framing errors first?
The stop bit is sampled last, so it has the most accumulated drift.
Q. How do you keep negative tests from failing?
Mark the item as expected-error, or demote the specific ID with a report catcher for that test only — never globally.
Q. What if the scoreboard expects data but FE was flagged?
Follow the spec: usually data is stored with an error tag. The scoreboard compares data and the error flag together.
