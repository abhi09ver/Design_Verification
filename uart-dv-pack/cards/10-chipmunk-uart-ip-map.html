Deep dive — is ±5% really safe at 8×?

The ±5.3% figure is 0.5 bit ÷ 9.5 bits — the limit with perfect edge detection. Real limits are tighter:
8× edge uncertainty
1/8 = 0.125 bit
8N1, last sample 9.5 T
(0.5−0.125)/9.5 ≈ 3.9%
8O1, last sample 10.5 T
0.375/10.5 ≈ 3.6%
16× for comparison (8N1)
0.4375/9.5 ≈ 4.6%
Those are combined TX + RX budgets. So "±5%" only holds if the far end is near-perfect. A drift sweep (card 03) with parity on is the test that settles it — a strong talking point.

How each card changes for this IP

01 Fundamentals
Same frame; RX locks with 8 ticks/bit — confirm start at tick 4, sample every 8.
02 Checker
No register bus: pin monitors + valid/ready stream monitors on both data ports feed the scoreboard.
03 Baud
divisor = f_clk ÷ (8 × baud) for RX pulses; check TX pulse spacing and the pulse counter width vs lowest baud.
04 Framing
Check the status flag's timing: per-byte with data valid, or sticky until cleared?
05 Parity
Only none / odd / even — drop mark/space bins; data width fixed at 8, so no width bug.
06 Break
Not a feature: expect 0x00 + framing error. Check RX doesn't emit a byte every frame time while held low.
07 Overrun
No FIFO → becomes backpressure: a new byte completes while out-ready is low. Drop, overwrite or flag? Read the RTL.
08 Idle / CDC
Synchroniser flops must reset to 1; reset-to-0 makes a fake falling edge (false start) at reset release.
09 Reporting
Status flags instead of LSR: map each checker ID to a flag; cover flag × parity mode × stop bits.

Valid / ready rules — SVA

// once raised, valid holds and data is stable
a_hold: assert property (@(posedge clk)
  disable iff (!rst_n)
  (tx_valid && !tx_ready) |=>
    (tx_valid && $stable(tx_data)));

// a handshake starts exactly one frame
a_start: assert property (@(posedge clk)
  disable iff (!rst_n)
  (tx_valid && tx_ready) |-> ##[1:$] $fell(tx));

// TX line idles high out of reset
a_idle: assert property (@(posedge clk)
  !rst_n |-> tx === 1'b1);
Also cover: back-to-back handshakes, ready low for many frames, valid toggling with no handshake.

Open questions to settle from the RTL

  1. RX output ready low when a byte completes — drop, overwrite or flag?
  2. Framing / parity flags: pulse with data valid, or sticky?
  3. Number of sync stages on RX, and their reset value.
  4. Is the start re-checked at mid-bit (false-start rejection)?
  5. With 2 stop bits, does RX check both?
  6. Can config change mid-frame — and what happens?
  7. Baud counter width → lowest reachable baud at a given f_clk.
  8. What does the synthesisable TB check, and what does it skip?

Interview Q&A on this design

Q. Why baud enable pulses rather than a divided clock?
Everything stays in one clock domain: no generated clocks, no extra skew or CDC, simple STA and FPGA-friendly.
Q. Why does RX need a synchroniser but TX doesn't?
RX comes from a foreign clock and can change near our clock edge → metastability. TX is driven from our own flops.
Q. 8× vs 16× oversampling?
8× halves the sample-pulse rate (higher max baud, less toggling) but doubles edge uncertainty, shrinking drift tolerance.
Q. No FIFO — how do you test throughput?
Randomise ready on both ports, run continuous traffic, and check no byte is lost or duplicated under backpressure.
