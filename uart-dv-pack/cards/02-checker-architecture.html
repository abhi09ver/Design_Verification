Building the UVM Protocol Checker

A passive observer that turns wire activity into transactions — then judges them against the protocol.

Connection: monitor uvm_analysis_port → write() broadcast to every subscriber (uvm_subscriber / uvm_analysis_imp). One monitor per direction: TX line and RX line.

Building blocks

  • uart_cfg (uvm_object): baud, clk freq, data_bits, parity mode, stop_bits, tolerance %, per-check enable knobs. Set once by the test, fetched with uvm_config_db in build_phase.
  • uart_item (uvm_sequence_item): data, parity bit, stop bit(s), start/end timestamps, measured bit times, error flags.
  • Monitor: watches vif, never drives. Emits one item per frame — frame-level, not bit-level.
  • Checker: applies rules (baud, framing, parity, break, idle). Reports with distinct message IDs.
  • Agent: active (driver + sequencer + monitor) for the TB side, passive (monitor only) to observe DUT TX.

UVM phases used

build_phase
get cfg + vif from config_db, create ports and sub-components via factory.
connect_phase
monitor.ap → checker / scoreboard / coverage exports.
run_phase
forever loop: detect start, sample frame, write item.
check_phase
leftovers: unmatched items, frame cut by end of test.
report_phase
summary: frames seen, errors by type.

Monitor run_phase — the skeleton every later check plugs into

task run_phase(uvm_phase phase);
  forever begin
    uart_item it;
    @(negedge vif.rx);                      // candidate start edge
    t0 = $realtime;
    #(cfg.bit_time/2);                      // move to middle of start bit
    if (vif.rx !== 1'b0) continue;          // false start: glitch, ignore
    it = uart_item::type_id::create("it");
    for (int i = 0; i < cfg.data_bits; i++) begin
      #(cfg.bit_time);  it.data[i] = vif.rx; // LSB first
    end
    if (cfg.parity != PAR_NONE) begin #(cfg.bit_time); it.par  = vif.rx; end
    #(cfg.bit_time);    it.stop = vif.rx;   // checker flags stop == 0
    it.t_start = t0;    ap.write(it);       // broadcast to subscribers
  end
endtask
Use !== so X/Z on the line is caught. Delay-based sampling is simplest; a clocked 16× sampler mirrors the RTL more closely and catches mid-bit glitches.

Design choices — know the trade-off

  • Checks in monitor: least code, but couples collection with judgement; can't reuse the monitor where errors are expected.
  • Separate checker component: reusable, checks can be disabled per test, cleaner reporting. Preferred.
  • SVA in the interface: cycle-accurate, works in formal and emulation, but awkward for multi-bit frame state and config.
  • Best practice: timing checks as SVA, content checks in the class, data correctness in the scoreboard.

Bugs to spot in tutorial-style code

  • analysis_port has no get(). It only broadcasts with write(). To pull, use uvm_tlm_analysis_fifo and call get() on it.
  • Bit-per-transaction TLM carries no timing — you cannot check baud from it. Sample the vif.
  • new() on a component inside a module skips the factory and the hierarchy. Build via type_id::create under the env, start with run_test().
  • No objection handling → sim ends at time 0. The test raises and drops objections, not the monitor.

Interview Q&A

Q. uvm_object vs uvm_component?
Components are static, live in the hierarchy for the whole sim and have phases. Objects (items, configs, sequences) are transient data with no phases.
Q. Why should the monitor never drive?
It must observe the same bus in passive agents and at SoC level, where the DUT drives. Any drive breaks reuse.
Q. analysis_port vs blocking put port?
Analysis is non-blocking, one-to-many, zero-time write(); the monitor never stalls. Put ports are one-to-one and may block.
Q. How do you make the checker configurable per test?
Config object with enable bits and expected params, set from the test through config_db before build.
Q. Checker in RX path only, or both?
Both. TB→DUT checks your driver; DUT→TB checks the design's transmitter. Same monitor class, two instances.
Q. Where would you use SVA instead?
Idle-high after reset, no X on TX, minimum pulse width — local, timing-shaped rules that also run in formal.
