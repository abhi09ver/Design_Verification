Chapter 1 · Architecture

Cache organization

Everything coherence does happens per block (line). Know how a line is located, filled, replaced and written back before talking protocols.

Placement

  • Direct-mapped: 1 way, fast, conflict misses.
  • N-way set-assoc: the norm (L1 8–12 way, LLC 12–16+).
  • Fully assoc: TLBs, victim caches, small buffers.
  • 3 C's: compulsory, capacity, conflict (+ coherence misses in MP).

Write policies

  • Write-back + write-allocate: CPU L1/L2 default; needs dirty state → M/O.
  • Write-through + no-allocate: simple, used in many GPU L1s; coherence is easier since memory side is always current.
  • Store buffer / write-combining buffer sits in front and is a consistency concern.

Replacement

  • True LRU (cost ∝ ways²), tree-PLRU, RRIP/SRRIP for LLC scan resistance.
  • Victim of state M/O → writeback (PutM/PutO); S/E → silent or PutS (protocol choice).
  • Replacement races with incoming snoops are a top bug source.

Hierarchy & inclusion

  • Inclusive LLC: LLC ⊇ L1/L2 → LLC tags act as a snoop filter; eviction needs back-invalidation.
  • Exclusive: no duplication, L2 victims fill LLC.
  • NINE: neither, needs a separate snoop filter / directory.

Miss handling

  • MSHRs track outstanding misses; secondary misses to same line merge.
  • Non-blocking caches = transient states per MSHR entry.
  • Fill buffer, writeback buffer, eviction buffer: each holds data that must still answer snoops.

Addressing quirks

  • PIPT simplest; VIPT common L1; VIVT needs synonym/homonym handling.
  • Banking, way prediction, sectoring (coherence per sector vs per line).
  • I-cache, TLB, DMA must also be coherent (self-modifying code, shootdowns).
Chapter 2 · Specification

Coherence basics: the two invariants

Coherence makes private caches functionally invisible. It is per-location; consistency is about all locations together.

Invariant 1

SWMR: single writer, multiple readers

For any block at any instant, either exactly one core may write (and read) it, or zero or more cores may only read it. Never both.

Invariant 2

Data-value invariant

The value at the start of an epoch equals the value at the end of the last read-write epoch. SWMR alone is not enough: permissions can be right and the data still stale.

Granularity

Enforced per cache block (64 B on CPUs; GPUs often 128 B line, 32 B sector). Two cores writing different bytes of one line still ping-pong: false sharing.

Two interface styles

Consistency-agnostic: write is globally visible before it returns; coherence looks like atomic memory (CPUs). Consistency-directed: writes propagate lazily but in an order the model allows (GPUs, Ch. 6 here).

Other definitions

Write serialization (all cores see writes to one address in the same order) + write propagation (every write eventually visible). The first is safety, the second is liveness. Interviewers accept either if you name both halves.

Chapter 4 · Design trade-offs

Snooping vs directory

Both implement the same invariants. They differ in where ordering comes from.

Deadlock avoidance

Separate virtual networks per message class (Request → Forward → Response). A response must never wait behind a request. Classic interview: “why ≥3 VNs for a directory protocol?”

Ordering assumptions

Point-to-point ordered networks let the directory skip some acks. Unordered networks (meshes with adaptive routing) need extra handshakes, e.g. Put-Ack before reuse, Unblock after completion.

Directory organization

Directory cache backed by DRAM; inclusive directory (sparse/snoop filter) whose eviction forces back-invalidation of cached copies; or null directory (broadcast, e.g. HT Assist variants).

Blocking vs non-stalling

A blocking home NACKs or queues new requests until the in-flight one unblocks. Non-stalling designs add more transient states at the directory: more performance, much more verification surface.

Silent vs explicit evictions

Silent S evictions keep traffic low but leave stale sharer bits → spurious invalidations (correct but wasteful). Explicit PutS keeps the directory exact at the cost of messages and new races.

Real systems

SGI Origin (directory), AMD HyperTransport + HT Assist, Intel QPI/UPI (MESIF), Arm AMBA CHI (home node, snoop filter, DMT/DCT direct transfers), NVLink-C2C for CPU–GPU coherence.

Liveness, not just safety. Deadlock (cyclic waits on resources or VCs), livelock (requests keep bouncing, e.g. repeated NACK/retry), and starvation (one core never wins the line, e.g. under lock contention). Verification needs forward-progress checks, not just data checks.
Chapter 5 · Architecture spec

Memory consistency: SC, TSO, relaxed

The consistency model is the architectural contract. Coherence is one ingredient; the pipeline (store buffer, OoO loads, forwarding) is the other.

The single most important distinction. Coherence orders writes to one address. Consistency orders loads and stores across all addresses. A perfectly coherent system can still violate SC because of the core’s store buffer.

How OoO cores keep SC/TSO

Loads execute speculatively out of order. The load queue snoops incoming invalidations and evictions; a hit on a speculatively performed, uncommitted load squashes and replays it (MIPS R10000 style). Alternative: value replay at commit.

Atomics (RMW)

Obtain the line in M, then do load+store locally while deferring incoming snoops for that line. No bus lock needed. Under TSO an RMW also drains the store buffer, acting as a full fence.

SC for DRF

If software is data-race-free (all conflicting accesses ordered by synchronization), weak hardware looks SC. C++/Java models are built on this; acquire/release map to LDAR/STLR, fences.

Release consistency

Acquire: later accesses can’t move above it. Release: earlier accesses can’t move below it. One-way fences; cheaper than full fences and the basis of GPU scoped models.

Prefetch is harmless

Non-binding prefetches and coherence request order don’t affect consistency. The model constrains when loads/stores perform, not the order of GetS/GetM. (Primer quiz Q1 and Q2: both false.)

Axiomatic view

Relations: po program order, rf reads-from, co coherence order, fr from-reads. SC = acyclic(po ∪ rf ∪ co ∪ fr). Weaker models drop parts of po (ppo) and add fences.

Chapter 6 · Heterogeneous

GPU and accelerator coherence

Primer Ch. 10. Highly relevant at NVIDIA: GPUs often enforce consistency directly in the coherence mechanism instead of keeping SWMR.

Why GPUs skipped classic coherence

  • Thousands of threads, throughput-oriented, little fine-grained sharing in graphics.
  • Invalidation traffic and directory state for huge L1 counts is costly.
  • Typical design: write-through (or write-back at L2) L1s, L2 is the point of coherence.

Consistency-directed coherence

  • Self-invalidation: on an acquire, invalidate (or selectively invalidate) local L1 lines.
  • Self-downgrade / flush: on a release, drain write-through buffers to the shared L2.
  • Temporal coherence: leases/timestamps let copies expire without invalidation messages.
  • Still delivers SC for DRF, not SWMR in real time.

Scoped synchronization

  • Scopes like CTA/block, GPU/device, system. A release at block scope only needs to reach the SM’s L1; system scope must reach CPU-visible memory.
  • PTX memory model: .cta / .gpu / .sys scopes with .acquire/.release/.relaxed.
  • Bug class: scope mismatch (producer releases at CTA scope, consumer on another SM).

CPU + accelerator

  • Heterogeneous consistency: each device may have its own model; the combined system must define cross-device ordering.
  • Hardware-coherent links (NVLink-C2C, CXL.cache, CCIX, CHI) let accelerators cache host memory.
  • Verification: cross-protocol bridges, translating MOESI ⇄ simpler device states, and DMA/IO coherence.
Chapter 7 · Verification mindset

How to verify a cache and coherence subsystem

Primer Ch. 11 plus industry practice. Seniors are judged on what they check, how they stress, and how they know they are done.

Stimulus strategy

  • Shrink the address space: 2–8 hot lines, sometimes mapping to the same set, to force collisions and evictions.
  • Shrink the cache (config knob) so replacement races happen constantly.
  • False-sharing patterns: different bytes, same line, many writers.
  • Random + directed races: GetM vs PutM, upgrade vs invalidate, two upgrades in S.
  • Litmus suites (diy/litmus7 generated) run thousands of iterations with random skew.
  • Randomize NoC latency, credits, arbitration, retry/NACK and ECC error injection.
  • Locks, barriers, atomics and fence-heavy kernels as real-software stress.

Checkers and how they work

  • SWMR monitor: track every copy’s state from interface observations; at most one M/E, M excludes S.
  • Scoreboard: per address, serialize stores in coherence order; each load must return a value in its legal window (not older than the last value the same core saw: CoRR).
  • MCM checker: collect observed rf/co per test, check for cycles against the axiomatic model (TSOtool-style).
  • Protocol assertions: ack counter never negative at quiescence, directory sharer set ⊇ actual sharers, owner field consistent.
  • End-of-test: drain, then compare all cache contents and memory to golden.

Coverage: how you know you are done

  • Every (stable + transient state) × (incoming event) cell hit, including “stall” cells.
  • Every message type on every VC; VC-full and credit-zero conditions.
  • Race crosses: request type at requester × concurrent forward/inv type.
  • Ack count orderings: acks before data, data before acks, 0 acks.
  • Litmus outcomes: every allowed outcome observed at least once; no forbidden one ever.
  • Replacement × in-flight snoop for each dirty state.

Formal & methodology

  • Model-check the protocol at the spec level (Murphi, TLA+) with 2–3 caches, 1–2 addresses: finds deadlocks and SWMR violations early.
  • Formal on RTL: SVA for local controller tables, FIFO/credit correctness, livelock-freedom bounded proofs.
  • Axiomatic specs (herd/cat) as the reference; operational models for scoreboards.
  • PipeCheck/CCICheck style: verify the core pipeline + coherence together against the MCM.
  • Emulation/silicon: long-running litmus and lock torture tests, self-checking.

Chapter 8 · Interview

Interview questions with model answers

Answer shape that works at senior level: definition → mechanism → corner case → how you would verify it.

Coherence vs consistency, in one minute. core

Coherence: per address, single-writer/multiple-reader plus the data-value invariant; makes caches invisible. Consistency: architectural rule on the order of loads and stores across all addresses as seen by all threads. Coherence is a means; the core pipeline (store buffer, OoO loads) plus coherence together implement the consistency model. Example: x86 is perfectly coherent yet allows SB r1=r2=0.

Compute sets, index and tag bits for a 1 MiB, 16-way, 64 B line cache with 48-bit PA. core

Lines = 220/64 = 16384. Sets = 16384/16 = 1024 → 10 index bits [15:6]. Offset 6 bits [5:0]. Tag = 48−16 = 32 bits [47:16]. Tag store per line also holds state bits (3 for MOESI) and replacement bits.

Why add E? Why add O? What does each cost? design

E: a read miss with no other sharers can later write silently, saving the upgrade transaction (huge for private data). Cost: the system must know no sharers exist (wired-OR shared line or directory), and memory may be stale relative to E→M silently, so the E holder must answer forwards. O: lets a dirty line be shared without writing back to memory first; the O holder supplies data. Cost: extra state, owner tracking, more races on O eviction.

What are transient states and why are they where the bugs are? design

Real transactions are not atomic: between request and completion the controller sits in ISD, IMAD, SMAD, MIA etc., and any other message can arrive. Each (transient × incoming message) cell needs a defined action: stall, handle, or impossible. Coverage must hit all reachable cells; formal model checking proves no unexpected cell is reachable.

Walk through S→M upgrade racing with another core’s GetM. race

C0 in S issues Upgrade, goes SMAD. C1’s GetM is ordered first; C0 receives Inv, acks it, and must drop to IMAD, because it no longer has valid data. When C0’s request is serviced it needs data, not just acks. Bug if C0 keeps its old data and writes into it. Verification: directed race test + coverage of SMAD×Inv; scoreboard catches the lost update.

Dirty eviction races with a forwarded request. What happens? race

C0 in M evicts, sends PutM, enters MIA, keeping data in a writeback buffer. Directory meanwhile forwards C1’s GetS/GetM to C0 as owner. C0 must supply data from the WB buffer and transition to SIA/IIA. The directory later sees a PutM from a non-owner and must ack it without updating memory with stale data. Missing either half = stale data or hang.

Why does a directory protocol need multiple virtual networks? design

To break message-dependency cycles. A request may generate forwards, which generate responses. If all share one queue, a full queue of requests can block the responses needed to retire them → deadlock. Separate VNs for request, forward, response (and sometimes writeback) with responses always sinkable guarantee progress.

Snooping vs directory: when do you pick which? design

Snooping: small core counts, low latency 2-hop, needs a totally ordered broadcast medium, bandwidth grows with N. Directory: scales, point-to-point, 3-hop misses, storage overhead and more races. Modern chips are hybrids: snoop filters / inclusive directories at the LLC, directory between sockets, direct cache transfer to save hops.

How does an OoO core guarantee TSO while executing loads out of order? MCM

Loads issue speculatively. The load queue records performed-but-uncommitted loads. Any invalidation or eviction of a line matching such a load triggers a squash and re-execution from that load. Stores retire into a FIFO store buffer and drain in order; loads forward from it for the same thread only. Verification: MP and CoRR litmus tests with injected snoop timing, MCM graph checker.

Store buffering litmus (SB): why allowed on x86, how do you forbid it? MCM

Each core’s store sits in its store buffer while its later load reads memory, so both loads see 0. Forbid with MFENCE or a locked RMW between store and load, which drains the store buffer before the load performs.

How is an atomic RMW made atomic without locking the bus? MCM

Get the line in M, then perform load and store locally while deferring any incoming snoop for that line until the store completes (can’t deadlock: the store is guaranteed to finish). Aggressive versions speculate the load early and check the line wasn’t lost before the store. Under TSO it also drains the store buffer.

What is write atomicity and why does IRIW matter? MCM

Multi-copy atomic: a store becomes visible to all other cores at the same time. IRIW: two writers to x and y, two readers reading in opposite order; if readers disagree on order, writes weren’t atomic. Allowed on Power (stores can reach some cores early through shared store buffers/caches), forbidden on x86, Arm v8, RISC-V.

Design the checkers for a coherence verification environment. verif

(1) SWMR/state monitor with a global view of every cache’s state. (2) Data scoreboard: golden memory with per-address coherence order and a legal-value window per load. (3) Consistency checker building po/rf/co/fr from observed values and detecting cycles. (4) Protocol assertions: directory state ⊇ actual sharers, ack counts, owner uniqueness. (5) Liveness: per-transaction timeouts, MSHR age, VC credit monitors. (6) End-of-test flush and compare.

Your random test passes 10,000 seeds. Why might coverage still be poor? verif

Random addresses rarely collide, so races never happen. Fix: tiny hot address pools, addresses aliased to one set, shrink caches, bias toward same-line multi-writer patterns, randomize interconnect delay to widen race windows, and drive coverage of transient×event cells and race crosses. Pass rate without race coverage proves little.

How do you detect livelock and starvation in simulation? verif

Per-request age counters with thresholds, per-core forward-progress counters (retired memory ops per window), NACK/retry counters per address, latency histograms per requestor under contention (lock torture). Formally, bounded liveness or fairness properties on arbiters.

A load returned a stale value in a 32-core sim. How do you debug? debug

Pull the scoreboard’s history for that address: coherence order of writes and which write this load’s value matches. Find the cache that supplied data and its state at that time. Walk the protocol log for the line: requests, forwards, invalidates, acks, evictions around the window. Usually you find a transient state that handled an unexpected message (upgrade race, eviction crossing a forward, missed squash). Then reduce to a directed test and add coverage for that cell.

What is false sharing and how would you measure it? perf

Different variables in one line, written by different cores → line ping-pongs though there’s no true sharing. Measure coherence misses (HITM / snoop-hit-modified counters), invalidations per line, and line-level address heatmaps. Fixes: padding/alignment, sector-level coherence, or protocol optimizations.

Inclusive vs exclusive vs NINE LLC: verification impact? design

Inclusive: LLC eviction must back-invalidate inner copies (including in-flight fills and WB buffers); assert inclusion invariant at all times. Exclusive: data moves between levels on every L2 eviction; track unique copy. NINE: need an explicit snoop filter; check filter ⊇ actual contents and filter-eviction back-invalidation.

VIPT L1: what problem appears if index bits exceed page offset? core

Synonyms: two virtual addresses mapping to one physical line can land in different sets, creating two copies the coherence protocol (which works on physical tags) doesn’t know are aliases. Fix: keep cache size/ways ≤ page size, page coloring, or alias detection on fill. Test with deliberate aliased mappings.

How is GPU coherence different from CPU coherence? GPU

GPU L1s are often write-through and not kept coherent by invalidations. Coherence is consistency-directed: acquires self-invalidate L1, releases flush pending writes to L2 (point of coherence), at the scope requested (CTA, GPU, system). Gives SC for DRF with scoped synchronization. Verification focus: scope semantics, fence/acquire/release lowering, atomics at L2, CPU–GPU coherence over the link.

What is a scoped memory model and a typical scope bug? GPU

Synchronization operations carry a scope saying which threads they must order with. A release at block scope need not push data past the SM’s L1. Bug: producer releases at CTA scope, consumer on another SM acquires at GPU scope, sees stale data. Hardware must implement each scope correctly; tests need cross-SM producer/consumer at every scope combination.

Where does formal beat simulation for coherence? verif

Protocol-level model checking with 2–3 caches and 1–2 addresses explores all interleavings exhaustively: catches deadlocks and SWMR violations from rare message orderings simulation may never hit. On RTL, formal proves controller tables, credit/FIFO correctness and bounded liveness. Simulation still needed for full-system scale, performance, and pipeline+memory interactions.

What is a litmus test and how do you use one in DV? verif

A tiny multi-threaded program with a specified forbidden/allowed final state. In DV: generate many (diy), run each thousands of times with randomized start skew, cache pre-states and interconnect delay; histogram outcomes. Fail if a forbidden outcome appears; flag coverage holes if allowed outcomes never appear (stimulus too weak to expose relaxations).

Silent vs explicit eviction of S lines: trade-off? design

Silent: fewer messages, but the directory keeps stale sharer bits → unnecessary invalidations, and an inclusive directory can fill with dead entries. Explicit PutS: exact tracking at the cost of traffic and new races (PutS crossing an Inv). Verification must cover both the Inv-to-non-sharer path and the PutS-vs-Inv race.

Primer quiz: “GPUs don’t support hardware coherence, so they can’t enforce a memory model.” GPU

False. They enforce the consistency model through consistency-directed coherence: self-invalidation on acquire and write-back/flush on release, which is enough for SC-for-DRF and scoped models.

What would you put in a cache/coherence verification plan? senior

Spec sources (ISA MCM, protocol tables, interconnect spec). Features list: every request/response type, states, transient states, replacement, inclusion, atomics, fences, DMA/IO, ECC/poison, power states (flush on power-down). Checkers (four types above). Stimulus plan (directed races, constrained random with hot addresses, litmus, software torture). Coverage model with closure criteria. Formal scope. Reuse from unit to cluster to SoC, and emulation/silicon correlation plan.
