Level 1 · Why caches exist

The processor is fast, memory is slow

Story

You are cooking. The counter next to you holds a few things and you can grab them instantly. The fridge is a few steps away. The supermarket is a 30-minute drive. A good cook keeps what they’re using right now on the counter.

A CPU core can do an operation in well under a nanosecond. Fetching from main memory (DRAM) takes around 80–100 ns: hundreds of wasted cycles. So chips keep small, fast memories close to the core. These are caches.

Why does a small cache help so much?

Programs are predictable in two ways. Temporal locality: if you used something just now, you’ll likely use it again soon (the salt). Spatial locality: if you used one thing, you’ll likely use its neighbours (the next item in an array). Caches exploit both.

Check: a loop reads a[0], a[1], a[2] … in order. Which locality does that show most?

Level 2 · Basic words

Hit, miss and the cache line

Story

You need one egg. You don’t drive to the shop for one egg; you bring home a whole tray of 12. Next time you need an egg it’s already at home.

When the core asks for data and it’s in the cache, that’s a hit (fast). If it isn’t, that’s a miss: the cache fetches it from the next level and keeps a copy.

Caches never fetch one byte. They fetch a fixed chunk called a cache line (or block), usually 64 bytes. That’s the egg tray. It is also the unit that everything later in this guide is about.

Three reasons for a miss (the “3 C’s”)

  • Compulsory: first time ever touching it.
  • Capacity: the cache is too small to hold everything you’re using.
  • Conflict: two lines fight for the same spot (Level 3).

Later we add a 4th: coherence misses, when another core took your copy away.

Hit rate is everything

Average time = hit time + miss rate × miss penalty.

4 + 0.05 × 300 = 19 cycles

Even a 5% miss rate makes memory look ~5× slower than a hit. Small improvements in hit rate matter a lot.

Check: line size is 64 bytes. The core reads 1 byte at address 100. How many bytes come into the cache?

Level 3 · Organization

Where does a line go? Tag, index, offset

Story

A school has lockers numbered 0–3. Rule: your locker = remainder when your roll number is divided by 4. Roll 5 and roll 9 both get locker 1. To know whose stuff is in locker 1, a name tag is stuck on it.

The memory address is split into three pieces:

  • Offset: which byte inside the 64-byte line (6 bits, because 26 = 64).
  • Index: which set (locker row) to look in.
  • Tag: the name tag, stored next to the data, to check that the line there is really ours.

A set can hold several lines; each slot is a way. 1 way = direct-mapped. N ways = N-way set-associative. One set with all lines = fully associative. More ways means fewer conflict misses but more tags to compare.

Try it · split an address

Example cache: 16 bit address, 64 B lines, 16 sets. Type any number 0–65535.

tag (6 bits)index (4 bits) → setoffset (6 bits) → byte in line

The formula freshers get asked

sets = cache size ÷ (ways × line size)
index bits = log2(sets)  ·  offset bits = log2(line size)
tag bits = address bits − index − offset

Example: 32 KB, 8-way, 64 B → 32768 ÷ (8×64) = 64 sets → 6 index bits, 6 offset bits.

Check: 16 KB cache, 4-way, 64 B lines. How many sets?

Level 4 · Replacement

When the cache is full, someone leaves

Story

Your desk holds 4 books. You need a 5th. Which book goes back to the shelf? Usually the one you haven’t opened for the longest time.

Choosing which line to kick out is replacement; the line kicked out is the victim, and kicking it out is an eviction. Common policy: LRU (least recently used), or a cheaper approximation called pseudo-LRU.

Level 5 · Write policy

What happens when you write?

Story

You change a phone number in your pocket notebook. Do you also phone home every time to update the family diary (write-through)? Or do you update the diary only when the notebook page is torn out (write-back)? Then the page needs a small mark saying “changed, copy me before throwing away”: the dirty bit.

Write-throughWrite-back
On a writeUpdate cache and next levelUpdate cache only, mark line dirty
On evictionNothing to doIf dirty, write the line back
TrafficHighLow
Where usedMany GPU L1 caches, simple designsCPU caches

The store buffer (remember this for Level 11)

A core doesn’t want to wait for a write to finish. It drops the write into a small queue, the store buffer (an outbox tray), and carries on. The store reaches the cache a bit later. This one tiny trick causes most of the “weird ordering” behaviour you’ll meet later.

Level 6 · The problem

Many cores, many copies, one truth

Story

The class timetable says Physics is in Room 152. Three friends copy it into their own notebooks. The teacher moves the class to Room 252 and only one friend updates her notebook. The other two go to the wrong room. Nobody did anything wrong individually; the problem is stale copies.

Modern chips have many cores, each with its own private L1 (and often L2). If two cores cache the same line and one writes, the other’s copy is now out of date. Keeping all copies in agreement is cache coherence. The set of rules that does it is a coherence protocol.

Level 7 · The rules

The golden rule: one writer or many readers

Story

The class has one pen for the shared timetable. Anyone can look at the timetable together. But to write on it, you must hold the pen, and while you hold it, everyone else must close their copies and wait. When you finish, others re-copy the latest version.

Rule 1 · SWMR

Single Writer or Multiple Readers

For any line, at any moment: either exactly one core may write it, or any number of cores may only read it. Never a writer plus anyone else.

Rule 2 · Data value

Readers see the latest write

When a new reading period begins, everyone must get the value left by the last writer. Correct permissions with old data is still a bug.

Almost every real protocol (called an invalidation protocol) works like the pen: before writing, a core asks everyone else to invalidate (throw away) their copies. Coherence is tracked per cache line, not per byte, which matters in Level 9.

Check: Core 0 is writing line A. Can Core 1 read line A from its own cache at the same moment?

Level 8 · States

MSI: three stickers on every line

Story

Every notebook copy gets a sticker. M = “I hold the pen, my copy is the newest”. S = “read-only copy, others may have it too”. I = “torn out, don’t trust it”.

StickerNameCan read?Can write?Plain meaning
MModifiedYesYesOnly copy, newer than memory (dirty)
SSharedYesNoClean read-only copy, maybe others too
IInvalidNoNoNot usable, must ask again

The two requests

GetS “I want to read” → you end in S (others in M drop to S and share their newest data).
GetM “I want to write” → everyone else goes to I, you end in M.

Try it · three friends, one line A

Press buttons and read the story in the log. Watch the two rule-checks stay green. Try: Asha reads, Ben reads, Ben writes, Asha reads.

Check: Asha is in M. Ben does GetS. What are their stickers after?

Level 9 · Upgrades

Extra stickers: E and O

MESI adds

E Exclusive

Story: you borrowed the timetable and you notice nobody else has a copy. If you later want to write, you don’t need to ask anyone: just switch your sticker to M quietly.

Saves a message for data only one core uses, which is very common.

MOESI adds

O Owned

Story: you changed the timetable and friends want to read it. Instead of first walking it back to the office, you let them copy from you and you stay responsible for returning it later.

Shares dirty data without writing memory first.

False sharing

Story: two friends write in different corners of the same page. They only own whole pages, so they keep passing the page back and forth, even though they never touch each other’s writing. In hardware: two variables on the same 64-byte line, written by different cores, make the line bounce. Fix: put them on different lines.

Transient states (a peek at real life)

Asking for the pen isn’t instant. Between “I asked” and “I got it”, a cache is in between states, like IS (asked to read, waiting for data) or IM (asked to write, waiting for data and everyone’s “OK, I threw mine away”). Messages from others can arrive during this wait. Most real coherence bugs are hidden here.

Check: a line is in E. The core writes to it. What messages are sent?

Level 11 · Consistency

Coherence isn’t enough: order matters

Story

The teacher (1) emails the web admin to update the room, then (2) texts students “check the website”. The text arrives first, a student checks the website, still sees the old room. Each message was correct; the order they arrived in was the problem.

Coherence is about one line. A memory consistency model is the rule for the order in which loads and stores to different addresses can appear to other cores. It is part of the ISA spec (x86, Arm, RISC-V each have one).

ModelIn plain wordsWho uses it
SC Sequential ConsistencyAs if all cores took turns on one memory, each in its own program order. The easiest to reason about.Reference model, textbooks
TSO Total Store OrderLike SC, but your own writes may sit in your store buffer while your later reads go ahead.x86 (Intel, AMD)
Relaxed / weakAlmost any reordering allowed unless you add a fence (a “wait until earlier stuff is done” instruction).Arm, RISC-V, Power, GPUs

Level 12 · GPUs

GPUs do it differently

Story

A school with 5,000 students can’t have the teacher run around tearing pages out of everyone’s notebook. Instead the rule is: before you start using shared notes, you throw away your old copy and fetch fresh; after you finish writing, you hand your updates to the office. No one chases you.

GPUs have thousands of threads, so classic invalidation messages are too costly. Many GPU L1 caches are write-through and keep no strict coherence. Correctness comes from synchronization:

  • Acquire (start of sharing): throw away possibly old L1 data.
  • Release (end of sharing): push your writes to the shared L2.
  • Scope: how far the sync must reach: just my thread block, the whole GPU, or the whole system including the CPU.

If programs synchronize properly, the result looks just like SC. This is called SC for data-race-free programs.

Check: on a GPU, when does a thread drop its possibly stale L1 data?

Level 13 · Verification

How do we test all this?

Story

To test the classroom pen rule, you’d hire a hall monitor who watches every notebook at all times, keep a master copy of the timetable to compare against, make students fight over the same page as often as possible, and set an alarm if anyone waits too long.

Hall monitor

SWMR checker

Watches every cache’s state for every line. Fires an error if there’s ever a writer plus anyone else.

Master copy

Scoreboard

A reference memory that records every write in order. Every read is compared: did the core get a value it was allowed to see?

Same page fights

Stimulus

Random tests with only a few addresses, tiny caches and lots of evictions, so races happen often. Plus litmus tests and directed race scenarios.

Alarm

Hang watchdogs

Timeouts on every request so a deadlock (everyone waiting on each other) or starvation (one core never gets the line) is caught.

And how do we know we tested enough?

Coverage: a checklist the testbench fills in automatically. Did we see every state receive every kind of message? Did two cores ever race to write the same line? Did an eviction ever cross paths with a request? Unfilled boxes tell you which tests to write next.

Check: random tests use the full 48-bit address range and all pass. Why is that weak evidence?

One-page cheat sheet

Cache line
64-byte chunk moved and tracked as one unit.
Hit / miss
Found in cache / had to fetch from further away.
Tag·Index·Offset
Name tag · which set · which byte in the line.
Ways
Slots per set. More ways, fewer conflict misses.
LRU
Evict the least recently used line.
Write-back
Write cache only; mark dirty; write memory on eviction.
Store buffer
Core’s outbox for pending writes; source of reordering.
Coherence
All copies of one line agree (SWMR + latest value).
M / E / S / I / O
Modified · Exclusive clean · Shared · Invalid · Owned dirty-shared.
GetS / GetM
Request to read / request to write.
Snoop / Directory
Broadcast to all / central register of who has what.
Consistency

SC / TSO / weak

Fence
