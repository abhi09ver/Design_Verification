    Interviewers at CPU shops are not checking whether you know what a ROB is. They check whether you can turn an architecture into invariants, find where those invariants break under concurrency and speculation, and prove you covered it. Answer every design question by walking these four layers.

    Spec

    • ISA manual = architectural contract (what is visible)
    • Microarch spec = intent (how, when, how many cycles)
    • Separate “legal” from “expected” behaviour; list the implementation-defined choices

    Design

    • Find every place state is speculative and every place it becomes committed
    • Find every shared resource with arbitration or credits
    • Those two lists are your bug map

    Verify

    • Constrained-random + directed + formal, chosen per block
    • Stress knobs: tiny queues, aggressive flush, throttled memory, random back-pressure
    • Track holes, not just percent; show why each unhit bin is unreachable or waived

    Interview drill

    How would you verify a new out-of-order core from scratch?

    Start with lock-step co-sim against an ISS at retirement; it is the highest-value checker. Add unit scoreboards where co-sim gives poor debug locality (LSU, MMU, caches). Write SVA for structural invariants and use formal on small control blocks (free list, arbiters, ROB pointers). Build a random instruction generator with hazard-density knobs, exception/interrupt injection, and self-modifying code. Close with coverage on micro-architectural events, not just instructions.

    Co-sim says “match” on every instruction. Can a bug still exist?

    Yes: performance bugs (missed forwarding, stuck predictor), bugs masked by later overwrite, non-determinism in multi-core ordering where the ISS picks one legal order, timing of interrupts, and debug/PMU state the ISS does not model. Also a hang never retires, so you need watchdogs and forward-progress assertions.

    What makes a scoreboard hard for a speculative block?

    The DUT does work that is later thrown away. The scoreboard must either track speculation and flush exactly what the DUT flushes, or only compare at a commit point. Senior answer: compare at commit for correctness, and add a separate checker on the flush mechanism itself (correct age-based kill, no survivors younger than the mispredict).

    Interview drill

    Snoop arrives while a core is entering a power-gated state. What must the design guarantee?

    Either the core flushes its dirty lines and the snoop filter drops it before power-off, or the power controller blocks entry until outstanding snoops drain. Verification: race directed tests on the handshake, assertions that no snoop is sent to a powered-off agent, and coverage on each step of the entry sequence.

    Why do deep pipelines hurt?

    Branch penalty scales with the number of stages before resolution; more forwarding paths; latch overhead stops cycle-time gains; more power. Best depth balances CPI growth against frequency.

    Interview drill

    Two branches resolve mispredicted in the same cycle. What must happen?

    Only the older one's recovery counts: flush everything younger than it, including the younger branch. Coverage: same-cycle, back-to-back, and younger-resolves-first cases. Assertion: after recovery, no ROB entry younger than the redirecting branch remains valid.

    The RAS wraps on overflow. What do you cover?

    Call depth exactly at, one above, and far above capacity; return storms after deep recursion; a call or return on a wrong path followed by recovery (pointer and the overwritten entry must both be restored, or the design must document that only the pointer is); mismatched call/return pairs such as longjmp. Correctness never depends on the RAS, so co-sim stays clean; the check is on the RAS pointer after recovery plus a perf counter for return mispredicts.

    How do you verify the predictor without a reference model of it?

    Correctness does not need one: any prediction is legal, so check only that recovery is exact. Checking quality needs a C++ perf model fed the same trace; compare MPKI per benchmark and flag drift beyond a tolerance.

    Interview drill

    Which stages are in order and which out of order in a ROB-based core?

    Fetch, decode, issue and commit are in order. Dispatch, execute and write-result (broadcast) are out of order. This is the quiz in your notes; in interviews follow it with “so I compare against the ISS at commit, where the order is architectural again”.

    Commit writes the RF even when a younger instruction has renamed the same register. Why is that correct, and what should you assert?

    The RF must always hold the latest committed value; younger writers are still speculative. The RAT entry is cleared only if it still points to the committing ROB entry, otherwise it keeps pointing to the younger producer. Assert: at commit, if rat[rd] == rob_idx it becomes RF-valid; if it points elsewhere it is unchanged and the target ROB entry is younger and valid.

    In one cycle an instruction issues with Rd = F0 and a broadcast for the old F0 producer arrives. What breaks if the priority is wrong, and how do you catch it?

    If the broadcast clears the RAT entry after issue wrote it, later instructions read the RF and get the older value instead of waiting for the new producer. Directed test: force issue and broadcast to the same register in the same cycle, with a dependent right behind. Assertion: if issue writes rat[rd] this cycle, then next cycle rat[rd] holds the new tag regardless of any broadcast. Co-sim catches it too, but only if a reader follows closely enough.

    How do you check for physical register leaks?

    Conservation invariant every cycle: free + mapped-in-RAT + held-in-ROB-as-old-mapping = total pregs. Also at quiescence (pipe empty), free = total − arch regs. Add SVA that free list never holds duplicates, and a formal proof on the free list block.

    Why does renaming remove WAR/WAW but not RAW?

    WAR and WAW are name conflicts: two writes, or a read and a later write, use the same architectural name. Giving each write a new physical name removes the conflict. RAW is a true data flow; the value must exist before use.

    Exception and branch mispredict in the same cycle, different instructions?

    Age decides. If the branch is older, its flush kills the excepting instruction (wrong path, never reported). If the excepting op is older, it handles when it reaches ROB head and the branch is flushed. A common bug is taking the exception from a wrong-path instruction.

    Loads want to run early; stores must not write memory until commit. The load-store queue lets loads bypass older stores whose addresses are known, forwards store data to loads, and catches the case where a load guessed wrong.

    Interview drill

    Design a scoreboard for an LSU.

    Keep a byte-granular shadow memory updated at store commit. For each load at commit, expected data = bytes from older committed stores in shadow memory overlaid with older not-yet-drained stores in a model store buffer. Compare at commit, not at execute, so violations that get flushed are not false failures. Separately count violation flushes to check the predictor is not stuck.

    Single-core test passes; what LSU bug appears only on multicore?

    A load executed early whose line is invalidated by another core before it commits. Under TSO it must be replayed, or two loads can appear reordered. Requires a snoop of the load queue on invalidation.

    Interview drill

    Why can’t a “better” VLIW run old 2-op bundles two at a time without changes?

    The compiler only guaranteed independence inside a bundle. Two bundles side by side may depend on each other, so the hardware must check dependences, which makes it a superscalar, not a VLIW. This is the backward-compatibility weakness from your notes.

    A conditional-move instruction with a false condition reads a bad address. What should happen, and how do you test it?

    It depends on the ISA spec, which is the point to raise first. For a register-only cmov there is no memory access. For a predicated load, a false predicate must suppress the fault. Test with page tables that make the source unmapped, sweep predicate true/false, and check co-sim for no trap when false and a precise trap when true.

    Interview drill

    Write the reference model for the LRU counter scheme in your notes, and the invariant.

    On an access to way w with counter c: every way with counter > c decrements, w becomes N−1. On a miss, the victim is the way with counter 0. Invariant every cycle: the counters in a set are a permutation of 0..N−1. That one SVA catches almost every update bug, including two ways hit in the same cycle.

    Why do you shrink caches in verification?

    Real-size caches rarely evict in short tests, so eviction, writeback and replacement races stay uncovered. A parameterised small config hits them in every test. Keep a few full-size regressions for timing and indexing bugs.

    What is the VIPT aliasing problem and when is it absent?

    If index bits extend beyond the page offset, two virtual addresses mapping to one physical line can sit in different sets. It is absent when size/ways ≤ page size (32 KB / 8 = 4 KB). Otherwise use page colouring or alias detection on fill.

    Every access translates a virtual address through the TLB. A miss starts a hardware page walk; a fault reaches the OS precisely. Translation is where security, OS interaction and speculation collide.

    Spec

    • A/D bit update: hardware vs trap to software
    • Ordering of PTE stores vs later walks: needs SFENCE.VMA / TLBI / INVLPG

    Design

    • Multi-core: TLB shootdown via IPI or broadcast TLBI

    Verify

    • Generate page tables randomly: mixed sizes, illegal combos, shared frames, aliases
    • Cover: fault on line-crossing access, walk hits dirty line in L1, fence racing in-flight walk
    • Co-sim must include the ISS’s walker and A/D behaviour

    Bugs that ship

    • Stale TLB entry used after SFENCE because a walk in flight refilled it
    • Page-crossing load faults on the second page but first half already forwarded
    • Wrong-path walk sets the Accessed bit (spec violation on some ISAs)
    • Global bit ignored on ASID flush

    Interview drill

    How would you stress TLB shootdown?

    Several cores share pages; one core repeatedly rewrites PTEs and issues fences while others access those pages. Check with a checker that no core uses a translation after its fence completes. Cover fence during walk, fence during TLB fill, and fence with ASID filter.

    Main memory is organised in channels, ranks, banks and rows. Latency depends on whether the row is already open. Reliability features (ECC, parity, RAS) add their own verification surface.

    Spec

    • JEDEC timing parameters and refresh interval
    • ECC: SECDED corrects 1 bit, detects 2; chipkill for whole-device fail

    Design

    • Scheduler: FR-FCFS favours row hits; must prevent starvation
    • Address mapping interleaves banks/channels
    • Parity on arrays, ECC on caches and memory

    Verify

    • Timing checker assertions on every JEDEC parameter
    • Error injection: single/double/multi-bit, in each array, and check logging and poison
    • Starvation coverage: max wait per requester under hostile patterns

    Interview drill

    How do you verify poison propagation?

    Inject an uncorrectable error in a line, then follow it: the consuming load must raise a precise machine check, a non-consuming eviction must keep the poison marker, a write that fully overwrites the line must clear it. Cover poison in a forwarded store, in a prefetch, and in a page-table walk.

    Coherence guarantees one writer or many readers per line, and that every core eventually sees the latest write. Stable states are easy; the real bugs live in transient states, where requests cross on the interconnect.

    Spec

    • SWMR invariant: single writer or multiple readers per line per epoch
    • Data-value invariant: a read returns the last write of the previous epoch
    • Protocol spec (CHI etc.) defines legal request/snoop/response combos

    Design

    • Directory: full bit-vector, coarse, or limited pointers; inclusive snoop filter
    • Virtual channels separate requests/responses to avoid protocol deadlock
    • Home node serialises requests to the same line

    Verify

    • Global SWMR checker observing every cache's state at once
    • Few lines, many cores, random delays → maximise races
    • Model-check the protocol tables (Murphi, TLA+, JasperGold) before RTL
    • Cover every (state × incoming message) cell, including “impossible” ones as assertions

    Bugs that ship

    • Writeback races with a forwarded snoop: home gets stale data
    • Upgrade (S→M) loses to a remote RdX; requester must convert to full miss
    • Snoop filter eviction does not back-invalidate
    • Deadlock: responses blocked behind requests in a shared queue

    Interview drill

    Core A in S sends Upgrade; core B's RdX for the same line reaches A first. What happens?

    A invalidates (S→I) while its upgrade is outstanding. When the upgrade reply comes, A no longer has the data, so the controller must treat it as needing data (often the home NACKs or converts to RdX). Verification: directed race test plus coverage on transient state SM^A × snoop Inv.

    How do you detect a coherence deadlock in sim?

    Per-transaction watchdog timers, a global forward-progress check that some core retires within N cycles, and liveness properties in formal for the protocol controller. Debug: dump every queue's head and the dependency it waits on to find the cycle.

    • SC succeeds after the reservation line was evicted
    • Atomic split across two cache lines is not atomic

    Interview drill

    Why is SB allowed on x86 and what fixes it?

    Each core's store sits in its store buffer while its younger load reads the old value from cache. MFENCE (or a locked instruction) between the store and load drains the buffer first.

    How do you check consistency when the ISS picks one order?

    Do not lock-step multi-core shared data against one order. Log every load value and store order from RTL, then check that some legal execution under the model explains them (axiomatic check: no cycle in po-loc ∪ rf ∪ co ∪ fr plus the model's preserved-order relations).

    Spin lock with test-and-test-and-set: why better than test-and-set?

    Waiters spin on a shared copy of the line (reads hit in S) instead of each attempt being a write that invalidates every other cache. Coherence traffic drops from O(N) per attempt to bursts only when the lock is released.

    Interview drill

    What new bug classes does SMT add?

    Thread-ID mismatch on shared structures (wrong thread's entry flushed or forwarded), starvation of one thread, store-to-load forwarding across threads (must not happen), and shared-predictor security leakage. Coverage must cross every flush source with the other thread's state.
