01

Architecture: CSR file to pad and back

GPIO is a memory-mapped peripheral. The CPU writes CSRs over APB. The CSRs drive the tristate buffers on the way out. On the way in, pin levels pass through optional synchronizers into the input register and the interrupt logic, which raises one level-type o_intr.

It's a memory-mapped APB slave. The direction register drives each pad's output enable and the data register drives its value. Inputs come back through an optional 2-flop synchronizer and glitch filter, into a per-pin level/edge detector. That detector feeds sticky, write-1-to-clear status, which is masked and OR-reduced into one level interrupt.

GPIO_WIDTH [1–32], default 6

Test the edges: 1 (degenerate OR-reduce), 31, 32 (no reserved bits left). Check that bits [31:W] read 0 in every register.

DEF_O_VAL · DEF_IO_DIR

Per-bit reset values. DEF_IO_DIR: 1 = input, 0 = output. Many MCUs use the opposite polarity, so call it out. Default-input is the safe power-up state because no pin drives.

EN_SYNC · EN_GLF

Per-pin bitmasks. A glitch filter exists only on pins that also have a sync. Randomize the masks per build, and the TB must know each pin's latency and filtering.

04

Interrupt pipeline, one pin, end to end

Most of the bugs in this block are in this path. Each stage is a place where an event can be lost, duplicated or delayed.

Level vs edge, behaviour to verify

  • Edge: latches on the transition and stays set until W1C. Check: one edge gives one status set. Two edges before the clear still give one bit (events merge, and the bit doesn't count them).
  • Level: sets while the pin is at the active level. If the pin is still active when the ISR clears the bit, it re-sets next cycle, so the ISR has to remove the source first or you get an interrupt storm.
  • Polarity comes from evnt: 1 = high/rising, 0 = low/falling.

Enable vs mask, the classic trick question

  • IE = 0 clears status and drops future events. The event is gone.
  • ME = 1 keeps latching but hides the bit from o_intr. The event waits.
  • GIE = 0 holds o_intr low, but status still latches underneath.
  • Test: event while masked → read raw (1) and masked (0) → unmask → o_intr rises with no new event.
Enable decides whether an event is recorded. Mask decides whether a recorded event is reported. I always run the masked-pending-then-unmask test, because that's where designs either lose an event or fire a stale one.
05

Tristate, CDC and reset

Tristate buffer UG §8

OE=1 drives the pad with o_data. OE=0 releases it to Hi-Z so an external driver controls it.

  • FPGA: the buffer stays inside the core so it maps onto IOBs.
  • ASIC: remove the wrapper and expose OE and data, or put in library pad cells. This is exactly the interface a pinmux consumes.
  • TB checks: no contention (DUT OE=1 while TB drives gives X), Hi-Z when input, and a pull resistor in the TB so a floating pin is caught.

CDC: 2-FF sync and glitch filter UG §5

  • Pins are asynchronous to clk. Without a sync, metastability reaches the edge detector and can cause double or missed edges.
  • RTL sim never shows metastability. Use a CDC tool structurally, and inject a random 0/1-cycle delay on sync outputs in sim.
  • Pulses shorter than about 2 clk (or the filter window) can vanish. Test pulse widths of 1, 2, N−1, N, N+1 clk at random phase.
  • Where EN_SYNC=0, the pin must already be synchronous. The UG says to enable sync for async interrupt sources.

Reset UG §7

  • resetn is asynchronous active-low. Assertion is async, and release must be synchronized to clk.
  • Sequence: assert reset → start clk → hold ≥ 8 clk → release.
  • areset_sync.sv ships in src/. The UG says to synchronize release externally, so check whether the core or only the board top uses it. INFERRED
  • Tests: reset values per parameter, reset in the middle of an APB transfer, reset while pins drive, and no pad glitch through reset.

APB timing: write 2 cycles, read 3

UG §7

Protocol assertions to bind

// setup then access
a_setup: assert property (@(posedge clk) disable iff(!resetn)
  $rose(i_psel) |-> !i_penable ##1 i_penable);
// hold everything stable until ready
a_stable: assert property (@(posedge clk) disable iff(!resetn)
  (i_psel && i_penable && !o_pready) |=>
  $stable({i_paddr,i_pwrite,i_pwdata}));
// read data never X on completion
a_rd_known: assert property (@(posedge clk) disable iff(!resetn)
  (i_psel && i_penable && o_pready && !i_pwrite) |-> !$isunknown(o_prdata));

APB tests

  • Back-to-back transfers with no IDLE in between, and random IDLE gaps.
  • Unmapped offsets 0x2C–0xFC: no side effects, and the read returns 0. With no PSLVERR, error reporting is a SPEC GAP.
  • Unaligned addresses (paddr[1:0] ≠ 0): does it alias or ignore? Find out and write it down.
  • Writes to RO regs, reads of WO set_rg.
  • Write to sts (W1C) in the same cycle as a pin event.

What the shipped testbench proves

  • The happy-path ISR loop works in one configuration (4-bit tristate, interrupts on).
  • On a Basys-3 at 100 MHz, the UG test summary lists every mode with and without interrupts, and level and edge at both polarities: "successfully passed".

What it doesn't prove, and where you come in

  • No constrained-random stimulus, no scoreboard or reference model, and no functional coverage.
  • Untested: race conditions (W1C vs event, IE toggling), widths 1/32, mixed EN_SYNC masks, glitch thresholds, unmapped accesses.
  • A board test only shows what a human could see on LEDs. It can't show a one-cycle spurious interrupt.

Covergroups

covergroup cg_pin_cfg with function sample(int i);
  dir  : coverpoint io_dir[i];
  ie   : coverpoint intr_en[i];
  me   : coverpoint intr_mask[i];
  typ  : coverpoint intr_type[i];   // level/edge
  evt  : coverpoint intr_evnt[i];   // low-fall/high-rise

  x_kind_out : cross kind, outcome;
  pw : coverpoint pulse_clks {bins b1={1}; bins b2={2};
       bins thr[]={[GLF-1:GLF+1]}; bins long={[GLF+2:$]};}

Assertions bound to the DUT

// interrupt output is purely status + GIE (allow 1-clk reg)
a_intr: assert property (@(posedge clk) disable iff(!resetn)
  o_intr == $past(glb[0] && |(sts_masked)) );

// status can't rise on a pin whose IE is 0
a_ie: assert property (@(posedge clk) disable iff(!resetn)
  !intr_en[i] |-> !sts_raw[i]);

// W1C clears (edge type, no new event that cycle)
a_w1c: assert property (@(posedge clk) disable iff(!resetn)
  (wr_sts && pwdata[i] && intr_type[i] && !evt[i])
   |=> !sts_raw[i]);

// tristate: release pad when input, drive when output
a_z:   assert property (@(posedge clk)
  io_dir[i] |-> ##[0:1] (dut_oe[i] == 1'b0));
a_drv: assert property (@(posedge clk)
  !io_dir[i] |-> io_gpio[i] === o_data[i]);

// reserved bits always read 0
a_rsvd: assert property (@(posedge clk)
  rd_done |-> (o_prdata >> GPIO_WIDTH) == 0);

Internal names like sts_masked and dut_oe are placeholders. Map them to the real RTL signals once it's unlocked. Use generate to loop i over the pins.

Code coverage tells you every line ran. It doesn't tell you a W1C landed on the same cycle as an edge. That's why the race cases get their own covergroup, and why I close on functional coverage first.

Spec gaps found by reading the UG

SPEC GAP

Interviewers like hearing that you read the spec critically. Each of these would become a clarification ticket and a test.

sts_reg listed RO, but it's W1CTable 6.1 says RO, and the text says to write 1 to clear. The RAL access type must be W1C, or bit-bash will flag it.
How GIE and GME interactGME ("global mask enable") isn't defined against per-pin ME. Is the mask ignored when GME=0? Every assumption here goes into the ref model, so get it in writing.
Raw status has no clear of its ownThe raw register is cleared through the masked register's W1C. Can you clear a raw bit that is currently masked? Test it both ways.
"32-bit address space", 8-bit paddrThe map ends at 0x28. What do 0x2C–0xFF return, and do unaligned addresses alias?
No PSLVERRBad accesses can't be reported. Confirm they complete silently with no side effects.
Set/clear priorityW1C and a hardware set in the same cycle, and set_rg with a W1C in the same cycle, aren't specified. The usual safe choice is that set wins.
Latency and filter lengthNo sync or glitch-filter cycle counts and no minimum pulse width. Needed for the checker window and for the firmware spec.
No atomic set/clear for o_dataFirmware has to read-modify-write, which races between ISR and main loop. It's a design critique point, since many MCUs add SET/CLR registers.
Typo: gpio_intr_set_rgThe table name doesn't match the convention. Small, but it breaks generated RAL and header names.
Reset: external sync vs areset_sync.svThe doc says release must be synchronized externally, yet a synchronizer ships in the package. Which one is it?

Your story: from GPIO core to pinmux

The bridge is the ASIC note in the UG: remove the tristate buffer and expose OE and data. In an SoC those signals go into the pinmux, alongside UART, SPI, I²C and PWM, before reaching the pad cell. Your pinmux work is the system-level version of this IP.

STAR outline. Swap the [brackets] for your real numbers.

S

Situation

  • SoC with [N] multiplexed pads. Each pad selects GPIO or one of [k] alternate functions (UART, SPI, I²C, PWM…) through pinmux CSRs.
  • Pad attributes: pull-up/down, drive strength, input enable.
  • The GPIO block was APB-mapped with level/edge interrupts, like this IP.
T

Task

  • I owned verification of the pinmux and GPIO pad path: every pad×function route, direction, reset defaults and pad attributes.
  • Plus GPIO interrupt routing through the mux.
  • Goal: [100% cross pad×func] before [tape-out / milestone].
A

Action

  • Built a pad agent with per-pin drive/Z and a pull model, and a reference table mapping (pad, sel) → expected source and sink.
  • Random mux configs through RAL, including live re-muxing during traffic.
  • Assertions: only the selected function's OE reaches the pad, and unselected inputs are gated.
  • [Formal connectivity / scripts generated from the pin spreadsheet].
  • Coverage: pad × func × dir × pull, plus mux switches.
R

Result

  • [X] bugs found, e.g. [your best one].
  • Coverage closed at [Y%] with waivers reviewed.
  • The pin-spreadsheet-driven checks were reused on [next project].
  • What I'd do differently: [e.g. start formal connectivity earlier].

90-second spoken version

"On my last project I owned pinmux and GPIO verification for a [N]-pad SoC. Each pad could be GPIO or one of [k] peripheral functions, picked by mux-select registers, and the GPIO itself was an APB block with per-pin direction and level or edge interrupts.

I wrote the testplan from the pin spreadsheet, so every pad and function pair became a coverage bin. I built a pad agent that drives or releases each pin and models pulls, so a floating pin shows up instead of reading as a quiet zero. A reference model predicted which function owned each pad. I ran random mux configurations through the register model, including re-muxing while traffic was running.

The bug I'm proudest of was [your bug]. [If true for you: when a pad switched from UART to GPIO input, the line went from idle-high to the pad's pull-down and the GPIO edge detector logged a falling edge, which was a spurious interrupt. We fixed it by [gating IE during reconfig / documenting a firmware sequence].]

We closed at [Y%] functional coverage with [X] bugs filed. If I did it again, I'd generate the connectivity checks straight from the spreadsheet and run formal connectivity on day one, because simulation is slow at covering N×k routes."

Pinmux bug patterns to draw on

  • Spurious GPIO edge interrupt when a pad's function or pull changes.
  • OE from an unselected function leaking to the pad, causing contention.
  • Wrong reset-default function, so a pad drives at power-up.
  • Input not gated for unselected functions, so a UART sees GPIO toggling.
  • Open-drain (I²C) pads driven push-pull high.
  • Mux-select index off by one, or swapped pads between spreadsheet and RTL.
  • Interrupt still enabled on a pad now owned by another function.

Follow-ups they'll ask about your story

  • How did you scale to N×k combos? (Coverage cross with ignore_bins for illegal combos, plus formal connectivity.)
  • How did you model the pad? (wire with strengths, pullup/pulldown, Z detection.)
  • Who owned the pin spreadsheet, and how did you catch it drifting from RTL? (Generate the checks from it.)
  • Did you verify pads at gate level or with the real pad library? (Behavioural vs library models.)
  • What did you not verify, and why? (Analog pad behaviour, slew, ESD: out of scope.)
Put "I" on your own work: "I built the pad agent", "I found…". Only claim the spurious-edge bug if it really happened on your project. Otherwise present it as "a case I made sure to cover".

Interview Q&A with likely follow-ups

The grey line is the short answer to give first. Open a question for depth and the follow-ups an interviewer will push on. Quiz mode blurs the short answers until you hover over them.

Q01Walk me through the architecture of a GPIO core.APB CSRs → data/dir → tristate pad. Pad → 2-FF/glitch filter → i_data and per-pin level/edge detector → sticky W1C status → mask → OR → GIE → one level IRQ.

Mention the four build modes and that the ASIC version exposes OE/data instead of a tristate.

Follow-ups
  • Why a level output rather than a pulse? An interrupt controller in another domain can miss a pulse, and a level holds until software acknowledges it.
  • Why is status sticky? So an edge isn't lost while the CPU is busy.
  • Two pins in one cycle? Both bits are set, there's one o_intr, and the ISR scans the status.
Q02How do you verify a W1C status register that hardware also sets?RAL W1C access, volatile, predicted by a reference model. Test write-0 no-op, write-1 clear, and clear in the same cycle as a set (agreed priority).
  • Exclude the field from bit_bash, or bit_bash it with no events pending.
  • For level type, expect re-assertion next cycle if the source is still active. The check is "clears, then re-sets", not "stays 0".
Follow-ups
  • How does the predictor handle HW updates? Turn off the mirror compare for the field, or update it from the ref model with predict().
  • The UG says RO but the text says W1C: what do you do? Raise a spec ticket and code to the clarified behaviour.
Q03Interrupt enable vs mask: what's the difference and how do you test it?IE=0 drops and clears events. ME=1 keeps latching but hides them. Test: event while masked, then unmask → o_intr with no new event.
Follow-ups
  • What does GIE add? A global gate on the output only, so status keeps latching.
  • When would firmware use mask rather than enable? A critical section where events must not be lost.
Q04Level vs edge interrupts: which bugs do you hunt in each?Edge: lost or double edges, merging, edges at sync boundaries. Level: storms when cleared while active, stale status after the source goes away.
  • Edge with no sync: metastability can produce a double edge.
  • Reconfiguring type or polarity while IE=1 can create a fake edge out of the detector's history flop.
Follow-ups
  • How many edges do two pulses before the ISR give? One bit, because the bit doesn't count. If counting matters, that's a feature request.
Q05Why a 2-FF synchronizer, and can simulation verify CDC?Pins are async, so the first flop can go metastable and the second gives it time to settle. RTL sim can't show metastability: use a CDC tool and delay injection.
  • MTBF depends on clock frequency, data rate and the flop's resolution time.
  • In sim, randomize a 0/1-cycle extra delay on synchronizer outputs (metastability modelling) and make sure the checks tolerate it.
  • Multi-bit buses can't go through per-bit 2-FF syncs coherently. GPIO is fine because each pin is independent.
Follow-ups
  • Why can EN_SYNC be turned off? To save latency and flops when the source is already synchronous.
  • What's the minimum pulse width? About 2 clk plus the filter window. Pulses shorter than that are lost.
Q06How do you verify the glitch filter?Sweep pulse widths 1…N+1 clk at random phase. Below threshold: no change in i_data or status. At or above: exactly one event.
Follow-ups
  • Why random phase? The clock-to-pulse alignment decides whether a pulse just short of threshold gets counted as N or N−1 cycles.
  • A filter on a pin with no sync? The UG doesn't allow it (GLF needs SYNC). Assert on the config.
Q07How do you model a bidirectional pin in a UVM testbench?Interface with a wire. The TB drives through assign io = en ? val : 'z, only when the DUT dir=input. Add a pull to catch floating, and check for X to catch contention. 
interface gpio_if(inout wire [W-1:0] io);
  logic [W-1:0] tb_en, tb_val;
  for (genvar i=0;i<W;i++)
    assign io[i] = tb_en[i] ? tb_val[i] : 1'bz;
  // pullup/pulldown in top to expose Z
endinterface
Follow-ups
  • Why not drive a logic net? A logic net can't resolve multiple drivers. Use a wire with strengths.
  • In the ASIC version with no tristate, check OE and data at the ports instead.
Q08The IP is parameterized (width, modes, sync masks). How do you verify all of it?A build matrix: 4 modes × widths {1, 6, 31, 32} × random per-pin masks. A config object drives the TB, and tests skip features a build doesn't have.
Follow-ups
  • You can't run every combination, so how do you choose? Edge values plus pairwise coverage on the macros, with random masks per nightly run.
  • How do you avoid one TB per build? A parameterized interface plus a config DB, with `ifdef only at the top level.
Q09What do you check around reset?Reset values per parameter, pins Hi-Z or DEF_O_VAL during and after reset, async assert/sync release, ≥8 clk hold, reset in the middle of a transfer.
Follow-ups
  • Why is default input the safe direction? Nothing drives at power-up, so there's no contention with the board.
  • What breaks if reset release isn't synchronized? Flops leave reset in different cycles, and the CSR or FSM can come up in an inconsistent state.
Q10What happens on an access to an unmapped address?The UG doesn't say and there's no PSLVERR. I'd confirm it completes, reads 0 and has no side effects, then get that documented.
Follow-ups
  • Unaligned addresses? Check whether the decode uses paddr[7:2] (aliasing) or the full address.
  • Would you ask for PSLVERR? For safety-related SoCs, yes, because silent failures hide firmware bugs.
Q11How does your scoreboard check o_intr timing when latency depends on the build?The ref model predicts when status sets. The scoreboard accepts o_intr within a [min,max] window computed from the config. SVA uses ##[min:max].
Follow-ups
  • Why not cycle-accurate? It's brittle across EN_SYNC/GLF builds and metastability injection. A window plus ordering checks is enough.
  • How do you catch a spurious interrupt? Any o_intr rise without a predicted status bit is an error.
Q12You hit 100% code coverage. Are you done?No. Code coverage misses the races: W1C with an event, unmask with pending, IE-off with pending, multi-pin same cycle. Those are functional crosses.
Follow-ups
  • What if coverage plateaus? Look at the holes. Usually a sequence can't line up timing, so write a directed-random sequence that times the W1C against the pin edge.
Q13Critique this GPIO design.Missing: atomic SET/CLR for o_data, PSLVERR, a defined GIE/GME relationship, configurable filter length in a CSR, pull/drive control. Good: per-pin sync/filter masks, sticky status, software set.
Follow-ups
  • Why does atomic SET/CLR matter? A read-modify-write in the main loop can be interrupted by an ISR that writes the same register, and that loses the ISR's write.
Q14Why have a software interrupt-set register?To exercise the ISR and interrupt-controller path without pin stimulus, for firmware bring-up, self-test and DV of the downstream path. It's gated by IE.
Follow-ups
  • What does a read return? It's WO, so expect 0. Verify that it isn't a readable register in disguise.
Q15The shipped TB passes on the FPGA. Why isn't that enough?It's directed and single-config, with no checker. LEDs only show slow, human-visible behaviour. A one-cycle spurious IRQ or a race goes unseen.
Follow-ups
  • What is board testing good for? Real I/O timing, the IOB mapping, and real async inputs (true metastability).
Q16How does GPIO interact with a pinmux, and what bugs live there?GPIO's OE/data/input go through the pinmux to the pad. Bugs: spurious edges on re-mux, OE leaking from unselected functions, wrong reset function, ungated inputs, open-drain misuse.
Follow-ups
  • How do you verify N pads × k functions efficiently? Generate the checks from the pin spreadsheet, use formal connectivity, and use sim for dynamic behaviour (re-mux, interrupts).
  • What's the right firmware sequence to change a pad's function? Disable the pad's IE, switch, clear status, re-enable.
Q17The level interrupt keeps firing after the ISR clears it. Bug or not?Expected if the source is still active, because level status re-sets. The ISR has to service the source first. Show it in a waveform and document it for firmware.
Follow-ups
  • How would you tell it apart from a real bug? Check the synchronized pin value at the cycle the bit re-sets. If the pin is inactive, it's an RTL bug.
Q18Debug: o_intr is high but the status register reads 0.Check GIE/GME and the mask path, a 1-cycle registered o_intr after the clear (timing), stale prdata from a read wait state, or masked vs raw confusion. Read 0x24.
Follow-ups
  • What if it's only intermittent? Suspect the W1C vs event race, so look for a same-cycle event in the waveform at the clear.
